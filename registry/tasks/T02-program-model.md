# T02 Определить сущности версии и модель программы

Цель: **G01**. Волна: **W1**. Профиль: **V1**.

**Статус и основания готовности** ведутся в [оценках](../../docs/verification.md) и [прогрессе](../../docs/verification.md), исполнимость — в [EXEC-1](../exec-progress.json); наличие этой карточки не означает выполнение.

## Результат

Дать точные адреса смыслу, контрактам и реализации, сохранив различие программы и её исполнения.

Контекст: [основа языка](../../spec/foundation.md), [цели](../GOALS.md), [дорожная карта](../PLAN.md).

## Входы и зависимости

Предшественники: [T01](T01-scope.md)

- Профиль T01
- Сценарий авторства и переходы rename/evolve/split/merge
- Рабочая модель записей

Рабочий материал: [01-program-model.md](../../spec/architecture/01-program-model.md). Его нужно завершить и проверить, а не считать готовой нормативной спецификацией.

## Решения, которые необходимо закрыть

- Форматы EntityId RevisionRef Snapshot и canonical hash
- Критерий evolve против replace
- Какие связи являются структурными, декларативными и наблюдаемыми

## Порядок работы

1. Определить схемы записей, равенство, область уникальности и правила сериализации.
2. Развести ID сущности, имя, ревизию, хеш и версию рабочего состояния.
3. Описать переходы идентичности, tombstone и неоднозначные соответствия потомкам.
4. Определить many-to-many соответствие обязательств и операций.
5. Устранить циклы хеширования snapshot/graph/evidence; зафиксировать правила неизменяемости.

## Критерии приёмки

| ID | Проверяемое условие |
| --- | --- |
| T02-C01 | Переименование сохраняет ID и все ссылки. |
| T02-C02 | Одинаковая реализация двух разных сущностей не объединяет их идентичности. |
| T02-C03 | Split/merge сохраняет историю и не назначает преемника угадыванием. |
| T02-C04 | Добавление evidence не меняет SnapshotId. |
| T02-C05 | StateVersion приложения нельзя подставить вместо SnapshotId программы. |

## Обязательные отрицательные случаи

- Граф включает ещё не вычисленный хеш собственного snapshot.
- Старые ссылки переназначены одному потомку split без основания.

## Основание завершения

Для каждого критерия сохранить точные версии предметов, входы, метод, ожидаемый и фактический результат. Лог выполненной проверки отличается от проекта проверки. Ревью должно проверить согласованность с зависимыми спецификациями; нулевое число замечаний без просмотра не является свидетельством.

Задача получает `done`, когда её выходы существуют, все обязательные критерии подтверждены допустимыми evidence и результаты приняты по действующим правилам проекта. Подготовка текста даёт `review`, а не автоматически `done`. Для изменения внешних систем нужны соответствующие полномочия; карточка не предоставляет их.
