# T17 Подготовить передачу в реализацию по компонентам

Цель: **G09**. Волна: **W8**. Профиль: **V1**.

**Статус и основания готовности** ведутся в [оценках](../../docs/verification.md) и [прогрессе](../../docs/verification.md), исполнимость — в [EXEC-1](../exec-progress.json); наличие этой карточки не означает выполнение.

## Результат

Сделать реализацию инженерной работой по определённым контрактам, а не продолжением скрытого проектирования поведения.

Контекст: [основа языка](../../spec/foundation.md), [цели](../GOALS.md), [дорожная карта](../PLAN.md).

## Входы и зависимости

Предшественники: [T16](T16-spec-freeze.md)

- Замороженная спецификация T16
- Карта переиспользования: прежний код не переиспользуется (D64), все компоненты новые ([baseline](../../spec/baseline.md))
- Conformance suite и решения по target

Рабочий материал: [06-specification-completeness.md](../../spec/architecture/06-specification-completeness.md). Его нужно завершить и проверить, а не считать готовой нормативной спецификацией.

## Решения, которые необходимо закрыть

- Границы компонентов и очередность интеграции
- Что переиспользуется, адаптируется или создаётся
- Как измеряется готовность реализации независимо от готовности спецификации

## Порядок работы

1. Разложить реализацию на parser/IR/type/effect/runtime/storage/graph/change/context/protocol/tools компоненты с точными интерфейсами.
2. Для каждого компонента указать нормативные разделы, входы, выходы, ошибки и conformance cases.
3. Построить DAG зависимостей и вертикальный первый срез; определить совместную интеграцию без моков, скрывающих смысл.
4. Определить критерии IMPLEMENTED/VERIFIED/RELEASED и фактические артефакты сборки.
5. Сохранить компактный паспорт задачи и единый реестр прогресса, не копируя все спецификации в каждое задание.

## Планируемые выходы

Эти пути — будущие результаты задачи; их отсутствие сейчас явно означает незавершённую спецификацию.

- `implementation/components/*.md` — паспорта компонентов
- `implementation/backlog.json` — DAG контрактуемых работ
- `implementation/integration-plan.md`
- `implementation/acceptance-map.csv`

## Критерии приёмки

| ID | Проверяемое условие |
| --- | --- |
| T17-C01 | Каждая работа ссылается на конкретное поведение и независимый ожидаемый результат. |
| T17-C02 | Нет обязательной функции V1 без компонента и интеграционного пути. |
| T17-C03 | Переиспользование текущего кода имеет подтверждение T00. |
| T17-C04 | Исполнитель не должен самостоятельно изобретать семантику или критерий готовности. |
| T17-C05 | Изменение спецификации во время реализации имеет версию и повторную проверку последствий. |

## Обязательные отрицательные случаи

- Задача звучит «сделать компилятор» без границ и oracle.
- Фикстура выдаёт заранее правильный граф вместо проверяемого извлечения.

## Основание завершения

Для каждого критерия сохранить точные версии предметов, входы, метод, ожидаемый и фактический результат. Лог выполненной проверки отличается от проекта проверки. Ревью должно проверить согласованность с зависимыми спецификациями; нулевое число замечаний без просмотра не является свидетельством.

Задача получает `done`, когда её выходы существуют, все обязательные критерии подтверждены допустимыми evidence и результаты приняты по действующим правилам проекта. Подготовка текста даёт `review`, а не автоматически `done`. Для изменения внешних систем нужны соответствующие полномочия; карточка не предоставляет их.

## Если условие не выполнено

Вернуть недоопределённую семантику в T16 и соответствующую задачу; локальные инженерные решения допустимы в пределах заданного поведения.

## Связь с общей готовностью

Проверить влияние пересмотра на прямых и обратных потребителей этой спецификации. Изменённые условия и оставшиеся вопросы внести в единый реестр. Статусы спецификации, реализации, проверки и выпуска вести отдельно.
