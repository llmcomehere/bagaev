# T12 Специфицировать операции агента и продолжение

Цель: **G06**. Волна: **W5**. Профиль: **V1**.

**Статус и основания готовности** ведутся в [оценках](../../docs/verification.md) и [прогрессе](../../docs/verification.md), исполнимость — в [EXEC-1](../exec-progress.json); наличие этой карточки не означает выполнение.

## Результат

Дать разным моделям единый проверяемый протокол работы с проектом без зависимости от истории чата.

Контекст: [основа языка](../../spec/foundation.md), [цели](../GOALS.md), [дорожная карта](../PLAN.md).

## Входы и зависимости

Предшественники: [T10](T10-change-acceptance.md); [T11](T11-intent-context.md)

- Контракт изменения T10
- ContextPack T11
- Рабочий протокол и состояния jobs/receipts

Рабочий материал: [04-agent-tooling.md](../../spec/architecture/04-agent-tooling.md). Его нужно завершить и проверить, а не считать готовой нормативной спецификацией.

## Решения, которые необходимо закрыть

- Транспорт, версии схем, статусы и коды ошибок
- WorkState и журнал, пределы хранения ключей
- Права операций и безопасные правила повторов

## Порядок работы

1. Задать схемы request/response для каждой операции inspect/search/expand/begin/apply/impact/verify/accept/continue.
2. Отделить command success, job status, change status и effect outcome.
3. Определить idempotency key scope и канонический hash параметров.
4. Специфицировать resume с guards, актуальностью оснований и без воспроизведения эффектов.
5. Проверить потерю ответа, смену исполнителя, отзыв доступа, параллельную правку и повреждение checkpoint.

## Критерии приёмки

| ID | Проверяемое условие |
| --- | --- |
| T12-C01 | Повтор локальной записи с тем же ключом не выполняется заново. |
| T12-C02 | Другие параметры под тем же ключом дают конфликт. |
| T12-C03 | Unknown outcome внешнего действия не превращается в автоматический retry. |
| T12-C04 | Смена модели не изменяет правила и открытые обязательства. |
| T12-C05 | Истечение хранения ключа имеет определённый исход, а не скрыто теряет гарантию. |

## Обязательные отрицательные случаи

- После потери ответа операция выполняется повторно.
- Старый checkpoint обходится без проверки новых предпосылок.

## Основание завершения

Для каждого критерия сохранить точные версии предметов, входы, метод, ожидаемый и фактический результат. Лог выполненной проверки отличается от проекта проверки. Ревью должно проверить согласованность с зависимыми спецификациями; нулевое число замечаний без просмотра не является свидетельством.

Задача получает `done`, когда её выходы существуют, все обязательные критерии подтверждены допустимыми evidence и результаты приняты по действующим правилам проекта. Подготовка текста даёт `review`, а не автоматически `done`. Для изменения внешних систем нужны соответствующие полномочия; карточка не предоставляет их.

## Если условие не выполнено

Продолжать из журнала с явным unresolved; непроверяемый checkpoint не восстанавливать пересказом.

## Связь с общей готовностью

Проверить влияние пересмотра на прямых и обратных потребителей этой спецификации. Изменённые условия и оставшиеся вопросы внести в единый реестр. Статусы спецификации, реализации, проверки и выпуска вести отдельно.
