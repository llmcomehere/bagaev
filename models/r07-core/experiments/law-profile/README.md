# R03: проверяемые локальные законы

Этот каталог содержит исследовательский слой над замороженным исполнимым профилем R02. Он добавляет четыре локальных закона `size`/`to_set`, журнал преобразований и небольшой checker этого журнала. Исходная программа продолжает исполняться как раньше; преобразованная форма используется для вывода use и для отдельного ограниченного основания эквивалентности. Это не компилятор bagaev и не машинное доказательство общей корректности языка.

Точные типы записей, API и диагностики находятся в [API.md](./API.md). Интерпретатор R02 загружается из соседнего каталога с проверкой закреплённого SHA256; его исходники и прежние результаты не изменяются.

## Воспроизведение

Из корня пакета, Python 3.10 или новее:

```bash
python -B experiments/law-profile/verify.py --output results/law-profile/report.json
```

Независимый verifier и корпус ведутся отдельно от `laws.py`. Фактические числа и source hashes принадлежат его отчёту. Наличие команды не является заявлением об успешном запуске.

## Что улучшает этот профиль

В R02 `size(read ordered_members)` консервативно сохранял зависимость от порядка. R03 знает точный закон: при закреплённой семантике размер упорядоченной последовательности равен наблюдению `count`, с тем же исходом ошибки чтения. После проверки этого преобразования use можно получить из `read count`.

Аналогично `to_set(read ordered_members)` соответствует `read member_set`. Размер множества соответствует count только благодаря уникальности ID в данном ресурсе. Четвёртый закон удаляет повторное преобразование уже полученного множества в множество.

Это конечный каталог точных шаблонов. Он не разрешает заменять `head` наблюдением множества, удалять initializer, условие или эффект. Например, `let unused = head(read ordered_members) in const 'ok'` по-прежнему зависит от ошибки `EMPTY_HEAD` и порядка; неиспользование значения не даёт разрешения удалить его вычисление.

## Пример обычного refined use

```python
from laws import Consumer, ResourceState, assess, normalize, refined_use

program = {
    "op": "size",
    "value": {"op": "to_set", "value": {"op": "read", "view": "ordered_members"}}
}
consumer = Consumer("article.count", program)
proof = normalize(consumer)
checked = refined_use(consumer, proof)

assert [step.rule_id for step in proof.steps] == [
    "TO_SET_ORDERED_TO_MEMBER_SET", "SIZE_MEMBER_SET_TO_COUNT"
]
assert checked.summary.required_observations == {"count", "read_status"}
assert assess(consumer, consumer,
              ResourceState(("A", "B")), ResourceState(("B", "A"))).decision == "EXCLUDED"
```

Пример показывает форму API; он не заменяет независимый отчёт. Нормализация работает снизу вверх. Каждый закон уменьшает число AST-узлов; путь следующего шага относится к уже обновлённому дереву. Истинность шага проверяется повторно: stamp или присланный узкий use не принимаются как доказательство.

## Checker и предпосылки

Перед преобразованием проверяются исходный AST и точная config. Derivation закрепляет stable ID, original revision, конфигурацию, provider, требования, версии профиля и каталога, хеши семантического движка и law kernel. Checker сам разрешает путь только через допустимые AST-child поля, сравнивает текущий redex, применяет фиксированное правило и проверяет весь конечный AST. Настоящий int-индекс отличается от bool; JSON-сравнение дерева также отличает `true` от `1`.

Условия законов следуют из закреплённой модели: неизменяемый ресурс, чистые чтения, согласованные ошибки представлений, уникальность ID там, где она требуется. Присланные флаги `unique=true` или `pure=true` не имеют доверительной силы. Поддержан только встроенный provider `provider/v1`; иной provider не получает refinement и сохраняет пересмотр либо unknown.

Генератор доводит дерево до насыщенной формы своего малого каталога. Checker также допускает корректную частичную или нулевую цепочку; такой результат может быть менее точным. Признак `saturated` вычисляется заново. Под `opaque` и `unknown` checker не спускается; известные преобразования в соседней ветви не устраняют неполноту самой программы.

## Два разных assessment API

Обычный `assess` сравнивает **неизменный original consumer**. Даже если исходная правка могла бы иметь ту же преобразованную форму, смена original AST остаётся `RECHECK`. При прежнем AST replay-проверенный refined use может безопаснее ограничить пересмотр конкретного перехода данных.

Отдельный `derive_equivalence` проверяет две исходные программы одного stable ID. Каждая самостоятельно проходит проверку цепочки; при одинаковых config/provider/requirements и буквально общей проверенной форме получается сертификат для выбранного полного исхода OBS. Разные формы дают `UNPROVED`, а не утверждение неэквивалентности. Для этого достаточного основания не требуется объявлять всю систему переписывания конфлюэнтной.

`assess_equivalent_edit` явно выбирает дополнительное основание и может исключить новое влияние ограниченной правки кода вместе с конкретным переходом ресурса. Обе original revisions остаются в сертификате. Равенство общих форм не сливает source identity и не заменяет принятие изменения.

При смене требований состояния `OPEN` и `REMOVAL_OPEN` сохраняются. Даже прежнее неизменное требование остаётся `UNCHANGED_UNASSESSED`: эти API не устанавливают base satisfaction. Ошибочный, устаревший или поддельный сертификат не становится основанием EXCLUDED; он получает diagnostic либо консервативный пересмотр без его использования.

## Граница результата

Законы относятся к статусу, значению/ошибке, упорядоченной закрытой trace и полноте исполнения R02. Стоимость CPU, allocation и бюджет выполнения не входят в это наблюдение. Runtime исполняет original AST; ускорение программы или общей работы не заявляется. Требования, наблюдающие source-структуру либо дополнительные каналы, не закрываются таким сертификатом.

Независимый oracle исполняет исходные и полученные формы; конечные проверки ищут контрпримеры, а намеренно плохие политики показывают различающую силу корпуса. Успешный конечный прогон не доказывает все допустимые программы и состояния. `bagaev_execution=false`, `hypothesis_tested=false`; исполняется только исследовательский AST. T08/T09 и сквозной опыт T15 остаются незавершёнными. Проектный граф и incremental извлечение R02 в этом слое не переписаны.
