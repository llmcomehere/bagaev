# Конечная проверочная модель связей

Это самостоятельная модель на Python standard library. Она **не читает, не компилирует и не исполняет bagaev**. Типизированные факты, ревизии и основания полноты задаются вручную в конечных фикстурах. Проверяются выбранные инженерные правила, а не центральная гипотеза продукта.

## Запуск

Из корня нового пакета:

```bash
python -B experiments/link-model/verify.py --output results/link-model/report.json
```

Нужен Python 3.10 или новее. Зависимостей вне standard library нет. Скрипт записывает фактический JSON-отчёт и возвращает ненулевой код, если ручной случай, конечный перебор или проверка различающей мутации не прошли. Показатели выполненного запуска берутся из отчёта; README не является протоколом выполнения.

## Что именно моделируется

`Graph` неизменяем и содержит поколение, узлы с устойчивыми ID, конечные типизированные `Fact`, compile-config, признак закрепления конфигурации, версию условного извлекателя и полноту объявленной области. Узлы и факты — **ручной вход**, а не результат настоящего извлечения из исходников. Синтаксис фактов не является новым синтаксисом bagaev.

Прямой и обратный `Index` построены из одного графа. Запрос отвергает смешанные поколения (`GENERATION_MISMATCH`) и неверное содержание индекса. Проверяются сами `rows` и `unknown_fact_ids` обеих сторон, а не только метаданные: модель заново строит каноническое содержание и сравнивает его с индексами. Это затратная проверка целостности, а не демонстрация ускорения; производственный способ аутентификации содержимого потребует отдельного правила. Два исторических графа разрешено читать одновременно, если каждый использует собственную согласованную пару индексов.

`ReverseCache` хранит результат `may_consumers` вместе с отпечатком всех членов объявленной области, их фактов, конфигурации, покрытия, версии извлекателя и registry. Отпечаток включает непотребителей и неактивные факты; он существует и для пустого ответа. Добавление или изменение потенциального потребителя делает старую запись неприменимой. Одноразовый iterable области нормализуется до первого чтения и затем используется повторно. В этой модели отпечаток вычисляется просмотром конечной области: доказательства производительности такого способа нет.

`Guard` имеет три поддерживаемых вида. `always` активен; `compile` вычисляется только по точной закреплённой конфигурации; `runtime` даёт `UNKNOWN`, даже если однажды наблюдалось `false`. Значения конфигурации, guards и признаков полноты требуют настоящего типа `bool`; строки и числа отвергаются. Неизвестный guard сохраняет may-edge. Неизвестная динамическая цель представлена `target=None`: она участвует в потенциальном ответе и делает его неполным. Неполное покрытие области также запрещает считать пустой ответ полным.

## Синтетическая семантика аспектов

Registry `synthetic-authorship-v1` задаёт независимые атомарные наблюдаемые координаты `values`, `order`, `cardinality`, `errors`, `effects`. Это **предположение конечной модели**, а не доказанная декомпозиция поведения реального языка. Применимость операции пересечения опирается на общий registry.

`FacetClaim` содержит объявленное множество и необязательный `Certificate`. Certificate — **доверенная синтетическая предпосылка фикстуры** с полным верхним ограничением и ID registry. Подлинность такого основания, связь с настоящим кодом и полнота наблюдений здесь не устанавливаются. В полном ТЗ потребуются сертифицированные проекции, точные версии и закрытый охват результатов, ошибок, эффектов, guards и прочих значимых наблюдений.

Если объявленное множество не покрывает полное множество из синтетического certificate, модель выдаёт `UNDERDECLARED_FACETS`. Нет полного основания либо registry различаются — используется `TOP`, представленный `None`. Нельзя считать недекларированный аспект отсутствующим.

`impact(base, candidate, target, delta)` проходит по объединению старых и новых фактов. Остановка допускается при двух полных совместимых верхних ограничениях и пустом пересечении. При пересечении потребитель остаётся `IN_SCOPE`; при неизвестном ограничении — `UNKNOWN`. Verified compile-config `false` исключает ветку только в своей зафиксированной области. При дальнейшем переходе через затронутого потребителя используется `TOP`: доказанный перенос изменения его выходных аспектов в этой версии модели отсутствует. Обход конечен благодаря учёту посещённых узлов и состояний аспектов.

`IN_SCOPE` означает необходимость пересмотра, а не доказанный дефект поведения. `complete_in_declared_scope` означает завершённость этого ограниченного анализа, а не готовность программы к приёмке. Модель не запускает реальные проверки бизнес-контрактов.

Переименование сохраняет идентичность только в профиле **без наблюдения или отражения служебных имён**. Изменение внешнего API, пользовательского текста или reflective lookup этим примером не покрыто.

## Как проверяется модель

`verify.py` содержит отдельные ручные ожидаемые исходы для положительных и отрицательных случаев. Среди них: потребитель после пустого результата; новый потребитель среди прежних непотребителей; снятое ребро; изменение compile-config при прежних исходных фактах; runtime-false; unknown guard/target/scope; неполные аспекты; несовпадающий registry; смешанные поколения; повторное использование неизменного извлечения; смена извлекателя; переименование; перенос TOP через вызов.

Дополнительно перебирается явно заданная конечная область графов, все упорядоченные переходы между ними и все сочетания выбранных множеств аспектов с признаками полноты. Отчёт содержит фактические размеры. Сравнение кэшированного ответа с полным пересчётом проверяет **согласованность кэша**. Ручные ожидаемые ответы нужны отдельно, поскольку две реализации могут иметь общую ошибку.

Два специально неправильных варианта обязаны отличиться от правильного ответа:

- `ReturnedItemsOnlyCache` следит только за уже возвращёнными объектами и пропускает нового потребителя после пустого результата.
- `unsafe_declared_facets=True` принимает декларацию за полное основание и ложно исключает потребителя при скрытом изменении `values`.

`HeadStore` проверяет два последовательных порядка CAS для конкурирующих ревизий от одной базы. Кандидаты здесь предполагаются уже проверенными: модель обновляет только указатель и не реализует политику допустимости приёмки. Это не тест потоковой гонки, атомарности реальной СУБД или восстановления после сбоя питания.

Отчёт включает хеши трёх исходных файлов, команду воспроизведения, ручные случаи, конечные проверки и результаты намеренных мутаций. `bagaev_execution=false`, `hypothesis_tested=false`, T08/T09 остаются `NOT_CLOSED`. Успех не доказывает понимание намерения, полноту произвольного проекта, истинность certificates, пригодность будущего компилятора или преимущество bagaev по цене.
