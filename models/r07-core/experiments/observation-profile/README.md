# R02: исполнимый профиль наблюдений

Здесь находится самостоятельная модель на Python standard library. Она действительно исполняет небольшой типизированный JSON AST и автоматически извлекает use из его подтермов. Это **исследовательский AST**, не реализация синтаксиса, компилятора или runtime bagaev. Подробный контракт входов, типов, ошибок и функций находится в [API.md](./API.md).

## Воспроизведение

Из корня пакета, Python 3.10 или новее:

```bash
python -B experiments/observation-profile/verify.py --output results/observation-profile/report.json
```

Проверяющий скрипт и независимый интерпретатор находятся рядом с движком; корпус сериализуется в `fixtures/programs.json`. Машинный результат записывается в `results/observation-profile/report.json`. Наличие команды в README не заменяет статус и source hashes фактического отчёта.

## Зачем нужен этот шаг

R01 проверял инженерные правила над вручную заданными фактами и синтетическими основаниями полноты. R02 делает следующий ограниченный шаг: конечные программы имеют определённое поведение, а зависимости выводятся из этих программ. Объявить произвольный список зависимостей в обычном AST нельзя.

Ресурс Authorship хранит упорядоченные уникальные ID авторов. Пустой список допустим, чтобы проверять ошибку `head`; отсутствующий ресурс и ошибка провайдера тоже представлены явно. Авторство здесь означает атрибуцию. Правила прав на редактирование не моделируются и не выводятся из этого отношения.

Порядок, множество и количество авторов **не объявлены независимыми**. Они вычисляются функциями над одним состоянием. Перестановка `[A, B] → [B, A]` меняет только упорядоченное наблюдение; замена `[A] → [B]` меняет порядок и множество, сохраняя количество; переход к ошибке чтения меняет доступный исход даже при прежних авторах.

`exact_delta` знает только конкретную пару таких конечных состояний. Он не доказывает ничего о произвольной смене схемы, кода провайдера или будущих данных.

## Пример использования

Из каталога с `engine.py`:

```python
from engine import Consumer, ResourceState, assess, execute, infer_use

program = {"op": "read", "view": "count"}
consumer = Consumer("article.counter", program)
before = ResourceState(("A", "B"))
after = ResourceState(("B", "A"))

assert execute(program, before).value == 2
assert infer_use(program).required_observations == {"count", "read_status"}
assert assess(consumer, consumer, before, after).decision == "EXCLUDED"
```

Это пример API, а не отчёт независимого корпуса. Для `read ordered_members` та же перестановка потребует `RECHECK`. Для `size(read ordered_members)` текущий анализ также сохранит зависимость от порядка: оптимизирующее сужение пока не реализовано.

## Что означает исключение

`EXCLUDED` допускается только при одинаковых AST, всей compile-config, revision провайдера и revisions требований, полном автоматическом use и равенстве всех требуемых наблюдений. Смена тела программы даёт `RECHECK` даже при пустом delta данных. Неизвестный внешний код или скрытое чтение дают `UNKNOWN`, то есть TOP.

Вывод относится к нормальному значению, известной ошибке и закрытой последовательности `emit`. Он не означает, что прежний результат был правильным. Два запуска могут одинаково завершиться ошибкой; новые требования всё равно остаются `OPEN`. Прежние требования помечены `UNCHANGED_UNASSESSED`, поскольку проверки их satisfaction в этом профиле нет. Удалённые требования получают `REMOVAL_OPEN`: предложенная отмена тоже требует отдельного пересмотра.

Конфигурация закреплена как mapping bool-значений и входит в основания решения целиком. Провайдер закреплён opaque revision; модель не загружает его новый код. Любая смена этой revision принудительно требует пересмотра. Схемы за пределами типа `ResourceState` не поддержаны и требуют другого профиля, а не переноса текущего результата delta.

## Почему анализ консервативен

Статический use объединяет условие и обе runtime-ветви `if`. Он сохраняет все initializer в `let`, даже если переменная не используется. Например, `let unused = head(read ordered_members) in const 'ok'` зависит от чтения и пустоты списка: ошибка initializer прерывает выполнение. Аналогично сохраняются эффекты и ошибки выражений, чьи нормальные значения позже отбрасываются.

В закрытой части AST можно рассуждать по структуре выражения: чтение детерминировано своим тотальным наблюдением; чистый builtin — значениями детей; составное выражение — вычислениями детей в определённом порядке. Для `var` нужен инвариант равенства значений в лексическом окружении: eager `let` получает одинаковые initializer и связывает одинаковые значения; отдельный use самого `var` поэтому пуст. Равные необходимые наблюдения при одинаковой программе и предпосылках тогда сохраняют результат, ошибку и trace. Этот текст — **аргумент по структуре модели, не machine-checked proof**. Конечный корпус отдельно проверяет случаи и ищет контрпримеры.

`opaque` не подставляет выдуманное значение и не обращается к внешней среде. Исполнение возвращает явный unknown и известный префикс trace; use помечается неполным. Даже когда непрозрачная ветвь не сработала в одном запуске, консервативный анализ не считает всю программу полной.

## Автоматическое извлечение проекта

`extract_project` обходит весь переданный registry и строит граф из автоматически выведенных наблюдений. В stamp входят все потребители, включая текущих непотребителей. Поэтому новый потребитель после пустого результата, смена тела прежнего непотребителя и удалённое ребро не могут быть скрыты неизменностью ранее найденных файлов.

`incremental_extract` моделирует повторное использование summary при точном равенстве входного stamp и каждый раз строит stamp всего нового manifest. Для целостности прежний граф проверяется полным повторным извлечением. Здесь **нет утверждения об ускорении**; это проверяемая исходная реализация правил извлечения и обновления. `graph_delta` хранит объединение старых и новых рёбер; `assess_project` рассматривает объединение ID обеих ревизий.

Registry считается замкнутым входом модели. Его полнота относительно реального репозитория, плагинов или внешней инфраструктуры не установлена. Неизвестные цели внутри данного AST обозначаются явно и запрещают полный отрицательный вывод.

## Независимая проверка и границы

`verify.py`, независимый oracle и корпус написаны отдельно от `engine.py`. Обычный assessment не принимает ручные summaries. Для различающих мутаций предусмотрен специальный `assess_with_test_analyzer`, который маркирует результат `TEST_ONLY_UNTRUSTED`; такое внедрение не является разрешённым способом получить обычное свидетельство полноты.

Фактические числа запусков и source hashes принадлежат отчёту verifier. У исследовательского результата должны оставаться признаки `bagaev_execution=false`, `research_ast_execution=true`, `hypothesis_tested=false`. Сравнение полного и повторно использующего данные извлечения проверяет согласованность механизмов, а не преимущество bagaev по стоимости или качество распознавания намерений.

Этот профиль не закрывает T08/T09. Он не поддерживает произвольные пользовательские функции, циклы, рекурсию, reflection имён, внешние host effects, неограниченное разрешение динамических целей, многопроцессную конкуренцию и миграции схем. Int-литералы ограничены signed 64-bit, строки — Unicode scalar values; выход за эти границы имеет явный `ProfileError`. Неизвестная операция получает явный diagnostic; разрешённый непрозрачный узел получает unknown. Python-ошибки типов входной программы не превращаются в успешные результаты.
