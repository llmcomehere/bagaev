# AUTH-TX-0.1 · Авторство через durable state и локальную проекцию

Малая исполнимая модель исследует конкретный переход: редактор заменяет упорядоченный список авторов статьи, изменение попадает в retained outbox, обработчик обновляет индекс каждого соавтора, затем producer сохраняет отдельный ACK. Модель работает с immutable Python records и абстрактной атомарной публикацией целого состояния. Она не подключается к СУБД и не исполняет bagaev.

Точный контракт, records, порядок проверок и preimages хешей находятся в [API.md](API.md); исполняемая машина — в [engine.py](engine.py). Independent verifier и oracle принадлежат отдельной проверочной части пакета. Их результат следует читать вместе с границами модели ниже.

## Что именно зафиксировано

Начальная область — уже подготовленный D1 / ArticleV2: существующие PersonId, непустые ordered unique authors и отдельные editor_ids. Авторство означает атрибуцию; право редактировать задаёт ACL. Порядок авторов значим, поэтому перестановка создаёт новую article_revision и полный event даже при неизменном membership set.

`ReplaceAuthorship` использует business CAS `expected_article_version`. У всего store имеется отдельная `state_version`: её увеличивают новые command receipts, обработка событий и ACK. NOOP сохраняет receipt и увеличивает только state_version. Этот receipt нужен, чтобы повтор после потерянного ответа возвращал первоначальный результат даже после дальнейшей правки статьи.

Идемпотентность закрепляет весь request и `(store_id, actor_id, command_id)`. Exact replay проверяется после формы и текущей ACL, но до stale article/store guards. Другой payload под сохранённым ключом получает конфликт. Неуспешная новая команда не сохраняет receipt и не резервирует ключ. Per-attempt `expected_state_version` не входит в request binding; реальный adapter должен проверять прочитанную StateVersion атомарно с записью.

Event содержит полный новый snapshot авторов. Обработчик принимает его только при точном совпадении с retained local outbox. Более новая article_revision заменяет проекцию и весь membership статьи; старая получает SUPERSEDED без отката. Индекс, проекция, inbox и projection receipt фиксируются одной абстрактной boundary. Outbox ACK выполняется отдельно и ссылается на сохранённый projection receipt. Событие остаётся pending до ACK, включая промежуток после успешной обработки и потери ответа.

Delivery v3→v2 и v2→v3 сходятся к одной последней проекции; результаты исторических receipts могут различаться. Это свойство full snapshots и одного закреплённого handler, а не универсальное правило для delta events.

## Commit и знание caller разделены

Каждая новая запись поддерживает три cuts: `none`, `before_commit`, `after_commit_before_reply`. Первый возвращает RESULT. Два последних возвращают UNKNOWN без receipt и наблюдаемой версии, хотя actual durable state различается. Поле `Transition.actual_commit` доступно исследовательскому harness; удалённый caller такого знания не получает.

Recovery читает сохранённый receipt, ничего не повторяя. Отсутствие обозначено ABSENT_AT_READ; недоступное чтение — UNKNOWN. Receipt содержит исходную committed_state_version, а текущая прочитанная версия находится отдельно в Observation. Поэтому восстановленный прежний успех не выдаётся за подтверждение текущего состояния статьи.

Cuts действуют только на новую commit boundary. Replay и явный отказ не создают новой записи. Ни один промежуточный частично обновлённый store обычный API не публикует: сначала строится и проверяется полный immutable candidate, затем выбирается old/new snapshot.

## Проверка и воспроизведение

Из корня R05-пакета:

```sh
python -B experiments/authorship-transition/verify.py --output results/authorship-transition/report.json
```

Отчёт связывает результаты с точными исходными файлами и authored корпусом. Independent oracle описывает whole-state переходы собственными JSON-словарями и hashing; он не импортирует функции переходов engine. Сравниваются полный durable state, observation и actual_commit, включая каждый cut, возврат исходных receipts, ошибки, повторную доставку и порядок событий. Различающие неправильные варианты проверяют разрыв producer atomicity, разрыв projection/inbox atomicity и принятие другого payload по одному ключу.

Конечный набор сценариев не является статистическим доказательством гипотезы языка. Результаты actual прогонов и число проверок берутся только из созданного report; эта инструкция не сообщает о ещё не выполненных проверках.

## Явные границы

- Это последовательная finite machine: durable commit — предпосылка абстрактного перехода. Не проверяются реальная транзакционная изоляция, fsync, сбои диска, сетевой broker или конкурентное исполнение adapter.
- `validate_state` проверяет типизированные формы, ссылки, exact bindings и согласованность materialized index. Оно не доказывает подлинность произвольной импортированной истории. Источник delivery — доверенный локальный outbox.
- People и ACL не изменяются операциями этой модели. Отдельный заранее подготовленный валидный snapshot с новой ACL может использоваться для проверки запрета replay после revocation; это не реализованная ACL-команда.
- Все receipts/outbox/inbox/ACK сохраняются. Есть предел 512 записей каждого журнала; CAPACITY_LIMIT возникает до публикации нового состояния, без GC и удаления старых ключей. Retention/TTL реального сервиса требуют отдельного решения.
- Поддержаны до 32 people/articles и до 32 authors/editors; source IDs ограничены 256 Unicode scalar values, derived event IDs — 512, версии — положительным signed64. Bool не является версией. Неизвестные значения и превышения профиля диагностируются явно.
- Индекс в этой небольшой модели пересчитывается целиком из проекций. Производительность и преимущество incremental processing не измеряются.
- Миграция D0→D1, активация кода/схемы, UI/byline/export и пользовательский A/B/C опыт здесь не исполняются. Старые illustrative fixtures не превращаются в actual results. T06, T07 и T15 целиком не закрываются.

В отчёте обязательны границы: `bagaev_execution=false`, `abstract_durable_model=true`, `real_storage_tested=false`, `hypothesis_tested=false`. Наличие локальных receipts не означает exactly-once внешнего действия или приёмку нового требования.
