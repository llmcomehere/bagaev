# P0 metadata catalog contract, revision 1

Status: **frozen for implementation** as `p0-contract/1.0.0`. The machine-readable
oracle is [p0-cases/1.0.0](p0-cases.json). This contract refines the P0 slice in
the historical version 0.6 [research foundation](foundation.md#first-experiment-p0-metadata-change-and-work-handoff);
it does not replace or rewrite P0-01 through P0-10 there.

The separate file gives simulator work a small context boundary and executable
precision without turning the research foundation into an implementation spec.

P0 is a standalone synthetic metadata catalog and a CPU-only failure simulator.
It uses no photographs, external service, model run, new language, paid fallback,
or claim about performance or adoption. Model choices, repetitions, comparative
thresholds, budgets, and the full comparison passport remain later work.

Normative terms `MUST`, `MUST NOT`, `SHOULD`, and `MAY` apply only to this frozen
revision. The prose owns semantics and ordering. The JSON oracle owns exact
vectors and expected observations; simulator output never defines expectation.

## Frozen types and state

Identifiers are non-empty ASCII strings matching `[a-z][a-z0-9-]{0,63}`.
Revisions and epochs are unsigned 64-bit integers. A tag matches
`[a-z][a-z0-9-]{0,15}` and is compared byte-for-byte. A `TagSet` is encoded as a
strictly increasing JSON array of unique strings; the tag grammar is checked by
the mutation contract. All arithmetic MUST refuse on overflow.

The authoritative receiver stores one state value:

```text
ReceiverState = {
  record: {revision: Revision, tags: TagSet},
  task: {
    task_id: Identifier,
    task_revision: Revision,
    behavior_revision: Identifier,
    contract_revision: Identifier
  },
  authority: {epoch: Epoch, assignee: PrincipalId, scope: ScopeSet},
  operation_receipts: Map<(task_id, operation_id), WriteReceipt>,
  transfer_receipts: Map<(task_id, transfer_id), TransferReceipt>,
  retained_candidates: Map<candidate_id, RetainedCandidate>,
  admission_records: Set<AdmissionRecord>
}
```

`ScopeSet` is encoded as a strictly increasing JSON array of unique scope names,
ordered byte-for-byte. A scope name matches `[a-z][a-z0-9:-]{0,63}`.
Reordering or duplicating a name is a
non-canonical set encoding and therefore an `invalid-request`; two well-formed
scope sets are equal exactly when their canonical arrays are equal. The
supported names are `write:catalog`, `read:receipts`, `manage:transfer`,
`candidate:store`, and `candidate:admit`. A canonical but unsupported name is
structurally valid and reaches the transfer support check below. The receiver
also has a current authentication fixture mapping a presented session to one
`PrincipalId` and its current grants. The fixture principals and sessions in
the oracle are synthetic. Authentication means only a successful fixture
lookup; P0 makes no cryptographic, identity-provider, or real-world identity
claim.

The initial protocol state for every case that names `protocol-base` is:

```text
record = (revision 10, tags ["blue", "manual"])
task = ("task-catalog", 7, "catalog-set-1", "write-contract-1")
authority = (epoch 4, assignee "writer-a", scope {"write:catalog"})
operation_receipts = {}
transfer_receipts = {}
retained_candidates = {}
admission_records = {}
```

Current grants are exact, not inherited: `writer-a` and `writer-b` each have
`write:catalog` and `read:receipts`; `coordinator` has `manage:transfer` and
`read:receipts`; `reader` has `read:receipts`; `submitter` has
`candidate:store`; `admitter` has `candidate:admit`; and `outsider` has none.
The session named `anonymous` does not authenticate.

### Commands, intent, and receipts

A write request is an authorization envelope plus a durable semantic intent:

```text
WriteRequest = {
  session, presented_epoch,
  intent: {
    task_id, operation_id,
    task_revision, behavior_revision, contract_revision,
    expected_record_revision,
    mutation: {add: TagSet, remove: TagSet}
  }
}
```

`add` and `remove` MUST be disjoint. The authenticated principal, session, and
presented epoch are authorization context, not semantic intent. This lets a
currently authorized successor retry an exactly saved intent under its current
epoch. Changing any field inside `intent` while retaining the operation ID is
an identifier conflict.

A transfer request has `{session, intent}` where its durable intent is
`{task_id, transfer_id, expected_epoch, recipient, scope}`. The scope is a
`ScopeSet`. Changing any of those intent fields while retaining the transfer ID
is a conflict; the caller session is authorization context.

Before its first send, every sender MUST durably save the complete intent and
ID. Recovery restores that value. A timeout, summary, handoff, or missing reply
MUST NOT cause a fresh ID to be invented for the same intended effect.

A committed `WriteReceipt` contains its key, the complete immutable intent,
and exactly one outcome:

- `effect-committed`, with record revisions before and after and the resulting
  canonical tags; or
- `refusal-committed`, with `revision-conflict` or `contract-refusal` and the
  observed record revision. A contract refusal also carries one deterministic
  detail: `overlapping-change`, `invalid-tag`, `missing-remove`, or
  `revision-overflow`.

A committed `TransferReceipt` contains its key, complete immutable intent, and
the complete prior and resulting authority values. Receipts are values, not
permissions. They MUST NOT be deleted, overwritten, or reinterpreted in P0.
An exact retry returns the stored receipt unchanged. A later task, record, or
authority revision does not alter a historical receipt.

## Receiver algorithms

Malformed JSON, a missing field, a value outside its structural type, or a
non-canonical set encoding is refused as `invalid-request` before the state
machine. It creates no receipt. A syntactically valid tag string that fails the
tag grammar is a contract error at step 9. For a well-formed write, the receiver
performs the following checks in this exact order inside one serializable
operation:

1. authenticate the current session, else `authentication-required`;
2. resolve the current named task, else `task-not-found`;
3. require the authenticated principal to equal the current assignee, else
   `assignee-mismatch`;
4. require `write:catalog` in both the principal's current grants and the
   current authority scope, else `write-scope-required`;
5. compare, in order, task revision, behavior revision, and contract revision,
   returning `task-revision-mismatch`, `behavior-revision-mismatch`, or
   `contract-revision-mismatch` at the first mismatch;
6. require exact equality with the current epoch, else `epoch-mismatch`;
7. look up `(task_id, operation_id)`. An equal intent returns the immutable
   receipt; a different intent returns `operation-id-conflict`;
8. for a new ID, compare the expected record revision. A mismatch atomically
   commits a `revision-conflict` refusal receipt;
9. validate the mutation contract. Overlap between `add` and `remove`, an
   invalid tag, or removal of a tag not present atomically commits a
   `contract-refusal` receipt;
10. otherwise apply removals and additions, increment the record revision once,
    and commit the data and `effect-committed` receipt atomically. An increment
    past the maximum revision instead commits `contract-refusal` with
    `revision-overflow`.

Failures in steps 1-6 do not look up, disclose, create, or occupy an operation
receipt ID. The response is generated only after the transaction decision.
The serialization boundary includes authority, so a transfer cannot commit
between write verification and the write decision.

For a well-formed transfer, the receiver performs this exact order inside one
serializable operation:

1. authenticate the current session, else `authentication-required`;
2. resolve the named task, else `task-not-found`;
3. require the caller's separate current `manage:transfer` grant, else
   `transfer-scope-required`;
4. look up `(task_id, transfer_id)`. An equal intent returns the immutable
   receipt; a different intent returns `transfer-id-conflict`;
5. for a new ID, compare `expected_epoch`, else `epoch-mismatch`;
6. require the recipient to be an authenticated fixture principal and every
   requested scope to be a supported scope currently granted to that recipient,
   else `recipient-or-scope-unsupported`;
7. increment the epoch once, replace assignee and authority scope, and commit
   that state with one transfer receipt atomically. An increment past the
   maximum epoch returns `epoch-overflow` without a receipt.

Transfer refusals create no transfer receipt. Revocation of
`manage:transfer` therefore prevents even duplicate retrieval through the
transfer endpoint because current transfer rights are checked before receipt
lookup. A caller with current `read:receipts` MAY use the status endpoint.

Status lookup authenticates the session, resolves the task, and requires the
current `read:receipts` grant. It returns either the immutable receipt or
`receipt-absent-at-query`. The latter is an observation at that instant: it
does not prove that a delayed request cannot later commit.

### Atomicity, crash, and recovery

The data change and its write receipt have one commit point. The authority
transition and its transfer receipt have one commit point. A crash before a
commit leaves neither half visible. A crash after commit preserves both halves,
even if no response was sent. Recovery loads committed receiver state and
receipts before accepting another command; a sender restores its saved intent
before retrying. Concurrent operations MUST be equivalent to one serial order
and MUST reevaluate all ordered checks against the state at their commit turn.

The old assignee is cut off at the authoritative receiver's transfer commit,
not at a coordinator message or at response delivery. If the write serializes
first, its effect may commit before cutoff. If transfer serializes first, the
old write is refused. A receiver or external path that accepts writes without
the current authentication, assignee, scope, task revisions, and epoch checks
does not provide this guarantee.

## Knowledge states and unsupported actions

These observations are distinct:

- `unknown-outcome`: local knowledge after a timeout or lost response;
- `receipt-absent-at-query`: an authoritative lookup found no receipt then;
- `effect-committed`: an immutable receipt proves the specified effect;
- `refusal-committed`: an immutable receipt proves the specified semantic
  refusal; and
- a current pre-receipt refusal, which proves only that this delivery did not
  pass the current gate.

Unknown outcome MUST NOT be displayed as success, refusal, no effect, or
cancelled. Cancellation is unsupported in revision 1. A cancellation message
receives `unsupported-action`; it neither orders against a write nor establishes
that a write stopped. Supporting cancellation requires a new frozen revision
with its own authorized transition, retry semantics, and terminal outcomes.

## Candidate retention and admission

Candidate handling is separate from receiver permission. A candidate contains
`candidate_id`, `code_revision`, the retained candidate bytes and their SHA-256,
`base_snapshot_revision`, `behavior_revision`, `contract_revision`, and evidence
record IDs. Candidate-supplied evidence text and record IDs are untrusted
metadata. They do not create evidence or authority.

For the bounded oracle fixtures only, `candidate_payload_utf8` and handoff
`content_utf8` are the exact bytes after UTF-8 encoding without a byte-order
mark or normalization. Their SHA-256 values are recomputed from those bytes;
digests use 64 lowercase hexadecimal characters. Symbolic or invented digests
are not admissible fixture evidence.

P0 has one fixed mandatory evidence requirement, not a general evidence-policy
framework. Assertion `behavior-cases-pass` must have result `pass`, trusted
origin `trusted-checker`, tool revision `checker-1`, assumptions exactly
`["synthetic-cpu-only"]`, and an input binding to `p0-cases/1.0.0` and every
frozen `BHV-*` case ID. The receiver's initial admission fixture contains
immutable trusted evidence records. Each record binds that requirement to the
exact candidate SHA-256, code, base, behavior, and contract revisions. Merely
naming or reproducing such a record inside a candidate does not add it to this
trusted store. These records are synthetic state-machine inputs; they do not
claim that a simulator, candidate, or repository check has run.

An authenticated principal with current `candidate:store` may retain the exact
candidate bytes and complete metadata after recomputing the digest; a mismatch
returns `candidate-digest-mismatch`. Retention then looks up `candidate_id`. An
absent ID is bound immutably to that complete record. An exact retry returns the
same successful retention observation without another record. A different
record under the same ID returns `candidate-id-conflict` and preserves the
first record. Retention does not admit or execute it.

An admission request presents the session, `candidate_id`, and the complete
candidate record. Admission requires a separately authenticated principal with
current `candidate:admit`. After those current gates, absence from
`retained_candidates` returns `candidate-not-retained`; a presented record that
differs in any byte or metadata value from the immutable retained record returns
`retained-candidate-mismatch`. Neither result creates an admission record.

The admission decision is one serializable operation over the retained
candidate, current session grants, current selected revisions and digest, the
fixed mandatory requirement, and the trusted evidence store. It checks, in
order: authentication; `candidate:admit`; retained-record presence and exact
binding; selected candidate digest and code revision; current base snapshot,
behavior revision, and contract revision; then the mandatory trusted evidence
record and all of its bindings. The first technical mismatch returns `code-stale`,
`base-stale`, `behavior-stale`, `contract-stale`, or
`evidence-not-applicable`. A missing trusted record or non-`pass` result returns
`mandatory-evidence-unknown`. Current permission and dependencies are
reevaluated at the decision point. On any refusal the candidate remains
retained and unexecuted. A successful decision adds one immutable
`AdmissionRecord` binding the exact retained candidate, digest, code, base,
behavior, contract, mandatory requirement, and trusted evidence record. An
exact repeated successful decision returns the same record. It still does not
execute the candidate.

An old successful response, admission record, receipt, label, delivery tag,
historical evidence, or candidate text grants no current scope and cannot
satisfy a different revision. Admission records remain immutable historical
facts; current applicability is false after any bound selected revision or
digest changes, and a new decision still begins with current permission checks.
P0 does not execute candidate code.

## Selected behavior task: list to set

Only the tag-list-to-set task is selected for this first workload. Preserving a
manual tag during reindexing and changing missing-date sorting remain outside
revision 1.

The predecessor format is:

```text
CatalogListV1 = {
  schema: "catalog-list-1", revision: Revision,
  entries: [{id: Identifier, tags: [Tag, ...]}, ...]
}
```

Entry IDs MUST be unique and strictly increasing. List equality compares tag
arrays element by element, so order and duplicates are observable. The target
format has the same outer structure with schema `catalog-set-1`; every `tags`
value is a canonical `TagSet`. Target equality compares membership; canonical
encoding then fixes presentation order.

`migrate-list-to-set` validates the complete input first. It retains each entry
and tag membership, removes repeated tags, sorts tags by ascending ASCII bytes,
changes the schema, and increments the catalog revision exactly once. Empty
sets are valid. Its refusal reasons are `invalid-schema`, `invalid-entry-id`,
`duplicate-entry-id`, `entry-order`, `invalid-tag`, and `revision-overflow`.
It checks the schema, all entry-identifier grammars, duplicate identifiers,
strict entry order, all tag grammars, and overflow in that order. Every refusal
leaves the entire input unchanged; there is no partial per-entry migration.

For target catalogs, `add-tag` validates the complete catalog, entry ID, and
tag before change. A non-canonical target catalog is invalid. Adding an absent
tag inserts it in canonical order and increments revision once. Adding an
existing member is a successful idempotent no-op and preserves revision.
Its refusal reasons are `invalid-schema`, `invalid-entry-id`,
`duplicate-entry-id`, `entry-order`, `noncanonical-set`, `invalid-tag`,
`entry-not-found`, and `revision-overflow`. Invalid input changes nothing.
It checks the schema, all catalog entry-identifier grammars, duplicate
identifiers, strict entry order, every stored `TagSet`, the requested entry-ID
grammar, requested tag grammar, target existence, and overflow in that order.
An invalid stored tag or non-canonical stored set is `noncanonical-set`;
`invalid-tag` applies to the requested tag. Overflow is checked only when an
absent tag would increment the revision; an existing member remains a
successful no-op even at the maximum revision.

The oracle-only `compare-migrations` action first compares the two predecessor
catalogs using list equality, applies `migrate-list-to-set` independently to
both, and then compares the complete target catalogs using target equality. It
is a composed check, not a third workload operation. Exact positive and
negative vectors are the `BHV-*` entries in the oracle.

### Observable handoff checkpoint

An interrupted implementation is handed off as a checkpoint containing the
task, behavior contract and oracle revisions; base and candidate snapshot
identifiers; every candidate file path and content digest; completed and
remaining work; every frozen `BHV-*` case ID with its observed result or
`not-run`; started external effects and their knowledge states; and unresolved
assumptions. This is the behavior-implementation handoff only; it does not add
a simulator handoff phase. It contains no hidden reasoning prerequisite and
grants no authority.

The frozen `BHV-*` inputs and expectations MUST be evaluated against the exact
predecessor checkpoint bytes and again on the successor candidate. If the
predecessor stopped before this run, `not-run` is honest checkpoint state but
does not satisfy behavior acceptance; the successor first runs the unchanged
checkpoint candidate, before making a change. Earlier inputs, criteria, and
observed results are retained. The successor is accepted only when the before
and after records cover every frozen `BHV-*` positive and negative case, the
after results match the independent oracle, the checkpoint accounts for all
effects, and separate candidate admission succeeds. A handoff label, delivery
tag, model agreement, or a claim of completion is not behavior evidence.

Checkpoint validation and completed-handoff acceptance are distinct. Validation
checks the checkpoint fields and hashes only; it never accepts behavior. A
completed-handoff request pins the contract and oracle versions, every exact
`BHV-*` input, the predecessor checkpoint snapshot, the successor snapshot, and
one before and after result for every frozen case. Each result carries the exact
case input, normalized observed projection, and a status. The checker recomputes
`pass` only when the observation equals the oracle expectation; a different
observation is `fail`, while `not-run` has no observation. A malformed result or
a claimed status that differs from this computation is `handoff-result-invalid`.

The acceptance decision is ordered and deterministic: check the contract,
oracle, and input bindings; validate the checkpoint and both snapshot byte
bindings; validate every result's status against its observation; require
complete before coverage with no `not-run` (honest before failures are retained
and allowed); require complete after coverage with every result matching the
oracle; require all checkpoint effects and assumptions to be accounted for;
then require a separately created, currently applicable `AdmissionRecord` bound
to the exact successor snapshot. Success commits one
immutable `HandoffAcceptanceRecord` containing all of those bindings. Refusal
creates no record. The refusal reasons, in that order, are
`handoff-version-stale`, `handoff-input-stale`, `handoff-snapshot-mismatch`,
`handoff-result-invalid`, `handoff-before-incomplete`, `handoff-after-incomplete`,
`handoff-after-mismatch`, `handoff-checkpoint-unresolved`, and
`handoff-admission-missing`.

The handoff records in the oracle are synthetic state-machine fixture inputs.
They test this decision procedure; they do not claim that a candidate, behavior
check, simulator, or model run actually occurred, and a submitted boolean or
status is never evidence without the bound observation and independent
comparison above.

## Acceptance and progress boundary

The oracle maps every historical P0-01 through P0-10 and adds exact cases for
ordering, duplicate and concurrent transfers, lost replies, revocation,
receipt immutability, crashes, stale admission evidence, behavior semantics,
and a nonresponsive handler. A conforming simulator MUST match all normative
cases. `P0-10` is a negative receiver counterexample: recognizing
`guarantee-failure` is the expected oracle result; accepting that receiver as
conforming fails the suite.

Finite traces check safety and specified observations. They do not prove
finite-trace liveness. Conditional progress assumes available durable storage,
terminating local checks, current rights and revisions stable for the attempt,
and fair repeated delivery: after any finite point, a continuing permitted
request retransmission eventually delivers another request, and continuing
response transmission eventually delivers another response. For every
delivered valid request, the handler MUST generate a response describing the
committed outcome, absence observation, or refusal. A handler that remains
silent after delivery violates this system obligation. Permanent partition,
stopped retries, unavailable storage, continuously changing rights or
revisions, and nonterminating mandatory checks carry no completion promise.

Simulation establishes only conformance of the state model. It does not prove
atomicity of a real store, enforcement by an external receiver, model quality,
economic benefit, or the complete comparison passport.

## Defect and revision procedure

Every run binds the contract version, oracle version, and exact input bytes.
If a scenario defect or requirement change is found, stop the affected run and
retain its inputs, criteria, observations, and result under the old revision.
Do not edit or reinterpret that record. Propose a new explicitly versioned
contract and oracle, identify the defective clause and affected cases, and
obtain independent review of the new bytes before a new run. Prior results are
never retrofitted to the new criteria. An editorial change that cannot alter
parsing or expectation still produces new file bytes and must be identified;
any semantic change requires a new contract and oracle revision.
