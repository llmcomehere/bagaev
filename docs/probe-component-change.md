# Source-bound component change in the connected simulation

The [source component](probe-component-source.md) declares its types and frame.
This next non-normative composition makes candidate admission depend on five
explicit receiving obligations and applicable retained observations. It does not
add a production admission service, authentication system or new evaluator.

## The receiver owns the complete requirement set

The existing catalogue fixture requires types-and-imports, manual-tags-preserved,
actual-entry-consumer, operation-recovery and old-run-binding. A candidate cannot
replace this denominator with an easier pure test suite. The receiving graph pins
base/candidate component, candidate core, receiver policy, profile and all five
named obligations. Each has its own witness and claim dimensions.

The unchanged [finite obligation matcher](probe-evidence-obligations.md) supports
two requirements per call. A fixed adapter evaluates independent groups of two,
two and one after validating the entire evidence set. It retains conflict before
missing-evidence precedence across groups. No helper enum or bounds are widened.
The finite A/B positions belong to each group; exact source identities remain in
the outer binding. A selected assertion is not a count of all its inner calls.

A receipt must match its own named obligation, source/core, policy, profile and
assertion set. It cannot satisfy a different obligation merely because both are
processed in one group. A review control demonstrated this error in an earlier
private adapter: swapped obligation labels still yielded acceptance. The corrected
adapter binds all six claim dimensions to the named requirement before grouping.
The original eleven decisions and that additional frozen control pass unchanged.

Bytes-only evidence does not satisfy runtime requirements. Duplicate positives
cannot replace a missing consumer. An applicable negative with selected zero
still conflicts with a positive. Unrelated negatives do not veto. Malformed late
records cannot be hidden behind an earlier accepted group.

## Reuse exact observations without pretending to rerun them

The compact synthetic qualification bundle retains the earlier component run's
actual input/output strings, source-check wires, trace projections and hashes.
The adapter checks all retained bytes, producer-source bindings and the original
literal pure/trace expectations. It records the original execution timestamp.
This is prior evidence reuse. New execution concerns applicability matching and
the connected application trace, not another component qualification or benchmark.

The source/policy checker supplies the static ground. Four candidate-S2 pure
values and the actual S2 consumer call provide their finite runtime grounds.
WC17 supplies the lost-response, replay and old-run observations. The prior
manual corruption control exercised the common frame enforcer with S1; it is not
relabeled as a newly executed S2 mutant or a universal preservation proof.

These records come from an explicitly trusted owned qualification path. Hashes
and successful parsing cannot authenticate an arbitrary imported producer or
prove its claims true. Even a fully coherent bundle is not production execution
authority. Complete means complete for these five bounded fixture assertions,
not all possible consumers or inputs. The bundle contains synthetic public data.

## Final admission and continuation

The new connected receiver uses the actual five-obligation decision rather than
treating a complete-evidence label as a pass. Old event labels remain only as
positive/missing fixture selectors. Current simulated authority and expected base
are separate conditions. The live head is read again immediately before changing
the new-run default. Admission leaves live state, ledger and old run pins unchanged.

All seventeen existing world/receipt projections remain the independent oracle.
S1/A commits R8 and loses its response; S2/B commits R9; old A replay retrieves R8
without another call or write. A separate controlled serial interleaving changes
the head after evidence checking and requires stale admission. This is not a real
multi-process race, durable recovery or demonstrated production access control.

## Reproduction under a separately approved bounded profile

Use the reviewed component reader and generic typed-record/10 reference from the
component example. Build the existing evidence_reference_harness.rs.in against
the same reviewed backend to obtain the /8 matcher. Retain executable hashes
before invoking them. No downloads, native kernel or workflow changes are needed.

```
python tests/probes/component_change.py --matcher /absolute/matcher --matcher-sha256 RETAINED_MATCHER_SHA --output /absolute/new-decisions
python tests/probes/component_change_cycle.py --matcher /absolute/matcher --matcher-sha256 RETAINED_MATCHER_SHA --reader /absolute/component-reader --reader-sha256 RETAINED_READER_SHA --reference /absolute/record-reference --reference-sha256 RETAINED_REFERENCE_SHA --output /absolute/new-connected-run
```

New output directories and owner-controlled executables are required. Input and
source manifests are checked. The reference matcher is invoked serially. Static
CI validates documentation; it does not reproduce these runtime observations.
Foundation, L2/Store/P0 and production acceptance remain unchanged.
