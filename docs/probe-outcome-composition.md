# Typed outcome changes and pinned continuations

This finite experimental profile connects readable `component-form/2`, detached
`component-edit/2`, actual source/policy checks, five-obligation applicability,
source-pinned runs and `component-context/2`. The original /1 entry points remain
explicitly separate. Nothing here establishes production authority or durability.

## What a compatible draft means

An edit may add a helper and replace function bodies, while preserving the component
interface, nominal records/variants and existing function signatures. It cannot
remove a function. Exact base/target identities and an independently supplied
candidate mapping are checked. Its result is `component-draft/2` with
`execution_admission: false`.

Compatibility is not business refinement. A well-typed change from `quantity < 0`
to `quantity < 1` still produces a compatible draft, but wrongly declines zero.
The unchanged independent zero-value expectation refutes that candidate.

## Qualification and admission are separate phases

The isolated qualifier explicitly provisions both source versions. It checks five
pure cases, source/policy compatibility, the declared state frame, old terminal
replay and actual source association. It captures its own loaded producer files,
inputs, assertion files and executable identities before running and checks them
afterward. OS/standard-library behavior and trusted host callbacks remain premises.

The five requirement tuples are distinct, including across matcher groups. Outer
applicability binds component, core, policy, assertions, profile, producer and exact
raw qualification identity. The existing matcher calls a sole refutation missing
because there is no pass; a pass plus an applicable refutation conflicts. The
report separately exposes the actual business refutation.

The live consumer begins with S1 only. S2 cannot be submitted before admission.
After applicable observations and an actual source check, it rechecks the current
base, authority and capacity. Only then does it register S2 and change the default
for new runs. Existing run pins, application state and terminal receipts stay put.
The isolated qualification does not prove its own initial provisioning.

## Old decline after a new application

1. Run A under S1 computes `Decline`; the caller cannot yet observe its receipt.
   Application revision remains R7.
2. S2 is admitted and run B starts with its exact source pin.
3. B produces `Propose`; the owner applies it and reaches R8.
4. Context reconstruction checks current S2, retained S1 and the exact independently
   expected pending packet. It restores caller data, never owner state or rights.
5. Observation with current permission disabled is denied. With permission restored,
   A returns its original `Declined` receipt at R7 without another application call.

`owned-outcome-pending/2` is distinct from the older pending-record payload. Exact
pending hash, current manager head and retained run/source binding are all required.
Changed hash, head or run pin refuses reconstruction.

## Finite checks

- Source/policy: 18 frozen complete wires.
- Readable form: 12 cases; the decoded source also runs the 17 owner scenarios.
- Detached edits: 17 cases and the separate zero-value counterexample.
- Context: 9 cases; unchanged legacy context tests retain their documented doubles.
- Applicability: 9 decisions, 42 fresh reader/reference calls and 24 matcher calls.
- Manager ordering: 11 cases with explicitly controlled receipt premises.
- Live composition: 17 additional reader/reference calls, 3 matcher calls and 2
  application evaluations, plus wrong-pin/head/run and current-permission refusals.

Portable drivers live in `tests/probes/component_outcome_*_checks.py`. Supply
separately reviewed executables and their exact hashes. The qualification driver
produces raw evidence and producer/qualification files; supply their independently
retained hashes to the connected driver. Hash equality identifies bytes, not a
trusted signer. Reports and local producer paths are runtime outputs, not repository
fixtures. Use the previously admitted bounded execution environment.

No new performance or model-cost measurement is implied. These checks do not prove
crash recovery, multi-process atomicity, authentication or arbitrary-program correctness.
