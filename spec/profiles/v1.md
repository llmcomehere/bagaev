# V1 — реестр области и правила её завершения

Версия проекта профиля: `bagaev-v1-design/r06` (r26). Статус: **WORKING_DESIGN**. Это реестр обязательств предоставленного design baseline. Существующей реализации нет: вопрос T00 решён D64 «чистый старт» (критерии на стадии 2, задача не завершена) ([исходная точка](../baseline.md)).

Канонические данные: [v1-feature-ledger.json](../../registry/feature-ledger.json). Табличные представления: [feature-ledger.csv](../../registry/feature-ledger.csv) и [feature-ledger.md](../../registry/feature-ledger.md). Будущие проверки имеют собственные ID и статус NOT_RUN. Они не становятся новыми критериями процентного счётчика.

## 1. Область остаётся полной

V1 включает язык, его runtime, долговечные данные, знание о программе, безопасное изменение, работу агента с контекстом, компилятор, инструменты, проверку пользы, передачу в реализацию и правила поставки. OBS/R03/CALL/AUTH исследуют отдельные части этой области.

| Группа | Обязательный состав | Владелец |
| --- | --- | --- |
| Исходная точка и область | Реальный исходный срез, совместимость, профиль, критерии пользы | T00–T01 |
| Модель программы | Identity/alias/revision, lineage, требования, snapshots, evidence | T02 |
| Представления и язык | Лексика, grammar, CST/AST/typed IR, source maps, roundtrip, все типы и вычисления | T03–T04 |
| Эффекты и runtime | Effect bounds, capabilities, contracts, reference machine, budget/cancel, handles, journal/replay | T05–T06 |
| Данные | Codec/schema, transactions, events, projections, migration, activation, crash/recovery | T07 |
| Знание и последствия | Typed graph, forward/reverse indexes, coverage, old/new impact, invalidation и full oracle | T08–T09 |
| Изменение и агент | ChangeContract, verification/acceptance CAS, intent, ContextPack, durable WorkState и protocol | T10–T12 |
| Инструментарий | Compiler phases, packages/locks, reference target, FFI, полный stdlib API, CLI/editor/debugger/reader | T13–T14 |
| Проверка и готовность | Authorship pilot, A/B/C, независимые oracles, замкнутая версия ТЗ | T15–T16 |
| Реализация и поставка | Component contracts, integration DAG, compatibility, reproducible build, install/update/recovery/release | T17–T18 |

В частности, параметрические функции и типы, рекурсивные функции и лексические замыкания уже входят в исходный V1. Их отсутствие в конечном CALL-профиле не является решением об исключении. Durable data/events остаются в V1, хотя R04 их не исполнял, а R05 проверяет только одну их абстрактную границу.

## 2. Три независимые оси реестра

1. **Обязательство:** required / excluded_with_diagnostic / separate_profile / decision_pending.
2. **Контракт:** unresolved / partial_draft / достаточно полное правило для своей явно ограниченной области.
3. **Основание:** будущий oracle / конкретное ревью / finite research execution / actual V1 conformance.

У обязательной возможности может быть проверенный исследовательский фрагмент и незакрытая общая семантика. Эти два факта сохраняются одновременно. Нельзя переименовать required в excluded только для совпадения с уже реализованной моделью.

Текущий реестр содержит **77 обязательных позиций**, 4 отдельные области расширений, 4 явных запрета и 3 решения о типах, которые ещё нужно принять: всего 88 позиций. Все исходные 96 критериев V1 связаны хотя бы с одной позицией; для позиций подготовлено 165 будущих positive/negative cases. Это прослеживаемость предоставленного плана, не 165 пройденных тестов и не закрытый список синтаксических форм. Групповые позиции, например «records/sums/collections», должны раскрываться до полного registry конструкций на T03/T04.

Каждая required-позиция имеет source refs точной редакции R04, owner tasks, исходные criterion IDs, draft refs, шесть клеток контракта, конкретные открытые решения и будущие случаи с ожидаемым исходом. Исходные SHA256 разрешаются внутри сохранённого плоского снимка R04, а не по изменяемым одноимённым файлам R05.

## 3. Что означает unresolved в рабочем проекте

У готового профиля [критерий полноты](../architecture/06-specification-completeness.md) допускает только полностью определённую поддержку, определённый запрет или отдельный профиль. В рабочем реестре unresolved/decision_pending явно обозначают блокер до такого состояния. Они не разрешают реализации придумать поведение самостоятельно.

Незакрытые обязательные области включают: полную grammar/IR schema; type inference/generic instantiation; полный primitive/error/cost registry; capability lifecycle/ABI; schema codec/migration/activation; общий retry/poison/retention protocol; полный stdlib; tool/agent wire schemas; реальные платформы; полный conformance и опыт T15. Наличие проектного текста о каждой из них не означает устранения всех пробелов.

Для рабочих экспериментальных сборок `PENDING_SPECIFICATION` означает отсутствие утверждённого правила. Опубликованный профиль V1 не может использовать этот ответ для обязательной формы: такая редакция ещё не SPEC_READY.

## 4. Исключения и точка отказа

| ID | Возможность | Статус | Диагностика в V1 |
| --- | --- | --- | --- |
| V1-X01 | Распределённое исполнение и межузловая exactly-once фиксация | Отдельный T19 | UNSUPPORTED_FEATURE до launch |
| V1-X02 | GPU и специальные устройства | Отдельный T20 | UNSUPPORTED_FEATURE до launch |
| V1-X03 | Специальные model/training/streaming-exchange профили | Отдельный T21 | UNSUPPORTED_FEATURE до launch |
| V1-X04 | Live code/state update | Отдельный T19 | UNSUPPORTED_FEATURE до launch |
| V1-X05 | Shared mutable threads | Запрет первого runtime | UNSUPPORTED_FEATURE до launch |
| V1-X06 | Произвольная dynamic loading | Запрет первого toolchain | UNSUPPORTED_FEATURE до launch |
| V1-X07 | Higher-kinded parameters и implicit ad-hoc dispatch | Запрет первого type profile | UNSUPPORTED_FEATURE до launch |
| V1-X08 | Циклический импорт пакетов | Запрет первого module profile | `MODULE_IMPORT_CYCLE` на resolve (прежнее имя `CYCLIC_PACKAGE_IMPORT` — псевдоним DIAG-1) |

Диагностика содержит feature_id, requested profile, supported profile revision и source location либо operation ref. Запрещённое исполнение и внешний эффект не начинаются. Отсутствует fallback к другой приблизительной семантике. Точная привязка к окончательным token/opcode/transport codes остаётся частью T03/T13/T14.

Эти исключения не запрещают обычный агентный протокол, статическую рекурсию функций, разрешённые типизированные host adapters, локальные durable transactions и остановленную миграцию. Программа V1 исполняется без обязательной LLM.

**r27 (решения приняты 23.10.2026).** V1-P01, V1-P02 — floating point и big integers исключены с `UNSUPPORTED_FEATURE`, это отдельный профиль (D71); V1-P03 — recursive user data types включены при регулярной рекурсии (D69). Пользовательский FFI (D87) и дополнения поставки (D88) исключены из V1 как сужение состава профиля; баллы за сужение не начисляются, затронутые критерии пересчитываются явно.

## 5. Сочетания, которые нельзя проверять по отдельности

В реестре сохранено 13 взаимодействий с собственным ожидаемым правилом и остатком работы. Основные:

- Strict evaluation × effects: неиспользуемый аргумент сохраняет эффект, невзятая ветвь — не исполняет его.
- Recursion/closures × budgets: остановка определяется машиной, а не аварией host stack.
- Optimization × observation domain: прежний value/error/trace witness не покрывает cost/cancel/settlement автоматически.
- Cancel × durable action: termination машины не стирает committed или неизвестный внешний результат.
- Capability × persistence: контейнер не позволяет сериализовать authority; attribution не даёт edit rights.
- Receipt × stale guards: старый успешный результат возвращается до проверки устаревшей попытки, но после current access check.
- Migration × activation × event backlog: судьба pending events и dedup фиксируется вместе с переходом state/schema/epoch.
- Graph × old/new impact: исчезнувшая связь остаётся существенной для прежнего потребителя.
- Context budget × WorkState: урезание видимого пакета не урезает обязательства.

Это не исчерпывающий combinatorial test corpus. При добавлении новой формы нужно раскрывать её новые наблюдаемые взаимодействия и связывать их с oracle, а не объявлять весь cross-product проверенным по нескольким примерам.

## 6. Порядок доведения реестра до реализации

1. Для каждой группы форм закрепить закрытую grammar/IR/protocol schema. Неизвестные варианты имеют явную диагностику.
2. Для каждой формы дописать typing/validation, transition order, effects/errors и budget/termination/recovery.
3. Зафиксировать независимый expected result, включая отрицательные и аварийные случаи; actual run учитывать отдельно.
4. Проверить междокументные сочетания и applicability research evidence. Все необоснованные расширения claim вернуть в unresolved.
5. После закрытия поведения назначить component/interface/integration path; independent implementer не должен достраивать семантику.

Процент считается по неизменной методике [SPEC-PROGRESS-1](../../docs/verification.md), 96 критериев × 4 балла. Число строк реестра, страниц, проверочных примеров и пройденных абстрактных transitions не увеличивает этот знаменатель и не даёт баллы автоматически.
