## 1. Проектное хранилище

**CHG-01.** Хранилище (D85) лежит в `<корень>/.bagaev/`:
- `objects/<sha256>` — неизменяемые объекты по содержимому: исходники, контракты, правки, свидетельства. Объект появляется целиком (запись во временный файл и переименование) или не появляется. При чтении его хеш сверяется;
- `project.db` — SQLite (WAL, `synchronous=FULL`, как HST-01) с таблицами:
  - `meta` — `head`, `head_revision`;
  - `snapshots` — манифест и признак «принят»;
  - `works` — входы работ;
  - `receipts` — квитанции операций;
  - `evidence` — свидетельства;
  - `acceptance` — записи приёмки;
  - `journal` — журнал операций.
- Все записи — в транзакциях `BEGIN IMMEDIATE`.
- `bag project init <корень>` делает начальный снимок рабочего дерева: файлы `*.bag` с путями в нормальной форме CHG-03, скрытые каталоги (`.git`, `.bagaev`) не входят. Снимок первый принятый, становится head с ревизией 1 и получает запись приёмки вида `bootstrap`. Наличие head проверяется внутри транзакции: повторный или одновременный `init` — `PROJECT_EXISTS`.
- Кэш графа `.bagaev/graph/<SnapshotId>/<extractor_rev>.json` (D84) — производный: запись `{tools, graph}`, где `tools` — дайджест кода всего эталона (итог CHECK-1 зависит от разборщика и проверки, не только от извлекателя). Запись атомарна (временный файл и переименование). Повреждённая запись, другая ревизия кода или другой набор исходников — промах, граф и проверка считаются заново. Это единственная запись при операциях чтения.
- git остаётся внешней VCS: хранилище его не заменяет.

**CHG-01а. Язык проекта** (r37) задаёт `bag project init` по файлам корня и хранит в `meta.language`: есть `*.bag` — `bagaev`; иначе есть `tsconfig.json` и `*.ts` — `typescript` (вариант B пилота, [contract.md](../../pilot/authorship/contract.md) §4а). Язык поставляет пять функций: проверку кандидата (CHECK-1 или компилятор TypeScript), граф общей схемы ([graph.schema.json](../links/graph.schema.json): LINKS-1 или извлекатель `pilot/authorship/links-ts/extract.ts`), прогон тестов (машина или `node --test`), сущности для операций идентичности и смыслы сущностей для поиска. Остальное — WorkState, свидетельства, обязательства, приёмка, протокол и транспорты — от языка не зависит и одинаково для обоих. Различия языка:
- исходники TypeScript — `*.ts` и `*.json` в нормальной форме путей CHG-03;
- идентичность кода в TypeScript — имя (переименование — удаление и новая сущность, без объявления); операции идентичности CHG-06 относятся к объявленным в JSDoc смысловым сущностям, контрактам и правилам;
- `assign_ids` у TypeScript — `REQUEST_INVALID`: `@id` нет.

## 2. Снимок

**CHG-02. Снимок** — манифест `{format: "bagaev-snapshot/1", parents, sources: {путь → ObjectRef}}` (ObjectRef CANON-09: вид `source`, формат `bag-utf8`, sha256, размер).
- SnapshotId = `digest("snapshot", "1", манифест)`.
- Граф (D84: `.bagaev/graph/<SnapshotId>/<extractor_rev>.json`), свидетельства, записи приёмки и признак «принят» в манифест не входят. Поэтому добавление свидетельства или приёмки SnapshotId не меняет (T02-C04).
- Равные исходники с равными родителями дают равный ID. Идентичности сущностей при этом не объединяются: они — `@id` внутри исходников (T02-C02).

## 3. SourceEdit и идентичность

**CHG-03. SourceEdit** — `{files: [...], identity_ops?: [...], assign_ids?: bool}`. Элемент `files`:
- `{path, base_sha256, edits: [...]}`, где правка — `{start, end, text}` (байтовый полуинтервал) или `{old_text, text}`;
- `{path, base_sha256, whole_file: text}`;
- `{path, base_sha256, delete: true}`;
- `{path, create: text}` — новый файл.

Путь — относительный `*.bag` в нормальной форме: сегменты `[A-Za-z0-9_][A-Za-z0-9_.-]*` через `/`, без пустых сегментов, `.`, `..` и скрытых имён. Так у файла одно имя: `a//b.bag` и `a/./b.bag` — `REQUEST_INVALID`. Файл указывается один раз.

**CHG-04. Проверка правки** — по порядку, каждый шаг для всей правки (всех файлов и `identity_ops`) до следующего; первый отказ останавливает её; кандидат при отказе не меняется:
1. форма — `REQUEST_INVALID`. Строки — представимые в UTF-8 (одиночный суррогат — нет);
2. `base_sha256` равен sha256 текущего файла кандидата — иначе `STALE_SOURCE`. Файла нет — тоже `STALE_SOURCE`; `create` существующего — `FILE_EXISTS`;
3. `old_text` встречается ровно один раз — иначе `AMBIGUOUS_EDIT` с числом вхождений. Перекрывающиеся вхождения считаются: `aa` в `aaa` — два;
4. `start ≤ end` в пределах файла и на границах скалярных значений UTF-8 — иначе `RANGE_INVALID`;
5. правки файла не пересекаются. Две вставки в одну точку и вставка на краю замены — тоже `OVERLAPPING_EDITS`: порядок не однозначен.

Правки применяются по убыванию начала. Отдельный сравнитель проходит вперёд по отрезкам без правок и проверяет, что они перешли в новый текст в том же порядке, а между ними стоят ровно тексты замен (T03-C04). Ответ называет затронутые диапазоны в новом тексте.

**CHG-05. Назначение ID.** `assign_ids: true` вставляет недостающие `@id` в затронутые файлы (FMT-16). Генератор детерминирован: семя — `digest("assign-ids", "1", {seed: "<работа>:<ревизия>"})`. Новые ID не совпадают ни с ID кандидата, ни с ID истории принятых снимков. Назначенные ID записываются в журнал правок вместе с правкой (`{source_edit, assigned_ids: {путь: [ID по порядку мест]}}`): перенос ставит те же ID (CHG-18).

**CHG-06. Идентичность.** Сравниваются EntityId кандидата до и после правки по местам SURF-07 (нужен разбор; неразбираемый результат — `CANDIDATE_UNPARSABLE`, кандидат не меняется):
- повтор ID (копия без нового ID) — `DUPLICATE_ENTITY_ID` (T03-C03);
- новый ID из истории принятых снимков, которого нет в кандидате, — `ENTITY_ID_RETIRED`: удалённый ID не воскресает (01 §7A);
- исчезнувший ID должен быть объявлен в `identity_ops`: `delete` (с причиной), `split.from` или `merge.from`. Иначе `ENTITY_REMOVED_WITHOUT_INTENT`;
- вид сущности под тем же ID не меняется (01 §3): функция не становится тестом — `ENTITY_KIND_CHANGED`. Смена вида — `delete` и новый ID;
- объявленная операция обязана совпасть с фактом, иначе `IDENTITY_OP_MISMATCH`:
  - `rename {id}` — ID в обеих версиях, имя другое;
  - `copy {from, id}` — источник жив, копия — новый ID того же вида;
  - `split {from, into[≥2], reason}` и `merge {from[≥2], into, reason}` — источники исчезли, преемники новые.

Переименование с тем же ID распознаётся и без объявления: это та же сущность (T02-C01). Преемник при split и merge не угадывается: обязательства прежней сущности остаются открытыми, пока их не закроют свидетельства преемника (T02-C03).

**CHG-07. Lineage.** Объявленные операции записываются в работу как записи `{op, predecessors, successors, reason}` и переходят в запись приёмки. Причина обязательна у `delete`, `split`, `merge`; у `rename` и `copy` — необязательна (`null`), `rename` добавляет `names: [прежнее, новое]`. Тело правки хранится объектом в журнале правок работы (для переноса, CHG-18).

**CHG-08.** Кандидат с ошибками проверки (CHECK-1) сохраняется как черновик (`draft: true`, диагностики в ответе). Принять его нельзя: блокер `CANDIDATE_INVALID` (A01).

## 4. ChangeContract и политика

**CHG-09. ChangeContract** — неизменяемый объект `{format: "bagaev-change-contract/1", change_id, revision, intent, base, policy, clauses, replaced, replaced_tests, policy_pins, assumptions, allowed}`. `policy` — ссылка на политику приёмки, закреплённую при `change_begin` (A05 шаг 3). Правка контракта (`contract_update`) даёт новую ревизию. Операции:
- `add_clause {id, claim, method: {test}, stage}` — условие успеха с методом проверки; `stage` — `program_acceptance` (по умолчанию) или `runtime_activation`. Последние приёмку программы не блокируют и выполненными не становятся (A05);
- `replace_clause {id, claim, method, reason}` и `remove_clause {id, reason}` — прежнее условие с причиной уходит в `replaced` и остаётся в истории. Запись приёмки перечисляет заменённые и удалённые условия: молча условие не исчезает (T10-C02);
- `replace_test {test, reason}` — тест базы (полное имя или EntityId) перестаёт быть методом своих правил: он изменён, удалён или снял `checks`. Без этой записи такой тест держит обязательства правила открытыми (CHG-13). Запись приёмки перечисляет заменённые тесты с причинами;
- `assume {obligation: [вид, цель, источник], reason}` — принятое предположение для обязательства. Действует только для видов, которые политика разрешает закрывать предположением;
- `scope {allowed}` — сущности (EntityId или полные имена), которые разрешено менять. Изменённая сущность внутри области, если её ID в списке или **все** её имена — в базе и в кандидате — в списке: переименование чужой сущности в разрешённое имя область не обходит. Вне области — блокер `SCOPE_EXCEEDED`. `null` снимает ограничение;
- `pin_policy {reason}` — закрепить текущую политику проекта. Прежняя и новая ссылки с причиной остаются в `policy_pins` и переходят в приёмку.

**CHG-10. Политика приёмки** — `.bagaev/policy.json` поверх политики по умолчанию. Допустимые основания по виду обязательства:

| Вид | Основания по умолчанию |
| --- | --- |
| `implements`, `requires` | `tests`, `D83a` |
| `checks` | `tests` |
| `about`, `derived_from` | `assumption` |
| условие контракта | `tests` (тест, названный методом) |

Раздел `obligations` файла заменяет основания перечисленных видов, остальные — по умолчанию. `D83a` закрывает обязательство, только если политика допускает его для этого вида; иначе пара — обычное обязательство. Раздел `principals` задаёт полномочия (CHG-14). Файл — `{format?, obligations?: {вид: [основания]}, principals?: {субъект: [операции]}}`; иная форма — `POLICY_INVALID` для любой операции.

Ссылка на политику — `digest("acceptance-policy", "1", политика без principals)`. Работа закрепляет её при начале; текущая политика, отличная от закреплённой, — блокер `POLICY_CHANGED`, пока работа не закрепит её заново (`pin_policy`). В приёмку записывается закреплённая политика. Политика не ослабляется автоматически.

## 5. Свидетельства

**CHG-11. Свидетельство** создаёт `verify`: прогон тестов кандидата на хранилищах в памяти (HST-18). Запись `{format: "bagaev-evidence/1", kind: "test-run", test, test_id, test_rev, subject (SnapshotId кандидата), verdict, closure, closure_complete, extractor_rev}`:
- `closure` — дайджест замыкания зависимостей теста в этом снимке (LNK-08-16);
- `closure_complete` — полнота переносящих видов CoverageRecord в снимке прогона;
- ID свидетельства = `digest("evidence", "1", запись)`.

Свидетельство неизменно и хранится вне снимка; работа хранит список их ID. `SKIP`, `TODO` и отсутствие наблюдения (`NOT_RUN`) сохраняются и не превращаются в PASS, в том числе у TAP `ok # SKIP` и `ok/not ok # TODO`. Последний результат теста вытесняет прежний PASS того же снимка. Ненулевой exit или сбой runner TypeScript даёт отдельное свидетельство `kind: "test-runner"`, `test: "runner:<путь>"`, `verdict: "ERROR"`, привязанное к модулю файла; успешный повтор даёт PASS. Записи runner не служат методами условий и к другому субъекту не переносятся.

Для TypeScript `verify` также сохраняет квитанцию всего прогона `{kind: "test-suite", test: "runner:typescript", subject, verdict, inventory: {путь: SHA256}}` в том же формате свидетельства и с тем же правилом ID. В `inventory` входят все запускаемые `test/**/*.test.ts`, даже без именованных тестов; пустой набор также получает квитанцию. PASS требует наблюдения каждого файла ровно один раз и успешного завершения всех runner. Добавление, переименование, удаление или изменение байтов runner требует нового полного прогона: набор сравнивается с последней целой квитанцией, а до неё — с базой. ERROR полного прогона сохраняется независимо от существования прежнего module ID (`runner-retry-required`) до успешного `verify`. Успешная квитанция снимает прежние ошибки, в том числе после реального удаления всех runner; возвращение удалённого файла снова требует проверки. Ошибка отдельного runner старого формата без общей квитанции также требует полного повтора. Повреждённая квитанция ошибки не снимает.

Граница варианта B: граф именованных тестов не описывает весь исполняемый верхний уровень TS и его импортов. Поэтому успешная общая квитанция действует только для текущего SnapshotId. Изменённый кандидат с runner требует нового полного `verify`, даже при неизменных байтах runner; `same-closure` именованного теста его не заменяет. Оптимизация такого переноса не реализована; это ограничение учитывается при сравнении B/C.

**CHG-12. Оценка свидетельства к обязательству** (A03, D13):
- `integrity` — запись совпадает со своим ID;
- `applicability`:
  - `applicable`, если субъект — текущий кандидат (`same-subject`);
  - `applicable` для неповторённого ERROR полного прогона TypeScript (`runner-retry-required`);
  - `applicable`, если замыкание теста в текущем кандидате и ревизия извлекателя те же, а полнота переносящих видов подтверждена и в свидетельстве, и в кандидате (`same-closure` — основание переноса); отсутствие записи о полноте переноса не разрешает;
  - иначе `stale`. Свидетельство другого кандидата без основания переноса не применяется (T10-C03);
- `sufficiency` — тест — метод правила (CHG-13): неизменённый тест базы, который проверяет правило, либо новый или изменённый тест, который проверяет правило и назван методом условия контракта (`program_acceptance`);
- `verdict` — результат теста.

`supports` = valid ∧ applicable ∧ sufficient ∧ PASS. Применимый FAIL/ERROR — противоречие. SKIP/TODO/NOT_RUN оставляют условие и обязательство открытыми (`test-not-run`).

## 6. WorkState

**CHG-13.** Работа хранит только входы: базу, кандидата, ревизию работы, контракт, статус (`open`, `accepted`, `abandoned`), список свидетельств, журнал правок, lineage. Всё остальное каждый раз пересчитывается чистой функцией (`work_resume`, только чтение):
- проверка кандидата;
- графы и анализ влияния (LINKS-1) с применимыми свидетельствами для D83(a);
- статусы обязательств и условий;
- блокеры и готовность.

Поэтому продолжение в другой сессии или другой моделью видит те же правила и обязательства (T12-C04), а лимит контекста их не теряет (T11-C04).

**Методы правила R.** Тесты базы, которые проверяют R, делятся на неизменённые (в кандидате с той же ревизией и по-прежнему `checks R`) и выбывшие (изменены, удалены или сняли `checks R`). Методы R — неизменённые тесты базы и тесты кандидата, которые проверяют R и названы методом условия контракта. Набор методов сохраняется целиком, а не «хотя бы один»: каждый выбывший тест требует записи `replace_test` с причиной.

Статус обязательства (пары LNK-08-17):
- `excluded_with_basis` и `unknown` — как в отчёте влияния; `D83a` — только если политика допускает его для вида;
- цель исчезла из кандидата: объявленный `delete` — `excluded_with_basis` с основанием `declared-delete` (решение с причиной в lineage приёмки); `split` или `merge` — статус по методам преемников: `supported`, если все преемники `supported`, `contradicted`, если любой; иначе `open` (`successor-evidence`);
- `supported` — допустимым основанием: для `tests` — у каждого метода правила применимый PASS; для `assumption` — предположение контракта;
- `contradicted` — у метода применимый FAIL;
- иначе `open` с причиной: `base-test-changed` (выбывший тест без `replace_test`), `no-method-tests` (методов нет), `evidence-missing-or-stale`, `no-method` (политика не даёт основания).

Тест, изменённый или добавленный в этой работе, не служит свидетельством для правила, пока не назван условием контракта; ослабленный или снятый тест базы держит обязательство открытым до явного `replace_test` (T10-C02, K6). Новое правило закрывается новым тестом, названным условием контракта.

**Блокеры приёмки:**
- `WORK_NOT_OPEN`, `NEEDS_REBASE` (head ≠ база), `CANDIDATE_INVALID`;
- `ANALYSIS_INCOMPLETE`;
- `OBLIGATION_OPEN`, `OBLIGATION_UNKNOWN`, `OBLIGATION_CONTRADICTED`;
- `CLAUSE_OPEN`, `CLAUSE_CONTRADICTED` (для `program_acceptance`);
- `EVIDENCE_CONTRADICTED` — применимый FAIL или ERROR **любого** теста кандидата, в том числе без `checks`: противоречие применимых свидетельств (A05 шаг 2);
- `TESTS_NOT_RUN` — тест кандидата из `tests_to_run` анализа влияния без применимого результата исполнения (в том числе SKIP/TODO/NOT_RUN), либо `runner:typescript` при необходимом полном повторе CHG-11: затронутое изменением прогоняется до приёмки;
- `SCOPE_EXCEEDED`;
- `POLICY_CHANGED` (CHG-10);
- `SUPERSEDES_UNKNOWN` — цель `supersedes` не встречается в истории принятых снимков или жива в кандидате (SURF-15).

Виды блокеров — коды DIAG-1 вида `blocker`. `ready_for_acceptance` истинно без блокеров. Неизвестное обязательное блокирует всегда (T10-C01).

Пробелы покрытия затронутых сущностей (`gaps` LINKS-1, например `EXTERNAL_CONSUMERS` у `pub command|query`, T08-C03) показываются в `work_resume` и записываются в приёмку (`coverage_gaps`, 03 §1 `coverage_refs`), но не блокируют: вызывающие точки входа вне программы — граница проекта, а не обязательство изменения внутри него. Решение принимающего видно в записи приёмки.

## 7. Операции протокола

**CHG-14. Субъект и полномочия.** Субъект (`principal`) задаёт транспорт: флаг `--principal` или `BAG_PRINCIPAL` у CLI, параметр запуска у MCP. Полем запроса назначить субъекта нельзя (04 §2). Раздел `principals` политики: `{субъект: [операции | "read" | "*"]}`; без раздела разрешено всё. Нет права — `ACCESS_DENIED`. Авторство в данных приложения прав на проект не даёт (O06).

**CHG-15. Запрос и ответ.**
- **Запрос:** `{protocol: "bagaev-protocol/1", operation, change_id?, expected_work_revision?, idempotency_key?, arguments}`. Неизвестные поля и операции отвергаются (`REQUEST_INVALID`, `UNKNOWN_OPERATION`).
- Операции чтения: `search`, `inspect`, `relations`, `impact`, `context`, `why`, `check`, `run_tests`, `work_resume`. Операции записи: `change_begin`, `contract_update`, `apply`, `verify`, `rebase`, `accept`, `abandon`.
- Каждая запись требует `idempotency_key` (CANON-10), а все, кроме `change_begin`, — ещё и `expected_work_revision`.
- **Ответ:** `{protocol, operation, status: succeeded | blocked | failed, replayed, change_id?, work_revision?, result | error{code, data, retry}}`. `retry`: `fix_request`, `new_key`, `new_decision`.

**Порядок записи** (R16 §7):
1. форма;
2. дайджест `digest("project-op", "1", {operation, change_id, expected_work_revision, arguments})`. Ожидаемая ревизия входит: новая ожидаемая ревизия — новое намерение. Числа аргументов кодируются строками;
3. транзакция `BEGIN IMMEDIATE` — квитанция по `(principal, namespace, key)` ищется **до** guard'ов, где namespace — работа, у `change_begin` — `project`:
   - тот же дайджест — сохранённый ответ с `replayed: true`;
   - другой — `IDEMPOTENCY_CONFLICT`;
4. полномочие;
5. guard'ы работы: работа существует; `expected_work_revision` равен текущему — иначе `WORK_CONFLICT`; работа открыта;
6. операция;
7. атомарно — новое состояние работы, объекты, журнал и квитанция.

Отказ на шагах 4–6 ничего не пишет и ключ не резервирует (как HST-05): повтор после нового решения — с новой ожидаемой ревизией, то есть новым дайджестом. Каждая успешная запись увеличивает ревизию работы на 1. ID работы = `ch-` + префикс `digest("change-id", "1", {principal, key})`.

В аргументах для дайджеста и журнала целое `n` — `{"$int": "n"}`, а ключ объекта, начинающийся с `$`, удваивает его. Запись однозначна: `5` и `{"$int": "5"}` дают разные дайджесты. Аргументы чтения проверяются по форме до поиска работы (`budget`, `cursor`, `analysis_budget` — целые ≥ 0; `query`, `entity`, `snapshot` — строки). Любое иное исключение реализации — ответ `failed` с кодом `INTERNAL`: транзакция откатывается, транспорт продолжает работу.

**CHG-19. Поиск** (`search`) возвращает кандидатов с основаниями (`name`, `purpose_or_terms`, отрицательное `not_about`), а не выбор (`selection: "none"`).
- Сходство текста не доказательство (T11-C01).
- Совпадение с `not_about` сущности — отрицательное основание (атрибуция ≠ совместное редактирование, T11-C02).
- `ambiguous` — при равном лучшем счёте или отрицательном основании среди первых трёх.
- Выбор фиксирует область контракта (`scope`).

## 8. Приёмка

**CHG-16. `accept`** — в транзакции записи CHG-15:
1. head = база работы — иначе `STALE_BASE`, head не меняется (A05 шаг 4);
2. производное состояние пересчитывается заново внутри транзакции. Блокеры, кроме `NEEDS_REBASE`, дают `OPEN_OBLIGATIONS` с их перечнем;
3. вместе:
   - запись приёмки `{format: "bagaev-acceptance/1", kind: "change", change_id, base, candidate, work_revision, contract, contract_revision, policy, principal, evidence, assessments, lineage, obligations, clauses, replaced_clauses, replaced_tests, policy_pins, coverage_gaps, head_revision}` (ID — дайджест). `assessments` — оценки последних свидетельств тестов: `[свидетельство, тест, применимость, основание переноса, вердикт]` (A05 шаг 1);
   - снимок помечается принятым, `head` = кандидат, `head_revision` + 1;
   - работа `accepted`, ревизия + 1;
   - журнал и квитанция.

Видимый head никогда не ссылается на отсутствующую приёмку. Две работы от одной базы: первая принятая сдвигает head, вторая получает `STALE_BASE` (T10-C04, C07). Точки сбоя `BAG_CRASH_AT=<операция>_before_commit | <операция>_after_commit` — как HST-16: до фиксации ничего не видно, после фиксации повтор с тем же ключом возвращает квитанцию.

**CHG-17.** Приёмка ничего не исполняет: ни тестов, ни точек входа, ни миграций, ни доставки событий. Активация данных — отдельный контракт хоста (HST-14, HST-15; D29, T10-C06). Свидетельства берутся только записанные.

## 9. Перенос на новый head

**CHG-18. `rebase`** (head ≠ база; иначе `REBASE_NOT_NEEDED`) повторяет журнал правок работы на текущем head:
- файл, равный в head прежнему состоянию, — правка как есть;
- изменённый файл — только правки `old_text`, если вхождение единственно;
- иначе — `REBASE_CONFLICT` с путём, работа не меняется.

ID, назначенные при `apply` (CHG-05), ставятся из журнала те же. Идентичность перехода head → новый кандидат проверяется заново (CHG-06) с объединением объявленных операций; несовпадение с новым head (например, удалённое работой уже удалено в head) — тоже `REBASE_CONFLICT`. База = head, кандидат — новый снимок с родителями `[head, прежний кандидат]` в этом порядке. Свидетельства не копируются: применимыми остаются только переносимые по `same-closure`. Совместный кандидат двух работ проходит полный анализ и проверку (T10-C05). Автоматическое текстовое слияние приёмкой не является.

## 10. Транспорты

**CHG-20. Один протокол, два транспорта** (D86, D17):
- CLI `bag op <корень> '<запрос>'` — JSON-запрос в JSON-ответ;
- MCP stdio `bag mcp <корень>` — JSON-RPC 2.0 с методами `initialize`, `tools/list`, `tools/call`. Инструменты `bag_<операция>` принимают поля запроса без `protocol` и `operation`. Ответ — тот же объект в `structuredContent` и тексте, `isError` при статусе не `succeeded`.
- По JSON-RPC 2.0: пакет (массив) — массив ответов, пустой пакет — `-32600`; уведомление (без `id`) исполняется без ответа; не объект, без `jsonrpc: "2.0"` или без `method` — `-32600`; `params` или `arguments` не объект — `-32602`; неизвестный метод — `-32601`; не JSON — `-32700`; исключение — `-32603`. Сервер после любой ошибки продолжает работу.

`bag mcp --selftest` прогоняет один сценарий через оба транспорта на копиях проекта и сравнивает ответы побайтно (T14-C05). Обёртки: `bag project init`, `bag work resume <корень> <работа>`.

## 11. Наблюдения корпуса

Случаи фаз `edit`, `accept`, `protocol` задают `run.change.steps` — запросы протокола ([conformance/README.md](../../conformance/README.md)). Наблюдение — проекции ответов по операциям; дайджесты заменены на `<digest>`, пояснения `detail` не сравниваются. Проекция приёмки перечисляет каждое обязательство вне `excluded_with_basis` с основанием, заменённые условия и тесты, пробелы покрытия: ослабление видно в наблюдении, а не только множество видов.
