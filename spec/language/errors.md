# ERR-0.1 — фазы отказа и значения ошибок

**R06 · WORKING_DESIGN.** Общий проект V1; exact codes и record shapes исполнимого CORE принадлежат [API](../../models/r07-core/experiments/core-machine/API.md). Ошибки OBS/CALL/AUTH сохраняют свои прежние версии и не переклассифицируются задним числом.

## 1. Разделение исходов

| Фаза/категория | Значение для вызывающего | Исполнялись ли шаги программы |
| --- | --- | --- |
| Decode / PrelaunchDiagnostic | Artifact/вход не принят по точному правилу профиля | Нет |
| Returned(v) | Получено значение declared type; v может быть Result.Err | Да; для уже терминального внутреннего состояния новых шагов нет |
| Fault | Определённая языком остановка: переполнение или деление на ноль оператором, повтор ключа литерала Map, проверка теста (D72, OUT-01) | Да; транзакция откатывается |
| SemanticStop BudgetExceeded | Израсходован указанный семантический ресурс | Только сохранённый prefix |
| SemanticStop Cancelled | Отмена видна на определённой границе | Только сохранённый prefix |
| ImplementationStop | Реализация не смогла предоставить обещанную семантику или нарушен invariant | Prefix, если его можно корректно сообщить; успех не синтезируется |
| EffectResult Indeterminate | Исход конкретного внешнего действия пока не установлен | Может сосуществовать с termination caller |
| Analysis UNKNOWN | Основания недостаточно для данного claim | Это не execution outcome |

Malformed input — не Result.Err приложения. `Err(Overflow)` — обычное значение, не SemanticStop. Физический таймаут, нехватка памяти host или внутренний Python exception не подменяют BudgetExceeded шагов. Diagnostic recovery IDE не разрешает запуск непроверенного IR.

## 2. Checked arithmetic CORE

Диапазон Int64: `−9223372036854775808 … 9223372036854775807`. Математическая операция вычисляется без host wrap, затем проверяется представимость результата.

| Операция | Тип результата | Отказ как значение |
| --- | --- | --- |
| i64.eq / i64.lt | Bool | Нет для допустимых Int64 |
| i64.add / i64.sub | Result<Int64,ArithmeticError> | Overflow |
| i64.div | Result<Int64,ArithmeticError> | DivisionByZero; MIN / −1 → Overflow |
| i64.rem | Result<Int64,ArithmeticError> | DivisionByZero; MIN rem −1 → Ok(0) |

Division quotient округляется к нулю. Остаток вычисляется как математический `a − trunc(a/b) × b`, имеет знак dividend при ненулевом значении и сам представим даже в случае MIN rem −1. Не требуется предварительно превращать математический quotient в Int64: иначе rem ошибочно наследует отказ div. Нулевой denominator проверяется до вычисления quotient. У `0 / 0` один определённый результат — Err(DivisionByZero).

Persistability проверяется по полному типу: Result<Fn,ArithmeticError> не сохраняется даже в ветви Err. Отсутствие Function в данном payload не меняет свойство declared type.

Конструктор Err требует ArithmeticError payload; неизвестное имя ошибки отвергается до запуска. Полученное Err может быть аргументом функции, значением Let или возвращаемым Result. Только явный Match выбирает обработку ошибки. Например, функция, игнорирующая аргумент типа Result, может вернуть обычное значение после вычисления Err-аргумента; runtime не имеет скрытого early return.

### 2.1. Операторы исходника (r26, D72)

| Оператор | Тип | Отказ |
| --- | --- | --- |
| `a + b`, `a - b`, `a * b`, `-a` | Int64 | `Fault(ARITHMETIC_OVERFLOW)` |
| `a / b` | Int64, усечение к нулю | `Fault(DIVISION_BY_ZERO)`; `MIN / -1` → `Fault(ARITHMETIC_OVERFLOW)` |
| `a % b` | Int64, знак делимого | `Fault(DIVISION_BY_ZERO)`; `MIN % -1` = 0 |

Проверяемые функции `std.i64.add/sub/mul/div/rem/neg` возвращают Result по таблице §2. Программа выбирает форму явно: оператор, если переполнение — ошибка программы; функцию, если это предметный исход.

## 3. Порядок видимых границ

1. `Value` при пустом continuation уже terminal; поздний cancel и нулевой остаток его не меняют.
2. В нетерминальном состоянии сначала учитывается видимая отмена.
3. Если отмены нет, нулевой бюджет даёт BudgetExceeded без следующего перехода.
4. Иначе списывается один шаг и исполняется ровно один переход.

Поэтому cancel и budget=0 на одной нетерминальной границе дают Cancelled. Cancel, назначенный на границу сразу после последнего нужного перехода, не отменяет уже вычисленный terminal value. Это правило задаёт воспроизводимость, а не обещание обработать wall-clock signal до любого физического instruction.

Расписание отмены research profile задаётся числом уже завершённых логических переходов. Настоящий runtime должен зарегистрировать фактическую точку видимости; преобразование внешнего запроса в такую запись требует отдельного общего journal contract. CORE не посылает host effects и не проверяет late settlement.

## 4. Нарушение инварианта и неправильная программа

Unbound Var, невозможный frame/value kind или отсутствующий tag внутри принятого состояния — ImplementationStop. То же имя/tag, отсутствующее в поданном source/IR, должно быть обнаружено prelaunch. Нельзя одновременно принимать malformed IR и считать его внутреннюю неисправность допустимым программным исходом.

Уже зафиксированное внешнее действие не откатывается из-за поздней остановки caller. Запись settlement отдельна от termination. В CORE таких действий нет; данное правило сохраняется из SEM-0.1 для будущего effectful runtime.

## 5. Состав diagnostics полного V1

Общая запись: `code`, `phase`, `profile_revision`, `artifact_ref`, `node_ref?`, `source_span?`, `expected?`, `actual?`, `related_refs[]`, `message`. Коды, фазы и шаблоны сообщений — реестр [DIAG-1](../diagnostics/registry.json) (r26, D80). Поля source span и prose помогают человеку, но не заменяют stable code и exact refs. Полный wire schema и международные тексты — T03/T12; текущая запись является проектом, не обещанием уже реализованного API.

Checker идёт детерминированно по форме и её source order, затем типовым правилам. Kernel возвращает первую ошибку по нормативному порядку профиля. Параллельный compiler может собирать дополнительные ошибки, сохраняя каноническую основную. Превышение его собственных guard limits отражается отдельно и не доказывает непригодность программы на всех реализациях.
