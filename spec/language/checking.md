# CHECK-1 — статическая проверка `bag check`

**r28 · WORKING_DESIGN.** Документ задаёт, как `bag check` применяет к проекту правила [surface.md](surface.md), [effects.md](effects.md) и [types.md](types.md), и где стоят диагностики фаз `resolve`, `type` и `effect`: диапазон и поля `data`. На этом тексте основаны ожидания корпуса `conformance/cases/{resolve,types,effects}` (origin = independent). Правила имеют идентификаторы `CHK-nn`.

## 1. Проект

**CHK-01. Вход.** `bag check <корень>` читает все файлы `*.bag` под корнем. Путь файла в диагностиках — относительный, с `/`. Модуль файла `<корень>/a/b.bag` — `a.b` (SURF-01).
- Имена `std` и `std.*` принадлежат набору инструментов: пользовательский файл с таким модулем → `DUPLICATE_DECLARATION` на пути модуля, модуль не загружается.
- Корень без файлов `*.bag` — исход `ACCEPTED`: проверять нечего. Корень, который не является каталогом, — ошибка вызова, а не исход проверки.
- Исчерпание защитного предела глубины реализации — исход `IMPLEMENTATION_STOP` с кодом `RESOURCE_LIMIT` (TYPES-0.1 §10).

**CHK-02. Порядок фаз.**
1. Сначала лексика и разбор всех файлов. Если хоть один файл дал диагностику `lex` или `parse`, ответ содержит только их.
2. Иначе проверяются имена, типы и эффекты всего проекта. Собираются все диагностики. Канонический ответ — первая по ключу SURF-58, режим редактора выдаёт все в этом порядке.
3. Нет диагностик — исход `ACCEPTED`, иначе `PRELAUNCH` ([outcomes.md](../kernel/outcomes.md), OUT-08).

**CHK-03. Без каскада.** Подвыражение, на котором выдана диагностика, получает тип «ошибка». Он совместим с любым типом, поэтому одна причина даёт одну диагностику. Так же:
- атом ряда с непубличным путём даёт только `PRIVATE_ITEM`, атом `host` — только `UNKNOWN_HOST_ADAPTER`;
- `match`, у которого шаблон ветви не разрешён, не проверяется на полноту;
- аргумент `Table`, на котором выдана диагностика, не вносит атом в ряд вызова.

## 3. Имена и объявления (фаза `resolve`)

**CHK-05. Импорт.**
- `use a.b` и `use a.b as c` вводят псевдоним модуля. `use a.b.{X, Y as Z}` вводит публичные объявления модуля `a.b` с этим именем из любых пространств; одноимённое непубличное объявление другого пространства не вводится. Если публичного нет ни одного → `PRIVATE_ITEM`. Реэкспорта нет.
- Псевдонимы модулей — отдельная таблица (SURF-03): совпадение псевдонима с именем объявления не ошибка, а повтор псевдонима — `DUPLICATE_DECLARATION`.

**CHK-06. Голова пути в выражении** ищется так: локальное имя → значение модуля (своё или импортированное) → тип модуля → псевдоним модуля → предопределённый вариант `Some None Ok Err` → предопределённая сумма `Option Result`. Дальнейшие сегменты — по SURF-06: хранилище → таблица, тип-сумма → вариант, значение → поле записи.

**CHK-07. Шаблон `match`** — путь к варианту той суммы, которой является проверяемое значение: `Some(x)`, `Shape.Circle(r)`, `m.Shape.Circle(r)`. Голое имя варианта пользовательского перечисления не ищется. Связывание `(x)` или `(_)` у варианта с нагрузкой необязательно; у варианта без нагрузки оно → `ARGUMENT_COUNT`. Шаблон opaque-типа `T(x)` разбирает значение в модуле объявления.

## 4. Объявления (фазы `type` и `effect`)

**CHK-09. Сигнатуры.** Таблицы и события всех модулей разрешаются первыми, затем параметры, результат и ряд каждой функции и точки входа — до проверки тел (D74). Отсюда:
- запись типа корректна (TYPES-0.1 §2): у `Map<K, V>` нужно `Key(K)`, у аргумента типа — ограничения его параметра. Нарушение → `BOUND_NOT_SATISFIED` на записи типа; проверяется после разрешения всех объявлений, предикаты — gfp;
- `TYPE_ARITY` — тип целиком; `data`: `type`, `expected`, `actual`;
- `TABLE_TYPE_NOT_MAP` — тип таблицы; `BOUND_NOT_SATISFIED` для `Key(K)` и `Persistable(V)` таблицы — тип таблицы;
- `EVENT_NOT_PERSISTABLE` — имя поля события;
- `COMMAND_RESULT_NOT_RESULT` — тип результата;
- `MIGRATION_TYPE_MISMATCH` — тип результата миграции, если он не `Result<V, E>` с V, равным типу значения таблицы;
- параметр handler не событие → `TYPE_MISMATCH` на типе параметра, `expected` = `event`.

**CHK-10. Ряды в сигнатурах.**

| Код | Диапазон | `data` |
| --- | --- | --- |
| `UNKNOWN_EFFECT_TARGET` | путь атома `reads/writes` (не таблица) или `emits` (не событие); путь таблицы `migration … on` | `path` |
| `UNKNOWN_HOST_ADAPTER` | путь атома `host` | `name` |
| `UNKNOWN_EFFECT_VARIABLE` | имя переменной ряда | `name` |
| `EFFECT_NOT_ALLOWED_IN_CONTEXT` | атом в `uses` точки входа вне EFF-09 | `atom` — как в исходнике, `context` |
| `TABLE_PARAM_ONLY_IN_STD` | тип `Table<…>` вне `std.store` | — |

## 5. Тела (фазы `type` и `effect`)

**CHK-11. Направление.** Проверка двунаправленная (TYPES-0.1 §7). Ожидаемый тип передаётся внутрь вызова (сначала результат, затем аргументы слева направо), лямбды, литералов, ветвей `if` и `match`, хвоста блока.

**CHK-12. Финализация** (TYPES-0.1 §5) выполняется после инициализатора каждого `let`, после каждого оператора-выражения и после тела функции. На границе проверяется только то, что возникло внутри неё:
- нерешённый тип специализации → `AMBIGUOUS_TYPE_ARGUMENT`, диапазон — место специализации (путь функции, `None`, `[]`, литерал карты), `data.param` — имя параметра типа;
- нерешённый тип параметра лямбды → `PARAMETER_TYPE_REQUIRED` на имени параметра;
- эффект-переменная, которую не задали аргументы, получает ρ(e) = ∅ (EFF-06); ожидаемый тип результата на ρ(e) не влияет и сверяется с ним после вычисления;
- отложенное ограничение → `BOUND_NOT_SATISFIED`.

**CHK-13. Тип блока.** Значение блока — хвост, без хвоста — `()`. Если последний оператор блока без хвоста имеет тип `Never` (`return x;`), блок имеет тип `Never` (D90, принято 24.10.2026; уточняет SURF-23).

**CHK-14. Эффекты тела.** Место атома:
- вызов функции — весь вызов, ряд вызова по EFF-05 с подстановкой таблиц (EFF-07) и ρ(e) (EFF-06);
- `emit` — всё выражение `emit`;
- вызов значения fn-типа — весь вызов.

Ряд лямбды без ожидаемого fn-типа — её фактический ряд. Ряд лямбды, переданной на место параметра с эффект-переменной, входит в ρ(e) и тем самым в ряд вызова, а не в ряд объемлющей функции напрямую.

**CHK-15. Где ставятся диагностики тел:**

| Код | Диапазон | `data` |
| --- | --- | --- |

**CHK-16. Запись типов и атомов в `data`.**
- Встроенные типы пишутся по имени, Unit — `()`. Номинальный тип — `модуль.Имя<аргументы>`, параметр типа — его имя.
- Атом — `reads модуль.Хранилище.таблица`, `writes …`, `emits модуль.Событие`, эффект-переменная — её имя.
- Атомы упорядочены по виду (`reads`, `writes`, `emits`, `host`), затем по записи.
- Ряд — `{ атом, … }`, пустой — `{}`. Ещё не решённая эффект-переменная вызова пишется последней через `| ` своим именем из сигнатуры вызываемой функции: `{ reads m.S.t | e }`, `{ | e }`.
