# FORMAT-1 — канонический формат исходника

**r28 · WORKING_DESIGN.** Канонический формат задаёт `bag fmt`. Формат не меняет смысл программы: разбор отформатированного текста даёт то же AST с точностью до диапазонов (T03-C02). Формат идемпотентен: `fmt(fmt(x)) = fmt(x)`. Правила имеют идентификаторы `FMT-nn`.

Ширины строки нет. Переносы задаются структурой (блоки) и решением автора (списки и цепочки операторов, FMT-12). Поэтому вывод детерминирован, а переименование не меняет раскладку соседних строк: правка `SourceEdit` остаётся локальной.

## Файл

**FMT-01.** UTF-8 в NFC; перевод строки LF; ровно один LF в конце файла; пробелов в конце строк нет.

**FMT-02.** Отступ — два пробела на уровень вложенности блока или тела объявления.

**FMT-03.** Порядок верхнего уровня:
1. заголовок модуля;
2. пустая строка;
3. объявления `use` в исходном порядке, без пустых строк между ними;
4. пустая строка;
5. объявления верхнего уровня в исходном порядке, разделённые одной пустой строкой.

## Объявления

**FMT-04.** Перед объявлением стоят:
1. документирующие комментарии `///`, каждый на своей строке;
2. атрибуты, каждый на своей строке;
3. строка объявления.

У поля, варианта, таблицы и правила атрибут стоит на той же строке перед именем: `@id("k3m9qa") title: String,`.

**FMT-05. Сигнатура.**
- Без `uses` и связей — одна строка: `fn f(a: Int64) -> Int64 {`.
- Параметры раскладываются по FMT-12: если автор перенёс строку после `(`, каждый параметр стоит на своей строке с отступом +2 и запятой, затем `) -> T`. Единственный параметр `handler` и `migration` всегда пишется в строку.
- С ними — заголовок `fn f(…) -> T`, затем каждая из частей `uses …`, `implements …`, `requires …`, `checks …`, `supersedes …` на отдельной строке с отступом +2, затем `{` на отдельной строке с отступом объявления.

**FMT-06. Ряд эффектов.** `uses { reads S.a, writes S.a, emits E }`. Атомы упорядочены по виду (`reads`, `writes`, `emits`, `host`), затем по пути. Переменная пишется последней: `| e`. Ряд только из переменной пишется `uses e`. Пустой ряд `{}` сохраняется.

**FMT-07. Тела объявлений** — `record`, `enum`, `event`, `store`, `contract`, `entity`: один элемент на строке. После полей и вариантов ставится запятая, после таблиц, правил и предложений сущности — нет. Пустое тело записи — `record {}`.

## Блоки и выражения

**FMT-08. Блок** с хотя бы одним оператором или хвостом всегда многострочный: `{`, каждый оператор на своей строке, хвост на своей строке, `}`. Пустой блок — `{}`. Одна или несколько пустых строк между операторами, ветвями или элементами тела объявления в исходнике сохраняются как одна пустая строка; в начале и в конце блока пустых строк нет.

**FMT-09. Операторы.** `let x: T = e;`. Выражение-оператор с `;`, кроме блоковых выражений без `;` (SURF-50). Формат сохраняет наличие или отсутствие `;` у блокового выражения.

**FMT-10. `if`** — `if c {`…`} else if d {`…`} else {`…`}`. **`match`** — `match e {`, каждая ветвь на своей строке с запятой после тела, включая тело-блок, затем `}`.

**FMT-11. Пробелы.**
- Бинарные операторы окружены пробелами. Унарный `-` пишется слитно, `not` — с пробелом.
- Постфиксы `.f`, `(…)`, `?` пишутся без пробелов.
- После запятой — пробел. В `( )`, `[ ]`, `< >` внутренних пробелов нет. В `{ }` литерала записи пробел есть: `T { a: 1 }`, пустой — `T {}`.
- Скобки выражений сохраняются. Скобки в типах печатаются только там, где без них меняется смысл: вокруг функционального типа без ряда, стоящего результатом перед `uses`.

**FMT-12. Решение автора о переносе.**
- Аргументы вызова, элементы литералов последовательности, записи, карты и `emit`, параметры сигнатуры: если в исходнике сразу после открывающей скобки стоит перевод строки, каждый элемент печатается на своей строке с отступом +2 и запятой после него, закрывающая скобка — на отдельной строке. Иначе список пишется в строку.
- Бинарный оператор: если между левым и правым операндом в исходнике есть перевод строки, оператор переносится в начало следующей строки с отступом +2.
- Аргументы типов, ряды эффектов, образцы и `use`-группы всегда пишутся в строку.
- Правило идемпотентно: напечатанный многострочный список снова начинается с перевода строки.

**FMT-13. Литералы** сохраняют исходное написание: экранирования, шестнадцатеричную запись, `_` в числах. Значение не перекодируется.

## Комментарии

**FMT-14.** Комментарии не теряются.
- Комментарий перед объявлением, оператором, ветвью match или элементом тела объявления переносится на отдельную строку перед ним с текущим отступом.
- Комментарий внутри выражения и комментарий в конце строки кода переносятся на отдельную строку перед ближайшим объемлющим оператором, ветвью или элементом.
- Порядок комментариев сохраняется.
- `///` после кода на той же строке — документирующий комментарий следующей декларации (LEX-06), а не хвост строки: он остаётся перед ней.
- Комментарии внутри тела `entity` печатаются перед его предложениями.

## Отказ

**FMT-15.** Файл с лексическими или синтаксическими ошибками не форматируется. `bag fmt` возвращает те же диагностики, что `bag parse`, в том же каноническом порядке.

## Назначение ID

**FMT-16.** `bag fmt --assign-ids` вставляет `@id("…")` во все обязательные места без него (SURF-07). Свежий ID случаен, состоит из 6 символов Crockford base32 и не совпадает ни с одним ID файлов, переданных команде; поэтому `--assign-ids` вызывают на корне проекта. Повтор с ID вне этих файлов ловит `bag check` (`DUPLICATE_ENTITY_ID`). Без флага форматтер ID не добавляет и не меняет.
