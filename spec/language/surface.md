# SURFACE-1 — поверхностный язык bagaev и его отображение в BIR-1

**r26 · контракт V1.**

Документ задаёт для каждой конструкции исходника:
- её смысл;
- форму единого IR BIR-1, в которую она переводится;
- порядок вычисления;
- статические правила и диагностики.

Связанные документы: лексика — [lexical.md](lexical.md); грамматика — [grammar.ebnf](grammar.ebnf); эффекты — [effects.md](effects.md); типы — [types.md](types.md); данные — [data-values.md](data-values.md); исходы — [kernel/outcomes.md](../kernel/outcomes.md); коды — [DIAG-1](../diagnostics/registry.json).

Решения: D66–D75, D79, D81, D82 ([07-decisions.md](../architecture/07-decisions.md#решения-r25)). Полная схема BIR-1 с полями узлов и правилами машины — Ф3 (`spec/ir/bir.md`, `spec/runtime/machine.md`). Здесь закреплены имена форм и порядок.

Правила имеют идентификаторы `SURF-nn` для [манифеста соответствия](../conformance-manifest.json).

## 1. Принципы

1. **Один способ записи.** В языке нет:
   - методов, перегрузки и неявных преобразований;
   - исключений и null;
   - макросов и аргументов по умолчанию;
   - наследования, циклов `for/while` и кортежей.

   Повторение выражается рекурсией и функциями `std.seq`.
2. **Явность на границах.** Сигнатуры функций и точек входа верхнего уровня полностью аннотированы, включая эффекты (D74). Типы выводятся только внутри тела.
3. **Происхождение каждого имени видно.** Каждое имя пришло из `use`, из объявления этого модуля или из предопределённого набора (§2.4). Вызовы чужих функций квалифицированы именем модуля: `seq.map(xs, f)`.
4. **Связи извлекаются, а не пишутся.** Вызовы, чтения и записи таблиц, события извлекает компилятор. Вручную пишутся только смысловые связи: `implements`, `requires`, `checks`, `supersedes`, `derived_from`.

## 2. Файл, модуль, имена

**SURF-01. Файл = модуль.**
- **Корень проекта** — каталог, который передан инструменту (`bag check <корень>`). Файл `<корень>/a/b.bag` объявляет `module a.b`. Несовпадение → `MODULE_PATH_MISMATCH`.
- Пример: у `examples/basics/` и `examples/authorship/` свои корни; `examples/authorship/blog/editor.bag` объявляет `module blog.editor`.
- Модули `std.*` встроены в набор инструментов.

**SURF-02. Импорт.**
- `use a.b` делает модуль доступным под последним сегментом имени: `b.f(x)`.
- `use a.b as c` — под именем `c`.
- `use a.b.{X, Y as Z}` вводит отдельные публичные объявления.
- Группа допустима только последним сегментом; `as` — только без группы. Иначе → `INVALID_USE_GROUP`, диапазон — токен после группы (`.` или `as`).
- Импорт непубличного объявления → `PRIVATE_ITEM`.
- Цикл импортов модулей → `MODULE_IMPORT_CYCLE` (V1-X08).
- Неизвестный модуль → `UNKNOWN_MODULE`.

**SURF-03. Пространства имён.** Их три:

| Пространство | Что в нём | Где ищется |
| --- | --- | --- |
| **типы** | `type`, `event` (событие — тип записи) | позиции типов; голова `T(e)`, `T {…}`, `T.V`; `emit E`, `emits E`, параметр handler |
| **значения** | `fn`, `command`, `query`, `handler`, `migration`, `test`, `store`, параметры и локальные имена | выражения; эффект-атомы `reads/writes S.t` |
| **смыслы** | `entity`, `contract` | `about`, `derived_from`, `implements`, `requires`, `checks` |

Правила:
- **Повторы.** Повтор имени в одном пространстве модуля, включая имена, введённые `use`, → `DUPLICATE_DECLARATION`. Затенения на уровне модуля нет.
- **Затенение в телах.** Внутри тел локальное имя затеняет внешнее и получает новый BinderId ([types.md §3](types.md#3-разрешение-имён-и-рекурсивные-области)).
- **Повторы внутри объявлений.** Повтор имени поля, варианта, таблицы или правила внутри одного объявления → `DUPLICATE_MEMBER`.
- **Выражения.** В позиции выражения путь сначала ищется среди значений. Если первый сегмент — тип, допустимы только три формы: `T(e)` (конструктор opaque), `T {…}` (литерал записи) и `T.V` (вариант).
- **Модули.** Псевдонимы модулей из `use` — отдельная таблица. Первый сегмент пути ищется в порядке: локальное имя → объявление или импортированное имя модуля → псевдоним модуля → предопределённое имя.

**SURF-04. Видимость.**
- Без `pub` объявление видно только в своём модуле. Это относится ко всем видам, включая `entity`, `contract`, `store`, `event`; импорт непубличного → `PRIVATE_ITEM`.
- `pub` у `command` и `query` экспортирует их хосту: вызвать точку входа без `pub` нельзя (`ENTRYPOINT_NOT_EXPORTED`).
- `handler`, `migration` и `test` всегда принадлежат хосту и из кода не вызываются: `pub` у них → `PUB_NOT_ALLOWED`.
- Никакая точка входа не вызывается из кода как функция (`ENTRYPOINT_NOT_CALLABLE`).
- Конструктор и разбор `opaque`-типа доступны только в модуле объявления; снаружи → `OPAQUE_CONSTRUCTOR_OUTSIDE_MODULE`.

**SURF-05. Предопределённые имена** (не требуют `use`):
- типы `Bool`, `Int64`, `String`, `Bytes`, `Unit`, `Never`, `Option<T>`, `Result<T, E>`, `Seq<T>`, `Map<K, V>`;
- конструкторы `Some`, `None`, `Ok`, `Err`;
- ограничения `Eq`, `Key`, `Persistable`.

Unit записывается как `()` и в типе, и в значении. Функции библиотеки предопределёнными не являются: `use std.seq` и т. п. обязательны (STDLIB-API-0.1: неявного prelude функций нет).

**SURF-06. Цепочка `a.b.c`.** Её разбирает разрешение имён слева направо:
1. Первый сегмент — локальное имя, импортированный модуль, объявление этого модуля или предопределённое имя.
2. Следующие сегменты по виду предыдущего:
   - модуль → его объявление;
   - тип-перечисление → вариант;
   - хранилище → таблица;
   - значение-запись → поле.

Неизвестный сегмент → `UNKNOWN_NAME` или `UNKNOWN_VARIANT`. Поле значения-записи требует типа значения, поэтому неизвестное поле обнаруживает фаза типов: `UNKNOWN_FIELD`, фаза `type`.

## 3. Объявления и идентичность

**SURF-07. Устойчивый ID (D67).**
- Правило синтаксическое и проверяется без типов. `@id("xxxxxx")` несут:
  - заголовок модуля;
  - каждая декларация верхнего уровня;
  - **каждое** поле каждой `record` и `event`;
  - **каждый** вариант каждого `enum`;
  - каждая `table` и каждое `rule`.

  Параметры, локальные имена и лямбды ID не имеют, атрибут там синтаксически невозможен.
- ID — 6 символов Crockford base32 в нижнем регистре: цифры и буквы, кроме `i l o u`.
- ID непрозрачен и никогда не выводится из имени.
- Ошибки:
  - нет ID → `MISSING_ENTITY_ID`, исправление вида `assign_id`: инструмент `bag fmt --assign-ids` вставляет свежий ID;
  - неверная форма → `MALFORMED_ENTITY_ID`;
  - повтор в проекте → `DUPLICATE_ENTITY_ID`. Копия обязана получить новый ID, угадывания нет.
- Переименование сохраняет ID. Смена ID — это удаление и создание, его видит анализ влияния (SourceEdit, Ф6).
- LLM, которая пишет новый код, может опустить `@id`: `bag check` выдаст `MISSING_ENTITY_ID` с исправлением, `bag fmt --assign-ids` вставит ID. Придумывать ID нельзя.

**SURF-08. Атрибуты.**
- В V1 есть только `@id`. Неизвестный атрибут → `UNKNOWN_ATTRIBUTE`.
- Атрибуты стоят перед `pub` и ключевым словом объявления.
- Документирующие комментарии `///` стоят перед атрибутами и относятся к той же декларации.

**SURF-09. Функция** `fn name<T: Eq, !e>(p: T, …) -> R uses {…} implements … { тело }`:
- **Параметры и результат** аннотированы. Без `uses` функция чистая.
- **Обобщения**: параметры типов с ограничениями и эффект-переменные `!e` ([effects.md §3](effects.md#3-эффект-переменные)).
- **Рекурсия.** Все функции модуля образуют одну рекурсивную группу BIR `LetRec`, допустима взаимная и полиморфная рекурсия (D74). Между модулями рекурсии нет: импорты ацикличны.
- **Проверка.** Тело проверяется против аннотации результата; эффекты тела ⊆ объявленных → иначе `UNDECLARED_EFFECT`.
- **Запуск** `bag run <модуль>.<имя>` исполняет `pub fn` без параметров (по соглашению `main`). Нет такого имени → `UNKNOWN_ENTRYPOINT`; есть параметры → `ENTRYPOINT_SIGNATURE`.

**SURF-10. Типы.** `type Name<…> = record {…} | enum {…} | opaque T`:
- **record** — номинальная запись. Поля имеют устойчивые ID; порядок объявления значим ([data-values.md §1](data-values.md#1-типовая-идентичность-и-неизменяемость)).
- **enum** — закрытая сумма. Вариант без данных или с одним значением `V(T)`; несколько значений собираются в запись. Хотя бы один вариант.
- **opaque T** — новый номинальный тип с представлением T. Конструктор `Name(v)` и разбор `match x { Name(v) => … }` доступны только в модуле объявления. Так задаются инварианты: значения `Authors` создаёт только функция, проверяющая правила.
- **Рекурсивные типы** допустимы (D69), если рекурсия регулярна: аргументы при рекурсивном обращении те же, что у объявления. Иначе → `IRREGULAR_RECURSIVE_TYPE`.
- **Синонимов типов нет.**

**SURF-11. Сущность и контракт** (D82):
- `entity Name { purpose "…" terms […] not_about […] }` — смысловая сущность. Её поиск по намерению используют `bag search` (Ф5–Ф6). Исполнимого содержания у неё нет.
- `contract Name about Entity { rule r "…" … }` — контракт: именованные обязательства, привязанные к сущности. Правило — это утверждение, которое подтверждается тестами (`test … checks Contract.r`) и анализом приёмки. Сам компилятор правило не исполняет.
- Неизвестная цель `about` или правило → `INVALID_LINK_TARGET`.

**SURF-12. Хранилище и таблицы** (D81).
- `store S { table t: Map<K, V> [derived_from Entity] … }` объявляет долговечное хранилище.
- Тип таблицы — `Map<K, V>` с `Key(K)` и `Persistable(V)` (иначе `TABLE_TYPE_NOT_MAP` или `BOUND_NOT_SATISFIED`).
- `derived_from` помечает проекцию, которая выводится из сущности.
- Доступ к таблицам — только функциями `std.store` в контексте транзакции ([effects.md §4](effects.md#4-хранилище-события-и-точки-входа)).

**SURF-13. Событие.** `event E { поле: T, … }` — Persistable-запись, которую производит `emit` и потребляет `handler`. Полезная нагрузка — полный снимок (D45).

**SURF-14. Точки входа** — правила транзакций в [effects.md §4](effects.md#4-хранилище-события-и-точки-входа):
- `command f(…) -> Result<T, E>` — транзакция. При `Ok` фиксируются данные, outbox и receipt. При `Err` или Fault ничего не меняется. Результат не `Result` → `COMMAND_RESULT_NOT_RESULT`.
- `query f(…) -> T` — только чтение (`reads`); иначе `EFFECT_NOT_ALLOWED_IN_CONTEXT`.
- `handler h(ev: E)` — транзакция обработки одного события E. Тело типа Unit. Повтор того же события дедуплицируется (D46).
- `migration m on S.t (old: OldV) -> Result<NewV, Err>` — чистое преобразование записи таблицы. Тип значения таблицы `S.t` обязан быть NewV (иначе `MIGRATION_TYPE_MISMATCH`). Его выполняет хост при остановленных писателях (D10):
  - записи обходятся по возрастанию ключа (порядок Key);
  - первый `Err` или FAULT останавливает миграцию; отчёт содержит ключ и ошибку;
  - ничего не активируется, прежняя пара кода и данных остаётся действующей.
- `test t checks … { … }` — тест. Тело типа Unit, проверки — функции `std.test`. Fault означает FAIL.

**SURF-15. Связи.**
- `implements`, `requires` и `checks` после сигнатуры перечисляют пути к сущности, контракту или правилу (`Contract.rule`) в пространстве смыслов; цель должна существовать (`INVALID_LINK_TARGET`).
- `supersedes` перечисляет **строки ID** заменённых деклараций: `supersedes "k3m9qa"`. Заменённая декларация обычно уже удалена, поэтому пути к ней нет. ID должен встречаться в истории проекта, то есть в принятых снимках (проверяется в Ф6).
- Все эти связи дают рёбра с provenance=declared ([links/01](../links/01-records-and-invariants.md)).

| Ключевое слово | Смысл |
| --- | --- |
| `implements` | декларация отвечает за правило |
| `requires` | декларация полагается на правило |
| `checks` | тест проверяет правило |
| `supersedes` | декларация заменяет прежнюю (по ID) |

## 4. Выражения

Вычисление строгое, слева направо, по значению ([semantic-core.md §4](semantic-core.md#4-минимальная-машина-вычислений)). Все ветви проверяются статически, исполняется только выбранная.

| ID | Конструкция | Форма BIR-1 | Порядок и правило |
| --- | --- | --- | --- |
| SURF-20 | `42`, `0x2a`, `"текст"`, `b"\x00"`, `true`, `()` | `Const` | — |
| SURF-21 | имя `x`, путь `m.f` | `Var` (разрешённый BinderId / EntityId) | — |
| SURF-22 | `let x: T = e; …` и `let _ = e;` | `Let` | e один раз, затем остаток блока. С аннотацией e проверяется против T. Обобщения в let нет |
| SURF-23 | блок `{ s1; s2; e }` | цепочка `Let` | Операторы по порядку. Значение блока — хвостовое выражение, без него — `()`. Если последний оператор блока без хвоста имеет тип `Never` (`return x;`), блок имеет тип `Never` (D90, CHK-13) |
| SURF-24 | `f(a, b)` | `Call` | Сначала f, затем аргументы слева направо, затем вход в тело. Неверное число аргументов → `ARGUMENT_COUNT` |
| SURF-25 | `r.field` | `Field` | Сначала r. Поле должно существовать (`UNKNOWN_FIELD`) |
| SURF-26 | `T { a: e1, b: e2 }` | `Record` | Значения полей в **исходном** порядке, затем раскладка по порядку объявления. Нужен ровно каждый объявленный ID поля: иначе `MISSING_FIELD` или `DUPLICATE_FIELD` |
| SURF-27 | `T { ..base, b: e }` | `Let`(base) + `Record` с `Field`(base, …) для непереопределённых полей | Сначала base, затем явные поля по исходному порядку. Хотя бы одно явное поле (`RECORD_UPDATE_WITHOUT_FIELDS`) |
| SURF-28 | `E.V`, `E.V(e)`, `Some(e)`, `None`, `Ok(e)`, `Err(e)`, `T(e)` для opaque | `Variant` | Payload, затем обёртка. Тип суммы берётся из ожидаемого контекста или из аргумента; `None`/`Err` без контекста → `AMBIGUOUS_TYPE_ARGUMENT` |
| SURF-29 | `[e1, e2]` | `SeqLit` | Элементы слева направо. Пустой `[]` требует ожидаемого типа |
| SURF-30 | `Map { k1 => v1, k2 => v2 }` | `MapBuild` (FAULT при повторе — в его правиле MAP_BUILD; r30, MCH-08) | Все пары слева направо (сначала ключ, затем значение), затем построение. Повтор ключа: если все ключи — константы, `DUPLICATE_MAP_KEY` до запуска; иначе `Fault(DUPLICATE_KEY)` с позициями первого и повторного ключа. Проверяемая форма без Fault — `std.map.build` → `Result` (D79) |
| SURF-31 | `if c { a } else { b }`, `else if` | `If` | c: Bool. Без `else` ветвь должна иметь тип Unit, отсутствующая ветвь — `()` |
| SURF-32 | `match e { P1 => a, P2(x) => b }` | `Match` | e один раз. Шаблон — вариант суммы с необязательным связыванием payload (`_` — не связывать). Покрытие точное: нет ветви → `NON_EXHAUSTIVE_MATCH`, повтор → `DUPLICATE_MATCH_ARM`, чужой вариант → `UNKNOWN_MATCH_TAG`. **Ветви «всё остальное» нет**: новый вариант заставляет обновить все match, и анализ влияния это видит |
| SURF-33 | `a and b`, `a or b` | `If(a, b, false)`, `If(a, true, b)` | Короткое замыкание |
| SURF-34 | `not a` | `Prim(op.not@1)` (r30, BIR-08) | — |
| SURF-35 | `a + b`, `a - b`, `a * b`, `a / b`, `a % b`, `-a` (Int64) | `Prim(op.add@1)` и т. п. (r30, BIR-08) | Сначала a, затем b. Переполнение, деление на ноль и `MIN / -1` → `Fault(ARITHMETIC_OVERFLOW)` или `Fault(DIVISION_BY_ZERO)` (D72). Деление с усечением к нулю. `%` имеет знак делимого; `MIN % -1 = 0`. `-N` с литералом N сворачивается в константу (так записывается MIN) |
| SURF-36 | `a ++ b` | `Prim(string.concat)`, `Prim(bytes.concat)`, `Prim(seq.concat)` по типу | Тип обоих операндов одинаков: String, Bytes или Seq<T> |
| SURF-37 | `a == b`, `a != b` | `Prim(op.eq@1)`, `Prim(op.ne@1)` (r30, BIR-08) | Нужно `Eq(T)` для одного точного T (`BOUND_NOT_SATISFIED`) |
| SURF-38 | `a < b`, `<=`, `>`, `>=` | `Prim(op.lt@1)` и т. п. (r30, BIR-08) | Нужно `Key(T)`. Порядок — [data-values.md §6](data-values.md#6-полный-порядок-key) |
| SURF-39 | `e?` | `Match(e, Ok(x) => x, Err(y) => Return(Err(y)))`; для Option — `Some(x) => x, None => Return(None)` | Функция обязана возвращать `Result<_, E>` с **тем же** E или `Option<_>`, иначе `QUESTION_MARK_CONTEXT`. Неявного преобразования ошибок нет (D73) |
| SURF-40 | `return e`, `return` | `Return` | Тип выражения — `Never`. Завершает текущую функцию или точку входа; без значения — `()`. В теле лямбды завершает лямбду |
| SURF-41 | `fn(x: T, y) => e` | `Lambda` | Создание без вычисления тела, захват значений. Типы параметров берутся из аннотации или из ожидаемого fn-типа (`PARAMETER_TYPE_REQUIRED`). Эффекты тела ⊆ ожидаемых ([effects.md §3](effects.md#3-эффект-переменные)) |
| SURF-42 | `emit E { поля }` | `Record` + `Perform(event.emit@1, E)` | Тип Unit, эффект `emits E`. Только в command и handler (и функциях, которые они вызывают) |

## 5. Литералы и числа

**SURF-45.** Целые литералы имеют тип Int64 (LEX-11). Неявного расширения и сужения нет. Строковый литерал имеет тип String, байтовый — Bytes. Литерал вне диапазона Int64 → `INT_LITERAL_OUT_OF_RANGE` (LEX-11). Числа с плавающей точкой (LEX-12) и упоминание типов `Float` или `BigInt` → `UNSUPPORTED_FEATURE` с `feature_id` V1-P01 или V1-P02 (D71).

## 6. Правила разбора, которые грамматика не выражает

**SURF-50. Блоковое выражение как оператор.** `if`, `match` или `{…}` в позиции оператора без `;` заканчивает оператор и обязано иметь тип Unit (`EXPECTED_UNIT_STATEMENT`, диапазон — это выражение). Последнее такое выражение блока — его значение (хвост).

**SURF-51. Отброшенный Result.** Оператор `e;`, где e имеет тип `Result<…>`, → `RESULT_DISCARDED` (диапазон — e). Явный отказ от результата — `let _ = e;`. Отброшенное значение другого типа допустимо.

**SURF-52. Запись в условии.** В условии `if` и выражении `match` литерал записи не разбирается без скобок: `if (p == Point { x: 0, y: 0 }) { … }`. Нарушение — запись вида `Path { имя: …` сразу после условия → `RECORD_LITERAL_IN_CONDITION`, диапазон — `{`.

**SURF-53. `and` и `or`.** Смешение без скобок (`a and b or c`) → `MIXED_AND_OR`; диапазон — первый оператор другого вида (`or`).

**SURF-54. Сравнения неассоциативны.** `a < b < c` → `NONASSOC_COMPARISON`; диапазон — второй оператор сравнения.

**SURF-55. Запятые в match.** Между ветвями `match` запятая обязательна, кроме ветви, тело которой — блок (`MISSING_COMMA_IN_MATCH`, диапазон нулевой длины сразу после тела ветви). Завершающие запятые допустимы во всех списках.

**SURF-59. Синтаксические ошибки.**
- Неожиданный токен → `UNEXPECTED_TOKEN`, диапазон — сам токен, `data.expected` — допустимые там токены.
- Неожиданный конец файла → `UNEXPECTED_EOF`, диапазон нулевой длины в конце.
- Зарезервированное слово на месте имени → `RESERVED_WORD_AS_NAME`, диапазон — слово.

**SURF-56. `uses` у fn-типа** относится к ближайшему fn-типу. Для внешней декларации fn-тип результата берётся в скобки.

**SURF-57. Обращение к записи** `Path { … }` допустимо только сразу после пути (`RECORD_LITERAL_NOT_AFTER_PATH`, диапазон — `{`). Внутри записи `name: e` — поле, `..e` — база обновления, `k => v` — пара карты; смешение видов в одном литерале → `MIXED_RECORD_ENTRIES`, диапазон — первый элемент другого вида.

**SURF-58. Первая ошибка.** Канонический ответ `bag check` — минимальная диагностика по ключу:
1. фаза в порядке DIAG-1 `phase_order` (lex → parse → resolve → type → effect);
2. путь файла относительно корня, по кодовым точкам;
3. начало диапазона диагностики — для типов и эффектов это узел, на котором обнаружено нарушение (аргумент, ветвь, место атома);
4. порядок кода в DIAG-1.

Режим редактора собирает и остальные.

## 7. Формы BIR-1 (предварительный перечень)

Выражения:

```text
Const  Var  Let  LetRec  Lambda  Call  If  Match  Record  Field
Variant  SeqLit  MapBuild  Prim(name@rev)  Perform(op@rev, resource)  Return
```

Декларации:

```text
Module  TypeDecl  Fn  Entity  Contract  Store/Table  Event
Command  Handler  Query  Migration  Test
```

У каждого узла есть `nid`. Исходные диапазоны хранятся отдельно в OriginMap. Для подмножества `Const, Var, Let, LetRec, Lambda, Call, If, Match, Prim` с типами Bool/Int64/Unit/Result правила вычисления и трассы L1 совпадают с CORE-0.1 ([core-machine.md](../runtime/core-machine.md)) с точностью до переименования форм. Поэтому 30 программ его корпуса остаются независимым оракулом (план, Ф3).

**r30.** Действующий перечень форм — [BIR-1](../ir/bir.md): `Var` разделён на `Local` и `Global`, отдельного `LetRec` нет (группа модуля связывается до запуска, MCH-04 и MCH-11). На поверхностный синтаксис перенесены 25 программ CORE. C10–C13 (локальный `letrec` с захватом) и C15 (`Ok(42)` без контекста) невыразимы; их подмножество проверяет мост core01.
