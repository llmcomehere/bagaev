# SEM-0.1 — общий семантический контракт V1

Статус: **рабочее проектное решение R05, не замороженная спецификация**. Этот документ связывает правила типов, вычислений, эффектов, runtime и долговечных операций. Он не заменяет будущую полную грамматику, схему typed IR, таблицу стандартной библиотеки и доказательство type safety. Неопределённые места перечислены в §12 и в [реестре V1](../../registry/feature-ledger.json); до их закрытия SPEC_READY недостижим.

Исходная область остаётся заданной [архитектурой языка](../architecture/02-language-runtime.md), [критериями полноты](../architecture/06-specification-completeness.md) и исходными T00–T18. Исследовательские OBS/R03/CALL сохраняют собственные версии и ограничения. Новая семантика не приписывается их старым результатам задним числом.

## 1. Объекты, которые нельзя подменять друг другом

| Объект | Что обозначает | Чего из него не следует |
| --- | --- | --- |
| EntityId | Устойчивая идентичность сущности программы | Имя, право редактирования, revision или хеш содержимого |
| ProgramSnapshot | Неизменяемая версия связанной программы | Активация этой версии и миграция долговечных данных |
| RuntimeInstance | Конкретное исполнение выбранного snapshot | Другая версия программы при изменении accepted head |
| StateVersion | Версия атомарного состояния конкретного store | Версия отдельной предметной записи или свежесть её проекции |
| Domain revision | Версия значения, например авторства статьи | Версия всех квитанций, очередей и индексов хранилища |
| OperationKey | Идентичность намерения произвести эффект | Успех эффекта, полномочие или возможность повторить его с другими аргументами |
| Evidence | Свидетельство о claim, методе и точных входах | Универсальное доказательство, capability или текущее право принять изменение |

Domain IDs (`ArticleId`, `PersonId` и другие) номинально различны и также не совпадают с EntityId программы. Их конкретное кодирование должно быть версионировано. Равенство строкового представления двух разных номинальных типов не разрешает подстановку.

## 2. Значения, типы и сохранение

Обязательные типы V1: Bool, Int64, String из Unicode scalar values, Bytes, Unit, записи, размеченные объединения, Option, Result, последовательности и отображения. Значения неизменяемы. V1 включает параметрические функции и типы, рекурсивные функции и лексические замыкания; ограничение CALL на ациклические вызовы не исключает их из языка.

### 2.1. Решения этой редакции

1. Int64 занимает диапазон от −2^63 до 2^63−1. Переполнение не оборачивается и не наследует поведение host-языка. Проверяемые арифметические примитивы возвращают `Result<Int64, ArithmeticError>`; ошибка деления на ноль и `MIN_INT / -1` различимы. **r26 (D72):** операторы исходника `+ - * / %` при переполнении или делении на ноль дают определённую остановку `FAULT` (`ARITHMETIC_OVERFLOW`, `DIVISION_BY_ZERO`), а не Result ([SURF-35](surface.md#4-выражения)). Для целочисленного деления результат округляется к нулю, остаток удовлетворяет `a = q*b + r` и при ненулевом значении имеет знак `a`. Написание операторов — [surface.md](surface.md); полная таблица примитивов — Ф3 (MACHINE-1).
2. Bool не является Int64. Условие принимает Bool; число, непустой текст или контейнер не получают неявную истинность. Неявного преобразования между номинальными ID, текстом и числами нет.
3. String сохраняет последовательность Unicode scalar values. Непарные суррогаты и некорректный UTF-8 отвергаются на входе соответствующего декодера. Неявной нормализации Unicode нет. Равенство сравнивает последовательность scalar values; лексикографическое сравнение использует их числовые значения. Пользовательский grapheme cluster и байт не подменяют scalar value. Отдельные API для этих представлений должны быть названы и типизированы.
4. Bytes — последовательность значений 0…255. Сравнение лексикографическое. Преобразование Bytes → String является явным декодированием с типизированной ошибкой, а не заменой повреждённых байтов без указания вызывающего.
5. Порядок списка существенен. Map принимает только ключевой тип с определённым полным порядком; обход идёт по этому порядку. Ключи и значения конструктора сначала вычисляются в порядке исходного выражения; каноническая сортировка хранения выполняется после вычисления. Повтор ключа — явный результат отказа конструктора, а не выбор последней записи. Точный API конструктора закрепляет T13.
6. Сравнение данных структурно только внутри разрешённых сравнимых типов. Function, Capability и HostHandle не получают скрытого сравнения адресов. Набор разрешённых key/comparable типов и вывод этих свойств должны быть закрытой таблицей T04.
7. **r26:** рекурсивные пользовательские типы включены (D69); плавающая точка и большие целые исключены из V1 с `UNSUPPORTED_FEATURE` (D71).  Higher-kinded parameters и неявный ad-hoc dispatch остаются за пределами первого профиля согласно исходной архитектуре.

### 2.2. Замыкания и persistability

Замыкание содержит ссылку на код точной версии и неизменяемое лексическое окружение. Переменная захватывает значение, а не будущую изменяемую ячейку. Рекурсивная группа имеет явные связи с определениями группы; свободные значения извне фиксируются при создании окружения. Произвольного динамического поиска нового accepted head нет.

`Persistable(T)` выводится структурно для разрешённых данных и их компонентов. Function, Capability и HostHandle не являются persistable; контейнер с таким элементом также не является persistable. Поэтому сериализация замыкания не становится способом сохранить полномочие или оживить закрытый дескриптор. Чтобы сохранить намерение выполнить действие, программа сохраняет типизированные данные команды; при её исполнении полномочия проверяются заново. Точная бинарная/текстовая схема codec остаётся задачей T03/T07, а правило запрета уже определено.

Локальный вывод типов должен быть конечным опубликованным алгоритмом; экспортируемые сигнатуры явны. Эта глава не объявляет алгоритм унификации, generalization и вывода полиморфной рекурсии завершённым. Неявное угадывание типов на этом основании запрещено.

## 3. Ошибка программы, остановка runtime и неизвестный эффект

Одна универсальная метка `error` теряет существенные различия. Контракт использует независимые категории; их закрытые словари и коды — [kernel/outcomes.md](../kernel/outcomes.md) (OUT-01…OUT-07):

| Категория | Пример | Семантика |
| --- | --- | --- |
| PrelaunchDiagnostic | Ошибка типа, неизвестная версия IR, необъявленный effect | Исполнение данного экземпляра не начато |
| Returned(value) | `Ok(x)`, `Err(DivisionByZero)`, `None` | Программа вычислила значение указанного типа |
| SemanticStop | `BudgetExceeded(kind)`, `Cancelled(request_id)` | Машина остановлена определённым правилом; это не значение Result программы |
| Fault | `ARITHMETIC_OVERFLOW`, `DIVISION_BY_ZERO`, `DUPLICATE_KEY`, `TEST_ASSERTION` | Определённая языком остановка программы (D72); транзакция точки входа откатывается; это не значение Result |
| ImplementationStop | Host memory guard, нарушение инварианта компилятора/адаптера | Реализация не предоставила обещанное семантическое выполнение; не принимается за доказательство результата программы |
| EffectResult | Succeeded / Rejected / Indeterminate | Отдельное знание о конкретном вызванном эффекте |
| AnalysisResult | PASS / FAIL / UNKNOWN с областью | Результат проверки claim, не исход выполнения и не полномочие |

Предлагаемый общий тип ответа зарегистрированного host adapter:

```text
EffectResult<T, E> = Succeeded(T)
                   | Rejected(E)
                   | Indeterminate(OperationKey)
```

`Rejected(E)` допустим лишь когда контракт адаптера определяет отказ и его отношение к уже выполненной работе. Для операции с одной атомарной границей это означает отсутствие новой фиксации этой операции. Адаптер, способный частично изменить внешний мир, обязан иметь отдельное типизированное описание частичного результата; ему запрещено выдать такой случай за простой отказ без изменения. `Indeterminate` означает, что подтверждённого исхода сейчас нет. Истечение ожидания или разрыв соединения не превращают его в Rejected.

`Result.Err` является обычным значением. Передача Err как аргумента разрешена, если тип аргумента — Result; она не останавливает вычисление автоматически. Явная операция распространения ошибки, если включена в синтаксис, разворачивается в Match и ранний возврат совместимого Result. Ошибки отдельных OBS-примитивов прежних профилей не переинтерпретируются этим правилом: они сохраняют прежнюю терминальную семантику своего профиля.

RunReceipt должен независимо фиксировать termination, упорядоченные host calls, их OperationKey и состояние settlement. Возврат значения не доказывает, что все ранее возникшие Indeterminate разрешены. Отмена тоже не стирает committed receipt; исход внешней операции после отмены может оставаться неизвестным.

## 4. Минимальная машина вычислений

Рабочая форма состояния:

```text
Machine = (snapshot, control, lexical_env, continuation,
           semantic_budgets, cancel_queue, host_journal,
           effect_settlements, runtime_instance)
```

Контракт использует явный continuation stack; семантика не зависит от глубины стека Python, Rust или другого host. Таблица ниже задаёт правила для классов форм, а не окончательный сериализованный opcode registry.

| Форма | Правило вычисления | Основное обязательство типов |
| --- | --- | --- |
| Const / Var | Константа является значением; Var читает точную lexical binding | Значение имеет объявленный тип; свободной переменной в typed IR нет |
| Let(x, a, b) | Вычислить a один раз; связать значение; вычислить b | Тип x — тип a; b проверен в расширенном окружении |
| Seq(a, b) | Вычислить a, затем b | Возвращается тип b; эффекты объединяются |
| If(c, a, b) | Вычислить c; исполнить только выбранную ветвь | c: Bool; типы ветвей совместимы; обе проверены статически |
| Record / Variant / List | Вычислить выражения полей слева направо в объявленном source order | Каждое поле соответствует declared type; tag существует |
| Map | Вычислить пары слева направо; затем проверить ключи и канонизировать хранение | Key type имеет разрешённый полный порядок |
| Match | Вычислить scrutinee один раз; выбрать соответствующую ветвь и привязать payload | Для закрытого sum все варианты покрыты; branch result types совместимы |
| Lambda | Создать closure с точным code ref и immutable environment | Типы параметров/результата и effect bound определены |
| Recursive group | Создать согласованную группу lexical code bindings | Вызовы имеют проверенные сигнатуры; алгоритм вывода рекурсии опубликован |
| Call(f, args) | Вычислить f; затем все args слева направо; только потом войти в тело | Арность и типы совпадают; эффекты тела входят в bound |
| Prim | Вычислить все явные аргументы; применить версионированное правило примитива | Типы/ошибки/границы указаны в его записи |
| Host | Вычислить аргументы; проверить текущую capability; dispatch; получить typed EffectResult | Declared effect покрывает вызов; adapter ABI согласован |

Short-circuit `and`/`or` разворачивается в If с соответствующим Bool-значением. Оно не эквивалентно строгому вызову двухаргументной функции при эффектах или остановке второго аргумента. Canonical serialization не переставляет исходный порядок вычисления полей и аргументов.

Вход в тело функции происходит после вычисления её аргументов. В `f(f(x))` внутренний вызов завершается до открытия внешнего frame. Настоящая рекурсия V1 исполняется до значения, остановки или исчерпания бюджета; исследовательский отказ CALL на recursive call graph не становится правилом runtime V1.

Неполный Match в исходнике — диагностика до запуска. Неизвестный tag в сериализованных данных — ошибка versioned decoder. Неизвестный tag или unbound Var, появившиеся внутри уже принятого well-typed IR вопреки проверенным предпосылкам, — ImplementationStop, а не новый предметный путь, который разрешено выдумать адаптеру.

## 5. Бюджеты, отмена и воспроизводимость

### 5.1. Порядок на границе шага

```text
step(machine):
    if machine already terminal: return machine
    if cancellation visible at this semantic boundary:
        terminate Cancelled; retain effect settlement records
    if remaining semantic steps == 0:
        terminate BudgetExceeded(steps); retain settlement records
    consume one reference-machine step
    execute the specified transition
```

Если cancel и нулевой step budget одновременно видимы на одной границе, выигрывает Cancelled. Поступление отмены имеет запись в журнале; replay воспроизводит ту же точку видимости, а не текущее wall-clock время. Уже терминальное состояние не меняется из-за более поздней отмены.

Поздний ответ host может дополнить отдельную историю settlement, но не переписывает зафиксированный termination завершённой машины. Recovery читает такую историю отдельной операцией. Это позволяет одновременно сохранить факт Cancelled и позже установить, что ранее отправленное действие всё же было committed.

Семантические шаги — переходы reference machine. Это не host instructions, не миллисекунды и не количество внутренних оптимизационных проходов. Отдельно лимитируются размер создаваемых значений, глубина вызовов и объём выводимых данных. Для каждого такого лимита нужна точная единица, правило списания и точка проверки до соответствующего действия. Полные таблицы для всех будущих IR forms ещё не закрыты; произвольный backend не может выбрать их молча.

Переход dispatch внешней операции и переход принятия её ответа различны. Между ними операция может завершиться после остановки caller. Истечение runtime budget не должно синтезировать rollback внешней фиксации. Вторая граница отвечает за получение/сохранение знания об эффекте, а отдельный recovery протокол — за последующее выяснение неопределённого исхода.

Физический guard реализации может остановить исполнение раньше семантического лимита. Такой результат явно помечается ImplementationStop и не сравнивается как нормальный программный исход. Опубликованные платформенные ограничения должны позволять оценить, для какого подмножества входов реализация обещает корректное завершение семантической машины.

### 5.2. Что именно сравнивает свидетельство

Claim о равенстве обязан указывать observation domain:

```text
ObservationDomain = (profile_revision, visible_values, visible_errors,
                     effect_trace_fields, budget_policy,
                     cancellation_policy, settlement_fields)
```

Это перечень обязательных измерений контракта, а не готовая wire schema. Нельзя опускать измерение и интерпретировать отсутствие как «всё равно».

- OBS/R03 сравнивают value/error/declared effect trace в собственной фиксированной семантике, включая prefix effects до modeled terminal error. Их результаты не включают host guard failure и не определяют общую V1-семантику budget/cancellation/settlement.
- Анализирующая нормализация, которая не меняет исполняемый AST и заявляет только соответствующий claim профиля, сохраняет эту ограниченную область применения.
- Оптимизирующее преобразование исполняемого V1-кода должно сохранять заявленные logical charges и наблюдаемые точки либо иметь отдельное достаточное основание для соответствующего observation domain. Равенства результата на неограниченном вычислении для этого недостаточно.
- Если нужное измерение не покрыто методом, применимость свидетельства к более широкому claim — UNKNOWN/не установлена. Повышение profile revision не переносит доказательство автоматически.

Например, удаление промежуточного узла может сохранить значение и trace, но сократить число переходов. При одном и том же предельном бюджете исходная программа остановится, а преобразованная вернёт результат. R05 фиксирует запрет скрытой подмены свойства.

**r26 (D76): два уровня соответствия.**
- **L1-TRACE** — значение, ошибки, трасса эффектов, а также точное число шагов и трасса переходов. Нормативен только для эталонной машины.
- **L2-OBS** — значение, Fault, диагностика, трасса эффектов и зафиксированное состояние. Обязателен для всех реализаций.

Семантический бюджет шагов — топливо эталона. В компилируемой реализации его исчерпание — защитный `IMPLEMENTATION_STOP` `RESOURCE_LIMIT`, и он не сравнивается. Поэтому оптимизации проверяются по L2 и дифференциальными тестами, а не сертификатами сохранения шагов R22 (план §B12).

## 6. Эффекты и authority

Эффект — типизированное описание возможного действия. Capability — текущая неподлежаща́я подделке authority для конкретного действия, ресурса и пределов. **В V1 (D81, EFFECTS-1 EFF-11)** capability — выданное хостом право вызвать точку входа и исполнить атомы её ряда, а не значение программы. ResourceRef, EffectSet, тест, successful Evidence, принятое изменение и участие в author_ids не порождают capability.

Сигнатура функции задаёт верхнюю границу эффектов. Для статически известного вызова эффекты вызываемой функции входят в эффекты вызывающей. Для рекурсивной группы вычисляется наименьшая неподвижная точка объединения в конечном домене effect kinds и заявленных resource selectors. Если пользовательское расширение нарушает конечность такого домена, оно требует отдельного профиля; молчаливое неограниченное расширение V1 не допускается.

Динамический выбор ресурса отделён от authority: анализ может получить полный конечный candidate set или UNKNOWN, но runtime всё равно проверяет capability на фактический ресурс. UNKNOWN dependency coverage не означает ни запрета любого runtime действия, ни разрешения считать влияние ограниченным. Сигнатура должна покрывать широкий класс возможного эффекта; неизвестность конкретных зависимостей сохраняется в анализе.

Перед host dispatch проверяется актуальная capability, а не только право на начало долгой сессии. Истёкшее или отозванное полномочие даёт определённый отказ до нового действия. Типизированный ответ adapter проверяется на границе. Ответ вне зарегистрированной схемы — AdapterContractFault; внешние некорректные данные превращаются в обычную ошибку только через объявленный decoder/adapter contract.

Отзыв блокирует будущий dispatch согласно точке проверки; отмена уже авторизованного и отправленного действия этим не обещается. Точная линеаризация revocation относительно dispatch/commit и полномочия на чтение позднего receipt входят в незакрытый capability lifecycle T05/T06. AUTH-модель использует заранее фиксированную ACL и не проверяет гонку её изменения.

Capabilities и HostHandle имеют явно ограниченный lifetime. Закрытие handle идемпотентно в пределах его контракта; использование после закрытия диагностируется. Ни сборка мусора, ни аварийный cleanup не должны обещать отмену уже совершённого внешнего эффекта. Полная таблица ownership/revocation/cleanup обязательна до T06/T13 freeze.

## 7. Журнал и replay

Внешние время, random и host input поступают через объявленные операции. Для воспроизведения журнал содержит exact operation/adapter revision, входную binding, ответ либо Indeterminate, порядок и необходимые semantic boundary refs. Параллельное получение данных host не даёт ему права менять наблюдаемый порядок выбранной V1-машины.

Replay читает зафиксированный журнал. Он не повторяет host calls. Отсутствующая запись, несовпавшая binding, версия адаптера или повреждение журнала дают явную диагностику; обращение к внешнему миру «для заполнения пробела» запрещено. Recovery неопределённого эффекта — отдельная зарегистрированная операция чтения receipt, а не режим replay, который заново исполняет исходное действие.

Замена программы в accepted head не меняет snapshot уже исполняемого экземпляра. Runtime activation, migration и epoch guards имеют отдельный контракт T07/T10. Эта глава не обещает live update.

## 8. Общая долговечная граница

Для локального атомарного действия используется схема:

```text
intent key + exact semantic request
    → read current durable state and current authority
    → find committed receipt before stale attempt guards
    → validate new intent if no receipt
    → atomic compare StateVersion + domain write + outbox + receipt
    → return stored receipt
```

Предварительная проверка формы и текущих прав остаётся до раскрытия старого receipt. Сам receipt возвращается до stale business/version guards: повтор уже выполненной команды не должен превратиться в новую попытку изменения. Точный состав request binding определяется операцией. Per-attempt scheduling guard не обязан быть частью семантического намерения; это явно решено в [AUTH-TX-0.1](../data/authorship-transition.md).

Receipt хранит версию первоначальной фиксации и исторический результат. Текущее чтение отдельно сообщает observed StateVersion. Неизменяемый старый receipt не изображает текущую предметную запись после дальнейших изменений.

Outbox принадлежит той же atomic boundary, что исходное изменение. Projection/index, inbox и receipt обработчика принадлежат одной boundary обработки. Producer ACK — отдельная запись после подтверждённого receipt. Изолированное присутствие одного флага не доказывает согласованность остальных записей.

Отсутствие receipt в одном чтении — ABSENT_AT_READ; оно не означает, что конкурирующая операция никогда не завершится. При недоступном чтении результат UNKNOWN. Retention и смена logical handler identity входят в семантику дедупликации: после удаления ключей прежняя гарантия не действует без отдельного протокола. Профиль AUTH поэтому вообще не удаляет эти записи.

## 9. Условное свойство type safety и необходимые основания

Это **формулировка обязательства, а не предъявленное доказательство**. Для завершённого V1 следует отдельно доказать/проверить:

**Preservation.** Если принят well-formed typed IR типа T с effect bound E, окружение и значения корректно типизированы и выполнены перечисленные предпосылки, каждый разрешённый переход сохраняет типы состояния машины и не производит undeclared effect. Полученное Returned value имеет T.

**Progress with explicit boundaries.** Такое состояние либо терминально по объявленному правилу, либо допускает следующий шаг, либо явно ждёт зарегистрированного host operation. Оно не застревает из-за unbound binding, неприменимого значения вместо функции, неизвестного внутреннего tag или недопустимого доступа к памяти. Это свойство не обещает завершения рекурсии, ответа внешнего сервиса, успеха Result или отсутствия BudgetExceeded.

Предпосылки:

1. Закрыты grammar, typed IR forms, type/effect rules, primitive table и все evaluation transitions; decoder не принимает неизвестные версии и повреждённые значения.
2. Связи и environment well-formed; typed program соответствует exact snapshot. Nominal IDs и capabilities не подделываются через cast или codec.
3. Каждый registered adapter соблюдает заявленный typed ABI, ownership, authority и effect contract. Внешние нарушения обнаруживаются на границе и не маскируются под обычный успех.
4. Runtime выполняет определённые budget/cancellation rules и различает physical implementation failure. Host memory safety и атомарность storage adapter входят в отдельные предпосылки, а не выводятся из проверки чистого выражения.

План обязательств: локальные preservation/progress lemmas на каждую форму IR; согласованность substitution/closure environment; fixed-point effect inclusion; корректность primitive boundaries и decoders; simulation reference machine ↔ backend; отдельные storage/FFI assumptions. Конечные корпуса OBS/CALL/AUTH проверяют примеры и ловят конкретные дефекты, но не доказывают эти квантифицированные утверждения для полного V1.

## 10. Версии и диагностики области

Любой executable artifact объявляет source/IR/profile/adapter revisions. `UNSUPPORTED_FEATURE` сообщает точную feature ID и profile, UnknownForm — неизвестный tag/version, PendingSpecification — отсутствие утверждённого правила в экспериментальной сборке (код выведен из V1, DIAG-1 `retired`). Неизвестная форма не исполняется приблизительно и не понижается в неподдерживаемый host-call без отдельного решения.

Ошибки версии до запуска отличны от domain Result и от UNKNOWN анализа. Опубликованный V1-профиль не может содержать PendingSpecification для обязательной возможности. Текущий design profile может, но тогда остаётся рабочим проектом.

## 11. Проверки, которые должны стать conformance suite

| Проверка | Положительный oracle | Отрицательный oracle |
| --- | --- | --- |
| Strict evaluation | Аргументы исполняются ровно по объявленному порядку | Неиспользуемый параметр не удаляет effect аргумента |
| Branch/short circuit | Исполняется только выбранная ветвь | Ошибка в статическом типе невыбранной ветви всё равно обнаруживается |
| Result | Err передаётся как значение совместимого типа | Runtime не выполняет неявное распространение Err |
| Integer/Text | Одинаковые границы и сравнение на всех target | Host overflow, bool-as-int и повреждённый Unicode не проникают в значения |
| Closure/recursion | Lexical capture и правильный recursive environment | Нет захвата будущей изменяемой ячейки и произвольного head lookup |
| Budget/cancel | Детерминированный порядок stop с сохранённым settlement | UNKNOWN эффекта не превращается в rollback при cancel |
| Evidence domain | Claim применяется только к покрытым наблюдениям | Value/trace witness не выдаётся за cost-preserving compiler proof |
| Replay | Тот же журнал даёт тот же наблюдаемый ход | Missing record не запускает новое внешнее действие |
| Persistability | Data-only значения проходят declared codec | Capability/closure/handle внутри контейнера отвергается |

Все общие проверки этой таблицы имеют статус **NOT_RUN для V1**. Отдельные пересечения с исследовательскими профилями ссылаются на их собственные результаты и сохраняют их область. Они не меняют статус всей строки на PASS.

## 12. Что нужно закрыть следующим

Обязательные открытые решения: opcode schemas T03 (грамматика — [grammar.ebnf](grammar.ebnf), r26); type inference/generic instantiation/comparability T04; полная primitive/error table и cost table T04/T06; exact capability lifecycle/adapter ABI T05/T06/T13; codec/migration/activation/backlog/poison handling T07; закрытый stdlib API и target build contract T13; полный conformance protocol T16. Реальные платформы проверяются исполнением на них, а не предполагаются; прежнего кода для переиспользования нет (D64).

Для каждого решения нужны формы входа/выхода, предусловия, порядок вычисления, ошибки, finite/termination argument, версия, recovery и независимый oracle. Пока этого нет хотя бы для одной обязательной возможности, implementer всё ещё вынужден проектировать часть языка. Процент проработки отражает движение к устранению этих пробелов; эта глава не объявляет ТЗ готовым.
