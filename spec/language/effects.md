# EFFECTS-1 — эффекты, ряды и точки входа

**r26 · контракт V1.** Решения D70, D81, D82, D87 ([07-decisions.md](../architecture/07-decisions.md#решения-r25)). Документ определяет `EffectSet`, которое в TYPES-0.1 было только именем (ledger CL-110).

Эффекты нужны для двух целей:
1. ограничить, что может делать функция;
2. дать **полное по построению** извлечение связей чтения, записи и событий ([links/01](../links/01-records-and-invariants.md)).

Других путей к хранилищу, событиям или внешнему миру в V1 нет: пользовательского FFI нет (D87), динамического выбора таблицы нет (EFF-07). Поэтому покрытие этих рёбер — COMPLETE, а не TOP.

Правила имеют идентификаторы `EFF-nn`.

## 1. Атомы

**EFF-01. Атомы эффектов V1:**

| Атом | Запись в `uses` | Где возникает | Ребро графа |
| --- | --- | --- | --- |
| `reads S.t` | `reads Blog.articles` | `store.get`, `store.all`, `store.contains` и др. по таблице `t` хранилища `S` | `reads` |
| `writes S.t` | `writes Blog.articles` | `store.put`, `store.remove`, `store.replace_all` | `writes` |
| `emits E` | `emits AuthorshipChanged` | `emit E {…}` | `emits` |
| `consumes E` | не пишется | параметр `handler h(ev: E)` | `consumes` |
| `host A.op` | `host clock.now` | вызов зарегистрированного адаптера хоста | `calls` к адаптеру |

`writes` не включает `reads`: изменение по прочитанному значению требует обоих атомов. Атомы сравниваются по EntityId таблицы, события или адаптера, а не по имени. Переименование не меняет ряд.

**EFF-02. Адаптеры хоста.** Реестр адаптеров V1 пуст: часов, случайности, сети и файлов нет. Атом `host` с незарегистрированным адаптером → `UNKNOWN_HOST_ADAPTER`. Добавление адаптера — отдельное решение с контрактом исхода EffectOutcome ([kernel/outcomes.md](../kernel/outcomes.md)).

## 2. Ряд эффектов

**EFF-03. Ряд** — конечное множество атомов и не более одной эффект-переменной: `uses { reads Blog.people, writes Blog.articles | e }`.
- Пустой ряд — чистая функция; `uses` тогда не пишется.
- Порядок и повторы атомов в записи не значимы. Форматтер сортирует атомы по виду, затем по пути.

**EFF-04. Проверка объявления.** Для функции, точки входа и лямбды с известным ожидаемым типом:

```text
actual(body) = ∪ атомов форм Perform/emit в теле
             ∪ ряд каждого вызова (EFF-05)
             ∪ consumes E для handler
требуется: actual(body) ⊆ declared
```

Иначе → `UNDECLARED_EFFECT` с перечнем лишних атомов и местом первого. Объявление шире фактического допустимо. Такой избыток виден анализатору как граница сверху, но рёбра графа строятся по фактическим местам (EFF-12).

**EFF-05. Ряд вызова.** У вызова `f(args)` с сигнатурой `f<…, !e>(…) uses R` ряд равен `R[e := ρ]`. Подстановка ρ получается по EFF-06. Вызов значения fn-типа `g(x)`, где `g: fn(T) -> U uses R`, вносит R.

Эффекты вычисления самих аргументов входят в ряд вызывающего отдельно, по порядку вычисления.

## 3. Эффект-переменные

**EFF-06. Эффект-переменные ранга 1 (D70).**
- Переменная объявляется в обобщениях функции: `fn map<T, U, !e>(xs: Seq<T>, f: fn(T) -> U uses e) -> Seq<U> uses e`.
- На месте вызова ρ(e) вычисляется так:
  1. **Кандидат.** Возьмите объединение рядов всех аргументов, чьи формальные fn-типы упоминают e. Ряд лямбды-аргумента — фактический ряд её тела; ряд выражения fn-типа (переменной, поля, результата вызова) — его тип.
  2. **Выражения, не являющиеся лямбдами.** Их ряд обязан **совпасть** с кандидатом: подтипизации fn-значений нет. Иначе → `TYPE_MISMATCH` с обоими рядами.
  3. **Лямбды-литералы** расширяются до кандидата, это правило включения EFF-04. Итоговый тип каждой лямбды — fn-тип с рядом ρ(e).
- Если e не встречается ни в одном параметре, ρ(e) = ∅.
- Неизвестное имя эффект-переменной в ряде → `UNKNOWN_EFFECT_VARIABLE`.
- Внутри тела обобщённой функции e — непрозрачный атом. Тело не может делать с ним ничего, кроме передачи дальше.

Подтипизации fn-типов нет. Переменная fn-типа `fn(T) -> U uses {reads X}` принимает только значения ровно с этим рядом. Лямбда проверяется против ожидаемого ряда по включению «фактический ⊆ ожидаемого» и получает ожидаемый ряд как тип.

Пример:

```bagaev
use std.seq
fn titles(ids: Seq<ArticleId>) -> Seq<String> uses { reads Blog.articles } {
  seq.map(ids, fn(id) => title_of(id))      // ρ(e) = { reads Blog.articles }
}
```

**EFF-07. Таблица — статический аргумент.**
- Функции `std.store` принимают таблицу параметром особого вида `Table<K, V>`, а их ряд ссылается на этот параметр: `fn get<K: Key, V>(t: Table<K, V>, k: K) -> Option<V> uses { reads t }`.
- Аргумент обязан быть путём к таблице (`Blog.articles`), а не вычисленным значением (`TABLE_REF_NOT_STATIC`). В ряд вызывающего подставляется конкретная таблица.
- Параметры вида `Table` разрешены только в `std.store`; в пользовательском коде → `TABLE_PARAM_ONLY_IN_STD`. Значения вида `Table` нельзя хранить в переменных, полях и коллекциях.

## 4. Хранилище, события и точки входа

**EFF-08. Контекст выполнения.** Атомы `reads`, `writes`, `emits` исполнимы только внутри транзакции, которую открывает хост для точки входа. Функция `fn` с такими атомами разрешена, но её можно вызвать только из точки входа, чей ряд их покрывает. Исполнение вне транзакции, например `bag run` чистой функции с `reads`, → `HOST_EFFECT_OUTSIDE_TRANSACTION`.

**EFF-09. Точки входа и допустимые атомы:**

| Объявление | Допустимые атомы | Транзакция (D46, D81) |
| --- | --- | --- |
| `command` | reads, writes, emits | Одна транзакция. `Ok` фиксирует записи, события в outbox и receipt. `Err` не меняет данных и событий, но фиксирует квитанцию отказа (r31, HST-06); Fault ничего не меняет. Повтор с тем же ключом идемпотентности возвращает прежний receipt (ядро R16) |
| `query` | reads | Чтение согласованного снимка; записи и события → `EFFECT_NOT_ALLOWED_IN_CONTEXT` |
| `handler h(ev: E)` | reads, writes, emits; `consumes E` неявно входит и в фактический, и в объявленный ряд | Одна транзакция. Изменения и запись в inbox фиксируются вместе. Повтор доставки события с тем же ID возвращает сохранённый исход и не повторяет работу (O07, C13). Fault ничего не меняет, событие остаётся недоставленным и видимым |
| `migration` | нет | Чистое преобразование одной записи. Хост применяет его ко всей таблице при остановленных писателях (D10) |
| `test` | любые объявленные | Исполняется на отдельном пустом хранилище, привязанном к схеме программы (HST-18) |

**EFF-10. `emit`.** Создаёт событие в outbox текущей транзакции. Оно станет видно обработчикам только после фиксации. Отменённая транзакция событий не производит. Полезная нагрузка — полный снимок (D45).

**EFF-11. Полномочия (D81).** В V1 нет значений-capabilities.
- Хост выдаёт право вызывать точку входа по своей политике (кто может вызвать какой command).
- При каждом Perform хост проверяет, что атом входит в ряд вызванной точки входа. Иначе → `ACCESS_DENIED`; это защита реализации, проверенная программа сюда не попадает.
- Права предметной области, например «кто редактор», — обычные данные приложения (O06). Участие в авторстве их не даёт.
- Прежние типы `ReadCap`/`WriteCap` из STDLIB-TYPES-0.1 заменяются этим правилом при встраивании stdlib (Ф3–Ф4).

## 5. Связи, которые дают эффекты

**EFF-12. Извлечение (D82).** Каждое фактическое место атома в теле даёт ребро от объявления-владельца:

| Место | Ребро |
| --- | --- |
| вызов std-функции хранилища | `reads` / `writes` к таблице |
| `emit` | `emits` к событию |
| параметр handler | `consumes` к событию |
| вызов | `calls` к вызываемой декларации |

У каждого ребра site = nid и диапазон. Объявленный, но не используемый атом даёт запись «объявленная граница без места». Это не ребро. Для функций с эффект-переменной ребро строится на месте вызова по подстановке ρ.

**EFF-13. Полнота.** Покрытие рёбер `reads`, `writes`, `emits`, `consumes` для программы V1 — COMPLETE. Обоснование:
- таблицы статичны (EFF-07);
- FFI нет (D87);
- эффект-переменные подставляются на каждом месте вызова (EFF-06).

Это условие для сертификата невлияния D83(b). Если появится механизм, нарушающий эти предпосылки, соответствующие рёбра получат PARTIAL/TOP.

## 6. Что здесь заменяется

- Отличие от TYPES-0.1 §1.6: там эффекты были закрытыми множествами без полиморфизма. Эффект-переменные добавлены, а `map_pure` и `fold_pure` STDLIB-API-0.1 заменяются обобщёнными `map` и `fold` (ledger CL-115, Ф3).
- Отличие от STD-SERVICE-0.1: там был один агрегат на транзакцию. Его заменяют эффекты по таблицам (CL-112, Ф4).
- `Capability` и `HostHandle` не являются типами пользовательской программы V1 (EFF-11). В таблицах предикатов TYPES/DATA их строки сохраняются для будущих профилей.
