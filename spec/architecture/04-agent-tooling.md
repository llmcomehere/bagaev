# Инструменты, агентный протокол и продолжение работы

**Рабочий архитектурный проект · 21 октября 2026.** Основа задач T11–T14. Схемы, состояния и имена операций ниже предлагаются для согласования; это не описание существующей CLI или утверждённый протокол. Существующей CLI нет (D64); схемы реализуются в эталоне, T16 фиксирует нормативную версию.

Назначение инструментов — проводить человека и модель через точные операции над программой, сохраняя условия изменения независимо от разговора. Общие понятия заданы в [модели программы](01-program-model.md), допустимое исполнение — в [языке и runtime](02-language-runtime.md), приёмка — в [алгоритмах изменения](03-change-algorithms.md). Порядок разработки: [ROADMAP](../../registry/PLAN.md); состояние: [PROGRESS](../../docs/verification.md).

## 1. Единое семантическое ядро инструментов

CLI, редактор и агентный интерфейс используют общие библиотеки разрешения ссылок, проверки типов, построения связей и проверки применимости свидетельств. Адаптер не определяет альтернативную семантику языка. Каждый результат содержит версию инструмента, профиль и ссылки на точные входы.

| Компонент | Ответственность | Граница |
|---|---|---|
| Компилятор | Разбор, разрешение ссылок, типы и эффекты, проверенный IR, выбранный backend | Не подтверждает человеческое намерение одним фактом успешной компиляции |
| Сборка и пакеты | Замкнутый набор зависимостей, lockfile, артефакты и их происхождение | Разрешение пакета не исполняет его установочные сценарии без отдельной операции |
| Форматирование и структурный редактор | Преобразования исходника с определённым сохранением ID, комментариев и смысла | Удаление и перенос сущностей проходят правила идентичности |
| Сервис связей | Прямые и обратные запросы, происхождение фактов, область покрытия | Отсутствие найденного ребра не объявляется отсутствием зависимости |
| Сервис изменений | Кандидат, обязательства, влияние, проверки, последовательное принятие | Принятие версии проекта отделено от развёртывания и миграции действующих данных |
| Редактор и LSP-адаптер | Диагностика, навигация, предложения действий, ссылки на обязательства | Версия транспортного стандарта выбирается T14; смысл действий задаёт общий протокол |
| Отладчик и трассировка | Входы, исполненная версия, состояние запуска, причинные события | Трасса одного исполнения не заменяет утверждения обо всех исполнениях |
| Читаемое представление программы | Объяснение сущностей, контрактов, версий и последствий для человека | Пересказ сохраняет ссылки и статус оснований, не повышая силу утверждения |

Рабочие семейства команд: `inspect`, `search`, `change begin/apply/impact/verify/accept`, `context build`, `work resume`, `build`, `run`, `format`, `package`, `trace`. Окончательные флаги, коды выхода и форматы потоков фиксируются T12–T14. Чтение и поиск не запускают приложение, миграции, установочные действия или произвольные команды из найденного текста.

## 2. Общая форма запроса и ответа

Транспорт сначала устанавливает действующего субъекта и его полномочия. Поле, присланное моделью, не может назначить ей другую роль. Протокол не зависит от поставщика модели; транспортный адаптер переводит вызовы в одну семантическую операцию.

| Поле запроса | Тип и назначение |
|---|---|
| `protocol_version`, `operation` | Версия схемы и имя операции |
| `request_id` | Идентификатор попытки доставки; не ключ идемпотентности |
| `project_id`, `target` | Проект и ровно одна выбранная цель: `snapshot_id` либо `change_id` |
| `expected_work_revision` | Обязательный guard для изменения рабочего состояния |
| `idempotency_key` | Ключ повторения одной операции записи в области проекта, субъекта и изменения |
| `arguments` | Типизированные параметры; ссылки на сущности включают требуемую ревизию |
| `limits` | Бюджет контекста, времени, раскрытия и ресурсов; отсутствие поля не означает бесконечность |

Ответ содержит `request_id`, `operation_status`, `resolved_snapshot_id`, `work_revision`, `result` либо типизированную `error`, а также созданные ссылки на основания и продолжение. `operation_status` принимает `succeeded`, `pending`, `blocked`, `failed`, `unknown_outcome`. Для длительной проверки `pending` содержит устойчивый `job_id` и операцию чтения результата. Успех команды `apply` означает сохранение кандидата, а не готовность всей задачи.

Ошибки имеют `code`, безопасное объяснение, точные разрешённые ссылки, `retry_policy` и требуемое действие. Минимальные коды: `INVALID_REQUEST`, `UNSUPPORTED_PROFILE`, `ACCESS_DENIED`, `STALE_BASE`, `WORK_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `AMBIGUOUS_INTENT`, `INSUFFICIENT_CONTEXT`, `OPEN_OBLIGATIONS`, `UNKNOWN_EFFECT_OUTCOME`, `CORRUPT_CHECKPOINT`. Неизвестная версия операции отклоняется явно. Машинное значение `retry_policy` различает безопасное повторное чтение, повтор с тем же ключом и необходимость нового решения.

## 3. Операции над проектом

| Операция | Результат и существенное условие |
|---|---|
| `inspect` | Выбранная сущность, контракт, связи и происхождение на указанной версии |
| `search` | Ранжированные кандидаты намерения с объяснением; выбор не становится фактом автоматически |
| `expand` | Разрешённые подробности ссылки; отказ сохраняет видимый пробел в пределах политики доступа |
| `beginChange` | Новый `ChangeId`, исходный snapshot и контракт изменения: сохраняемое, изменяемое, новое |
| `apply` | Атомарный набор структурных правок и новый кандидат; обновление извлекаемых связей |
| `impact` | Затронутые обязательства, границы исключения, неизвестные участки и основания пересмотра |
| `verify` | Задание проверок, их условия и append-only свидетельства; профиль исполнения проверяется отдельно |
| `accept` | `AcceptanceRecord` и CAS-переход принятой версии после выполнения политики приёмки |
| `continue` | Восстановленное рабочее состояние и следующий допустимый пакет контекста |

`apply` не может незаметно включать изменение требований: операция пересмотра контракта указывает основание и допустимую область. Если задача уже разрешает такой пересмотр, отдельное подтверждение каждого технического шага не требуется. Авторство человека в данных приложения не предоставляет ему полномочий редактора проекта.

Для `accept` arguments закрепляют base/candidate IDs, ревизии ChangeContract и политики. Вместе с `expected_work_revision` они проверяются внутри той же атомарной операции, что меняет принятый head. Совпадения одного head недостаточно: рабочий кандидат или обязательства могли измениться. Действующее полномочие также проверяется в момент записи; результат конфликта не публикует частичного принятия.

Snapshot — неизменяемый манифест кода, контрактов, графа, схем и зависимостей. Новое свидетельство проверки добавляется отдельно и не меняет `SnapshotId`. `AcceptanceRecord` связывает принимаемый snapshot, контракт изменения, выбранные свидетельства и политику. Конкретное состояние приложения обозначается отдельными `RuntimeInstance` и `StateVersion`.

## 4. Что сохраняется вне разговора

`WorkState` содержит `ChangeId`, исходный и кандидатный snapshots, ревизию контракта изменения, корневые обязательства, текущие задачи, открытые вопросы, ссылки на проверки, границы исключения, незавершённые jobs и receipts. Изменяемое рабочее состояние имеет собственный `work_revision`; это не ревизия программы.

Журнал операций и контрольная точка позволяют восстановить состояние без пересказа чата. Для каждого обязательства хранится состояние `open`, `supported`, `contradicted` либо `excluded_with_basis`. `supported` означает наличие основания требуемого класса в заданных условиях, а не универсальное доказательство. Исторические свидетельства неизменяемы; их применимость к кандидату вычисляется заново.

WorkState хранит ссылки на `EvidenceAssessment` из A03: целевой snapshot, точный query/scope, политика, `integrity`, `applicability`, `sufficiency` и исходный `verdict`. Для `supported` и `excluded_with_basis` требуется положительный `supports(assessment)`; применимый `fail` сохраняет противоречие. Статус команды, статус обязательства и статус применимости — разные поля. Перенос исторического evidence не меняет его `subject_snapshot_id`: новая оценка закрепляет его допустимое использование для данного кандидата.

Рабочая заметка модели может храниться как объяснение решения. Она не заменяет контракт, параметры команды, факт исполнения или основание исключения. По завершении шага новое состояние и его receipt записываются вместе; смена модели меняет исполнителя, но не правила проекта.

## 5. Поиск намерения и построение контекста

Поиск использует назначения, предметные понятия, примеры и точные связи. Оценка сходства служит порядком рассмотрения. Существенный выбор фиксируется с основаниями: какое свойство запроса соответствует какому обязательству. «Добавить соавторов» может касаться атрибуции или совместного редактирования; это различие должно попасть в выбор цели, если контекст задачи его не разрешает.

`ContextPack` содержит цель шага, ревизию контракта изменения, обязательные условия, выбранные интерфейсы и реализации, ссылки на свидетельства/assessments, предположения, исключённые участки с основаниями и способ продолжения. Отдельно сохраняются область и статус анализа, его `analysis_frontier/gaps/unknown`, а также `context_frontier` ещё не раскрытых представлений. Скрытая недоступная зависимость описывается только в объёме, разрешённом политикой; её недоступность не превращается в разрешение считать обязательство выполненным.

### Алгоритм boundedContext

Вход: `ChangeId`, ревизия работы, цель шага, бюджет, версия измерителя размера, область доступа. Выход: пакет `ready_for_step` либо сохранённый пакет `incomplete` с причиной и продолжением. Готовность пакета относится к заявленному шагу и покрытию модели, не к полноте проекта.

```text
boundedContext(change, workRevision, step, budget, access):
  state := readExactWorkState(change, workRevision)
  roots := mandatoryEnvelope(state, step)
  if size(roots) > budget:
      return persistIncomplete(roots.refs, reason=MANDATORY_ENVELOPE_TOO_LARGE)
  impact := analyzeImpact(state, step)
  pack := roots
  stepImpact := projectAnalysisToStep(impact, step)
  retainAnalysisStatusAndScope(pack, impact.ref, stepImpact.scope,
                              stepImpact.completeness)
  retainAnalysisFrontierGapsAndUnknown(pack, stepImpact, access)
  if size(pack) > budget:
      return persistIncompleteWithAnalysisRefs(pack,
                         reason=MANDATORY_ENVELOPE_TOO_LARGE)
  if not stepImpact.coverageForStepEstablished:
      addBlocker(pack, ANALYSIS_SCOPE_INCOMPLETE)
  frontier := stableOrder(stepImpact.requiredItems)
  while frontier has items:
      item := pop(frontier)
      if validBoundary(item, state, access):
          addBoundaryOrMarkIncomplete(pack, item, budget)
      else if canRead(item, access) and fits(item, pack, budget):
          addExactRepresentation(pack, item)
          enqueueNewRequiredItems(frontier, item)
      else:
          retainUnresolvedFrontier(pack, item)
  return persistPack(pack, statusForRequestedStepIncludingAnalysis(pack))
```

Порядок стабилен при одинаковых входах; версия ранжирования сохраняется. Важность не позволяет вытеснить обязательное условие. Очередь устраняет повторные посещения; циклическая группа раскрывается совместно либо остаётся нерешённой. Превышение бюджета не закрывает frontier. Возможные следующие действия — обоснованное разбиение шага, продолжение анализа, раскрытие деталей следующим запросом или явное изменение бюджета в допустимых пределах.

`projectAnalysisToStep` может отнести пробел к другому шагу только с сохранённым основанием границы. Если не установлено, затрагивает ли незавершённый анализ текущий шаг, пробел блокирует его готовность. Даже при пустом `requiredItems` неполнота анализа сохраняется. Простое включение исходника в пакет не закрывает `analysis_frontier`: нужен продолженный анализ. Метаданные анализа также учитываются в бюджете; при переполнении сохраняется полный незавершённый пакет, а ответ даёт ограниченные точные ссылки без объявления готовности. Недоступные детали сохраняются как разрешённый политикой блокер, без раскрытия закрытых сведений.

`ready_for_step` разрешён, когда достаточность области анализа для выбранного шага установлена, обязательные сведения раскрыты либо заменены допустимым контрактом с действительным основанием, и нет блокирующих пробелов анализа или раскрытия для этого шага. Общий реестр обязательств остаётся целиком в `WorkState`, а пакет содержит его точную ссылку и относящиеся к шагу записи. Незавершённые обязательства других шагов не исчезают и проверяются при общей приёмке. Готовность пакета не означает выполнения самих обязательств.

Минимальная оболочка может оказаться слишком большой. Тогда возвращаются точные ссылки и незавершённое состояние, а не усечённая версия требований. Контрпример: пакет показывает редактор и сохранение, но скрывает обязательство экспорта ради лимита токенов. Такой пакет не допускает приёмку изменения авторства.

## 6. Продолжение после смены исполнителя

### Алгоритм resume

Вход: `ChangeId`, выбранная контрольная точка, действующий субъект. Выход: согласованное рабочее состояние, актуальные ограничения и следующий пакет либо явный отказ.

```text
resume(change, checkpoint, principal):
  authorizeRead(principal, change)
  state, expectedWorkRevision, expectedJournalHead :=
      restoreCheckpointAndJournal(change, checkpoint)
  verifyManifestReferencesAndJournalOrder(state)
  requireSupportedVersions(state)
  refreshAssessmentsForExactQueries(state.candidate, state.obligations,
                                   state.evidenceRefs, state.policyRef)
  refreshBoundaryValidityAndObligationStatuses(state)
  jobs := readKnownJobAndEffectReceipts(state.pending)
  markUnknownOutcomesWithoutReplayingEffects(jobs)
  if acceptedHead != state.baseSnapshot:
      markNeedsRebaseForAcceptance(state)
  if derivedWorkStateChanged(state):
      if not mayRefreshWorkState(principal, change):
          return readOnlyResumeView(state, persisted=false)
      transaction:
          recheckCurrentRefreshAuthorization(principal, change)
          requireWorkRevisionAndJournalHead(expectedWorkRevision,
                                            expectedJournalHead)
          persistDerivedWorkStateAndReceiptAtomically(state)
  return nextPermittedContext(state, currentAccess(principal))
```

Восстановление журнала воспроизводит записи о работе, а не выполняет заново команды приложения. При изменившейся рабочей ревизии или новой записи журнала финальная запись resume даёт `WORK_CONFLICT` либо повторяет чтение в пределах заданного бюджета; устаревший результат не затирает новую работу. Выбранная старая контрольная точка дочитывается до согласованного текущего journal head. Просмотр исторической точки без этого дочитывания остаётся режимом чтения и не обновляет текущий WorkState.

Обновление производных статусов требует отдельного действующего полномочия записи; право чтения допускает только неперсистентный просмотр. Повреждённая ссылка или неподдерживаемая схема ведёт к отказу восстановления с диагностикой, сохраняя доступное чтение для разбора. Смена принятой версии не уничтожает кандидат: работа в ветке может продолжаться, но приёмка потребует явного пересмотра относительно новой базы. Финальный accept всегда повторяет собственные guards независимо от ранее выданного пакета.

Контрпримеры: после перерыва принять старый вывод «экспорт не затронут» без проверки предпосылок; повторно отправить письмо, поскольку его ответ не сохранён; автоматически перенести изменения поверх новой базы и оставить прежние результаты проверок. Все три случая должны иметь отдельную диагностику и путь продолжения.

## 7. Повтор операции и потерянный ответ

### Алгоритм idempotentWrite

Применим к локальной атомарной структурной правке, а не к произвольному внешнему эффекту. Хеш запроса включает семантические параметры, ожидаемую ревизию, цель и версию операции; транспортный `request_id` исключается. Область ключа включает проект, субъекта и изменение.

```text
idempotentWrite(request, principal):
  key := scopedKey(principal, request.project, request.change, request.key)
  digest := canonicalSemanticRequestHash(request)
  old := readOperationRecord(key)
  if old exists:
      requireSameDigest(old, digest)
      authorizeReceiptRead(principal, old)
      return storedReceiptOrPending(old)
  authorizeWrite(principal, request)
  transaction:
      recheckKeyGuardsAndCurrentAuthorization(key, request, principal)
      result := performLocalStructuralOperation(request)
      persistCandidateWorkStateAndReceiptAtomically(key, digest, result)
  return result.receipt
```

Параллельный повтор сериализуется по ключу. Тот же ключ с другими параметрами даёт `IDEMPOTENCY_CONFLICT`. Для уже совершённой операции устаревшая исходная ревизия не вызывает повторного исполнения: возвращается прежний receipt с текущими ограничениями чтения. После утраты полномочий старый ключ не даёт права выполнить новую операцию.

Внешние действия используют отдельные intent/receipt и правила адаптера. Если невозможно установить, произошло ли действие, сохраняется `unknown_outcome`; повтор допускается только по определённой политике идемпотентности или после разрешения неопределённости. Принятие проекта выполняет CAS по принятому head и записывает `AcceptanceRecord` атомарно. Развёртывание, миграция и отправка сообщений остаются отдельными операциями.

## 8. Условия готовности спецификации инструментов

T11–T14 должны зафиксировать схемы запросов и ошибок, конечные автоматы работы и jobs, правила доступа, формат журнала, пределы хранения ключей, алгоритм восстановления, формат пакета контекста и совместимость версий. Удаление старого ключа не должно делать неизвестный повтор безопасным: политика хранения и область гарантии объявляются явно.

Приёмочные сценарии включают конфликт двух кандидатов, повтор после потери ответа, недоступную обязательную зависимость, переполнение контекста, смену предпосылки исключения и продолжение другой моделью. [Эксперимент авторства](05-authorship-experiment.md) проверяет эти механизмы в совместной работе. Перед заморозкой требуется согласовать транзакционное хранилище журнала, схему авторизации, конкретный транспорт, измеритель бюджета и режим отмены jobs; отсутствие решения отмечается блокером соответствующей задачи.
