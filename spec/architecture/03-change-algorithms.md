# Алгоритмы изменения и действительности знания

**Рабочий проект для T08–T12.** Алгоритмы задают проверяемые обязательства будущей реализации; они ещё не являются доказанными свойствами существующего bagaev. Имена записей согласуются с [моделью программы](01-program-model.md), интерфейсы — с [протоколом инструментов](04-agent-tooling.md).

## 1. Предмет принятия

Принимается неизменяемый `Snapshot` вместе с `AcceptanceRecord`. Название `ProgramSnapshot`, если встречается в описании алгоритма, является синонимом той же записи, а не отдельным видом версии. Snapshot содержит версии кода, контрактов, схем, структурного графа и зависимостей. Свидетельства хранятся отдельно: добавление проверки не меняет идентификатор snapshot. Записи графа ссылаются на идентификаторы и ревизии предметов, а не включают собственный будущий SnapshotId в хешируемое содержимое.

Состояние работающего приложения, выполнение миграции и внешние эффекты имеют отдельные версии и разрешения. Принять исходник не означает запустить его, развернуть сервис или изменить пользовательские данные.

### Минимальный ChangeContract

| Поле | Содержание |
| --- | --- |
| `change_id`, `change_contract_revision`, `base_snapshot_id` | Идентичность работы, точная ревизия её контракта и исходная версия программы |
| `intent_ref`, `selected_entities` | Исходный запрос, выбор сущностей и основания выбора |
| `allowed_changes` | Какие свойства, интерфейсы и данные разрешено изменить |
| `preserved`, `added`, `replaced` | Сохраняемые обязательства, новые обязательства и явные замены старых |
| `transition_obligations` | Старые данные, потребители, незавершённые операции и нужный переход; для каждого пункта — стадия `program_acceptance` или `runtime_activation` |
| `scope`, `profile`, `coverage_refs` | Поддерживаемая область анализа и известные непокрытые границы |
| `accepted_assumptions` | Явные предположения и источники полномочий на их принятие |
| `verification_policy_ref` | Какие виды оснований достаточны для каждого вида обязательства |
| `budget`, `continuation_ref` | Ограничения одного шага и сохранённое продолжение |

`replaced` не удаляет историю. Каждая замена указывает старое обязательство, новую формулировку, причину и её связь с разрешённой задачей. Политика проверки не может автоматически ослабляться для получения успешного результата. Стадия обязательства задаётся контрактом изменения; перенос обязательного пункта на более позднюю стадию является изменением контракта, а не способом автоматически получить приёмку.

## 2. A01 Построение кандидата

**Вход:** base snapshot, структурные операции, ChangeContract, профиль языка. **Выход:** candidate snapshot либо диагностируемый отказ без частичной публикации.

1. Проверить доступ к предметам и совпадение базовых ревизий операций.
2. Применить операции к изолированному кандидату; сохранять историю entity ID и точные места изменённого исходника.
3. Выполнить разбор, разрешение ссылок и проверку типов/эффектов в заявленном профиле. Неподдерживаемая конструкция создаёт диагностику; её нельзя молча считать безопасной.
4. Пересчитать извлекаемые связи для затронутых единиц и их необходимого окружения. Сохранить старые связи для сравнения.
5. Вычислить различия: добавления, удаления, изменения контрактов, эффектов, схем, событий и объявленных предположений.
6. Сопоставить фактические изменения с `allowed_changes`. Выход за область требует отдельного решения или возврата к задаче.
7. Записать неизменяемый candidate manifest и вернуть его ID, диагностики и начальный набор последствий.

**Ошибки:** `BASE_MISMATCH`, `UNRESOLVED_REFERENCE`, `UNSUPPORTED_FEATURE`, `TYPE_OR_EFFECT_ERROR`, `SCOPE_EXCEEDED`. Сохранение незавершённого черновика допустимо, но оно не даёт статуса готовности к принятию.

## 3. A02 Область влияния

**Вход:** base, candidate, их структурные графы, ChangeContract, правила зависимостей, реестр оснований. **Выход:** `ImpactReport`: затронутые обязательства, исключения с основаниями, открытая граница, пробелы покрытия и статус полноты в заявленной области.

Используется объединение старого и нового графов. Иначе удалённая зависимость может исчезнуть из анализа раньше, чем будут рассмотрены её прежние потребители.

```text
analyzeImpact(base, candidate, change, policy):
    graph := unionWithVersionTags(base.graph, candidate.graph)
    queue := seeds(diff(base, candidate), change.transition_obligations)
    visited := empty set of (subject, obligation, changed_facet)
    report := mandatory obligations + explicit coverage gaps

    while queue is not empty:
        if analysis budget exhausted:
            persist(queue, report)
            return INCOMPLETE(report, frontier = queue)
        item := pop in deterministic order
        if item already visited: continue
        add item to visited
        for relevant relation in graph around item:
            rule := ruleFor(relation.kind, item.changed_facet)
            if rule unsupported or coverage insufficient:
                record UNKNOWN with cause and follow-up
                continue
            boundary := tryBoundaryCertificate(relation, candidate, policy)
            assessment := assessBoundaryForQuery(boundary, candidate,
                             obligationQuery(item), policy)
            if supports(assessment):
                record EXCLUDED with exact boundary, assessment and premises
            else:
                record obligation as IN_SCOPE
                enqueue(rule.successors(item, relation))

    return report with COMPLETE_IN_DECLARED_SCOPE only
           when no required frontier or coverage gap remains
```

Завершённый обход известного графа не доказывает полноты самого графа. Полнота отчёта всегда содержит профиль, инвентаризацию границ и предположения. Изолированная неизвестная зависимость закрывается только отдельным основанием изоляции, допустимым политикой.

### Правила отношений

| Отношение | Когда распространяется пересмотр | Какое основание может остановить его |
| --- | --- | --- |
| `calls` | Изменены требуемые результат, ошибки, эффекты, порядок или ресурсное обещание | Применимое подтверждение сохранения конкретного используемого контракта |
| `reads` / `writes` | Изменены представление, ограничения, порядок обновления или наблюдаемые значения | Подтверждённое соответствие старого и нового интерфейса данным; отсутствие нужного эффекта |
| `consumes` | Изменены payload, смысл, повторность, порядок или версия события | Совместимость ровно тех гарантий, которые использует потребитель |
| `requires` | Свойство изменено, заменено либо потеряло действующее основание | Проверка нужного свойства по принятой политике, а не совпадение сигнатур |
| `implements` | Изменена реализация или формулировка обязательства | Новое соответствие реализации обязательству |
| `checks` | Изменены предмет, данные, предпосылки, проверяющий инструмент или политика достаточности | Применимость прежнего свидетельства либо новый запуск |
| `derived_from` | Изменён источник вычисляемого представления | Проверка корректного обновления/перестроения проекции |

Это таблица требуемого поведения. Имена отношений соответствуют записи `Edge` из модели программы; событие или требуемое свойство уточняется типом конца и qualifiers. `assessBoundaryForQuery` использует A03 с точным обязательством и требуемыми условиями исполнения. Отсутствующее основание не проходит `supports`. T09 должен определить точные правила для каждой поддерживаемой операции, классификацию изменённых аспектов и случаи консервативного расширения.

### Циклы и стоимость

Циклически связанные компоненты рассматриваются как группы: обход использует множество посещённых предметов/обязательств/аспектов и, при необходимости, компоненты сильной связности. Расширение множества затронутого монотонно в пределах одного прохода. Новое основание пересчитывается в следующем проходе; оно не должно незаметно отменять ранее найденное обязательство.

При фиксированном конечном наборе аспектов сам обход ограничен размером графа и числом применений правил. Стоимость проверок свойств учитывается отдельно и может быть значительно выше. Тайм-аут анализатора даёт неизвестное, а не отрицательный ответ о влиянии.

## 4. A03 Применимость свидетельств

Свидетельство содержит предмет утверждения, точные входы, версии реализации/контракта/инструмента, конфигурацию, зависимости, предположения, область сценариев и результат. Оно не переписывается при появлении кандидата. Отдельная неизменяемая `EvidenceAssessment` оценивает его относительно **конкретного вопроса**, целевого snapshot и политики; хранится вне snapshot, как и свидетельства.

| Поля EvidenceAssessment | Смысл и допустимые значения |
| --- | --- |
| `assessment_id`, `evidence_refs[]`, `target_snapshot_id` | Идентичность оценки, исторические источники и целевая версия |
| `query_ref`, `query_scope`, `runtime_scope`, `policy_ref` | Точное обязательство с ревизией, область входов/условий и точная политика |
| `checked_input_refs[]`, `checked_assumptions[]`, `transfer_basis_refs[]` | Проверенные основания применимости; при переносе — независимые основания сохранения свойства |
| `integrity` | `valid`, `invalid`, `unknown`; целостность, происхождение и допустимость цепочки ссылок |
| `applicability` | `applicable`, `stale`, `out_of_scope`, `unknown` — канонические значения из модели программы |
| `sufficiency` | `sufficient`, `insufficient`, `unknown`; достаточность метода и силы утверждения по политике для данного вопроса |
| `verdict` | Исходный `pass`, `fail`, `inconclusive`, `error`, без повышения его силы |
| `diagnostics[]`, `validity_conditions` | Причины отказа/неопределённости, условия и срок применимости |

```text
applicability(evidence, candidate, query, runtime_scope, policy):
    a := assessment(target=candidate.id, query=query,
                    runtime_scope=runtime_scope, policy=policy.ref,
                    source=evidence.ref, defaults=unknown)
    a.verdict := evidence.verdict
    a.integrity := verifyEvidenceAndAcyclicOrigins(evidence)
    if a.integrity != valid: return persistAssessment(a)
    coverage := recordedClaimCoversQuery(evidence, query, policy)
    if coverage == false:
        return persistAssessment(a with applicability=out_of_scope,
                                 sufficiency=insufficient)
    if coverage == unknown: return persistAssessment(a)
    a.sufficiency := assessMethodAndAssurance(evidence, query, policy)
    if dependency footprint or required inputs are unavailable/incomplete:
        return persistAssessment(a with applicability=unknown)
    if relevant inputs, contract, premises or runtime scope differ
       or a required observation expired:
        basis := checkedPreservationBasis(evidence, candidate, query, policy)
        if basis absent:
            return persistAssessment(a with applicability=stale)
        a.transfer_basis_refs := basis.refs
    if reproducibility conditions for this method are not established:
        return persistAssessment(a with applicability=unknown)
    return persistAssessment(a with applicability=applicable)

supports(a):
    return a exists and a.integrity == valid
           and a.applicability == applicable
           and a.sufficiency == sufficient and a.verdict == pass
```

Сопоставление query проверяет именно нужное свойство, а не только название или собственное утверждение evidence. Свидетельство о сохранении первого автора не закрывает требование сохранить всех соавторов. Более сильное требование или более широкая область допускаются лишь при отдельном допустимом обосновании покрытия; сходства текста недостаточно. `applicable + fail` остаётся отрицательным результатом. Неизвестная личность проверяющего, повреждённый хеш или циклическое основание не маскируются статусом успешного метода.

Неизменность всех значимых входов позволяет повторно использовать результат только при установленных предпосылках воспроизводимости этого метода. Изменение общего SnapshotId само по себе не запрещает перенос: новая assessment фиксирует применимость к целевому кандидату. При изменившемся значимом входе требуется проверенное основание сохранения **этого** свойства либо новая проверка. Исторический `subject_snapshot_id` не переписывается. Основание переноса не может ссылаться на создаваемую assessment как на собственное доказательство; вся цепочка оснований ациклична. Хеш подтверждает байты, но не истинность утверждения.

Для чистой детерминированной проверки и наблюдения внешней системы правила различаются. Истёкшее наблюдение нельзя обновить сменой метки времени: нужен допустимый новый источник или основание сохранения наблюдавшегося свойства. Основания исключения компонентов проходят ту же процедуру: смена шаблона или доступа к данным пересматривает исключение экспорта.

Взаимно ссылающиеся заключения не могут быть единственным основанием друг друга. Для циклической группы нужен самостоятельный допустимый способ проверки, например проверка общего инварианта; иначе группа остаётся открытой.

## 5. A04 План проверок

1. Для каждого обязательного пункта ImpactReport выбрать метод, разрешённый политикой: статическая проверка, доказательство в поддерживаемой логике, сценарный тест, проверка миграции либо явно ограниченное внешнее свидетельство.
2. Сохранить соответствие «обязательство → метод → предмет/входы → ожидаемый результат». Отсутствие метода является открытым условием.
3. Для каждого источника создать assessment к целевому кандидату и обязательству. Повторно использовать достаточные результаты с проверенной применимостью; неподтверждённый перенос требует новой проверки. Применимый отрицательный результат сохраняется как противоречие, а не как успех плана.
4. Отрицательные случаи запускать вместе с положительными. Для соавторства проверить экспорт, берущий только первого человека, и старый индекс, хранящий одного автора.
5. После запусков пересчитать применимость и остающиеся обязательства. Успешный тест ограниченного набора входов не повышается автоматически до универсального свойства.

Запуск теста с эффектами требует отдельного разрешённого окружения и набора возможностей. Разрешение изменять исходник не предоставляет доступ к внешним данным или средствам развёртывания.

## 6. A05 Принятие согласованного результата

**Вход:** ChangeId, `expected_work_revision`, base/candidate IDs, точные ревизии ChangeContract и политики, субъект и ключ идемпотентности. **Предусловия:** candidate типизирован в поддерживаемом профиле; разрешённая область изменения соблюдена; обязательства удовлетворены по политике; нет обязательных неизвестных, незакрытых переходов или исчерпанной границы анализа; доступ к принятию действителен.

Эти предусловия относятся к стадии `program_acceptance`: закрываются корректность преобразования, готовность плана перехода и его проверки в объявленных условиях. Фактическое переключение рабочих данных не требуется для принятия исходника. Обязательства `runtime_activation` сохраняются отдельно и проверяются для конкретной среды/StateVersion перед A07; принятие программы не переводит их в выполненные.

1. Подготовить `AcceptanceRecord`: base/candidate IDs, рабочая ревизия, ChangeContract revision, профиль, policy ref, точные evidence и assessment IDs, принятые предположения, CoverageReport и результаты проверки.
2. Для каждого обязательного заключения требовать `supports(assessment)` с точным query и целевым candidate. Источники могут принадлежать прежним snapshot, если assessment подтверждает допустимый перенос. Отдельно убедиться, что нет неразрешённого противоречия применимых свидетельств.
3. В одной атомарной операции проверить head против `base_snapshot_id`, ожидаемую рабочую ревизию, текущий candidate, ревизии ChangeContract и политики, отсутствие изменения обязательств и актуальное полномочие субъекта. Проверить ещё действующие условия assessment, включая срок. Только после всех guards сохранить новый head, AcceptanceRecord, новую рабочую ревизию и receipt вместе.
4. При конфликте head вернуть `STALE_BASE`; при конфликте рабочего состояния или закреплённых ревизий — `WORK_CONFLICT`; при утрате полномочия — `ACCESS_DENIED`. Не изменять head. Перечитать работу; при новой базе построить кандидат и повторить анализ изменённых условий. Автоматическое текстовое объединение не является приёмкой.
5. При сбое читать журнал завершения по ключу операции. Уже завершённое принятие возвращает прежний receipt в допустимой области чтения; потеря ответа не создаёт второе принятие.

Политика реализации атомарности выбирается в T10: транзакционная база либо журнал с определёнными фазами восстановления. Нужен доказуемый порядок записи, при котором видимый head не ссылается на отсутствующее решение о принятии.

`accepted` относится к версии программы. Выполнение миграции и активация в среде эксплуатации — отдельные команды с собственными разрешениями, проверками состояния и результатами.

## 7. A06 Совместное изменение и продолжение

Рабочая запись сохраняет цель, ChangeContract, base/candidate, открытые обязательства, frontier, применённые операции и результаты инструментов. Сохранение выполняется на границах команд; завершённые команды имеют устойчивый результат.

При продолжении проверяются доступ, существование предметов, актуальность базы и применимость прежних оснований. Новому исполнителю выдаётся пакет из действующего состояния; текст чата служит пояснением, но не восстанавливает утраченные факты вместо записей.

Две по отдельности корректные правки проверяются совместно после объединения. Например, первая меняет порядок авторов, вторая считает первого человека владельцем. Их композиция может нарушать неизменённые права; прежние локальные успехи этого не исключают.

## 8. A07 Изменение данных и восстановление

Миграция описывает исходную и целевую схему, точную исходную StateVersion, преобразование, инварианты, стратегию повторов, проверку результата, политику накопленных событий и способ восстановления. Для первого профиля используется остановленный переход: после выбранной обработки накопленной работы останавливаются **все писатели мигрируемого состояния**, включая пользовательские операции, обработчики событий и обратные записи адаптеров. Совместная работа старых и новых клиентов не предполагается автоматически.

`ActiveBinding` — отдельная долговечная привязка среды: `binding_id`, `program_snapshot_id`, `state_version`, `schema_revision`, `activation_epoch`, `activation_operation_id`. Принятый head проекта не является этой привязкой. Запуск выбирает код и данные через одну согласованную ActiveBinding; нельзя независимо прочитать старый код и новый указатель данных. Обычная транзакция обновляет корень `state_version` в той же эпохе атомарно с данными и receipt; новая пара кода/схемы получает новую эпоху активации.

1. Зафиксировать ожидаемую ActiveBinding и исходную StateVersion; проверить разрешение перехода и остановку всех писателей.
2. Подготовить результат в изолированной области. Преобразовать/перестроить данные и проекции, проверить ограничения. Подготовка не публикует новые события и внешние действия.
3. Для outbox/inbox, незавершённых операций и dedup-записей применить заранее определённую политику: завершить до остановки, преобразовать с сохранением причинности/дедупликации, поддержать чтение старой схемы либо заблокировать активацию. Молчаливое удаление очереди или сброс ключей запрещены.
4. Атомарно сравнить исходную ActiveBinding, её эпоху и StateVersion с ожидаемыми, вновь проверить полномочие, затем переключить **пару кода и данных** вместе со схемой, новой эпохой и receipt. Конфликт оставляет исходную привязку действующей.
5. После сбоя восстановить выбранную пару по журналу операции; незавершённая подготовка не становится активной. После состоявшейся активации с потерянным ответом вернуть сохранённый receipt, не выполнять преобразование заново. Обработку возобновлять только после подтверждения согласованной пары.

Если движок не поддерживает единую транзакцию переключения, T07 обязан определить журнал и фазы восстановления с тем же наблюдаемым результатом. Не допускается окно, в котором приложение обслуживает операции на смешанной паре. При невозможности такой гарантии адаптер не входит в V1.

Откат версии программы не означает автоматический обратный переход данных. Необратимая миграция требует заранее выбранного восстановления из снимка либо компенсирующего перехода. Неизвестный результат внешнего действия хранится как неизвестный, пока не получена проверка его фактического состояния.

## 9. Минимальные отрицательные проверки механизма

| Случай | Обязательный результат |
| --- | --- |
| Удалили связь с экспортом вместе с изменением модели авторства | Старый граф возвращает прежнего потребителя в анализ |
| Результат другого candidate использован без assessment допустимого переноса | Принятие блокируется; требуется оценка применимости либо новая проверка |
| Свидетельство о первом авторе предлагается для требования о всех соавторах | `out_of_scope` или недостаточность; положительный verdict не закрывает требование |
| Применимый тест завершился `fail` | Обязательство противоречиво, не выполнено |
| Новый шаблон читает имя автора в ранее исключённом модуле | Прежнее исключение отменяется, появляется обязательство |
| Анализ исчерпал бюджет | Frontier сохранён; принятие не разрешено |
| Конфликтующий head появился перед принятием | `STALE_BASE`, без изменения head и повторного внешнего эффекта |
| Рабочая ревизия или контракт изменились при неизменном head | `WORK_CONFLICT`, без принятия прежней работы |
| Подготовка миграции закончена, но переключение ещё не записано | После сбоя активна прежняя пара кода и данных |
| Активация зафиксирована, но ответ потерян | Чтение receipt подтверждает новую пару; миграция не повторяется |
| После подготовки исходная StateVersion изменилась | Отказ CAS; подготовленный результат не активируется |
| В очереди осталось событие старой схемы без выбранной политики | Активация блокируется |
| Повтор завершённого события после миграции inbox | Сохраняется установленная дедупликация; эффект не повторяется |
| Тесты изменены так, чтобы игнорировать второго автора | Несоответствие исходному обязательству остаётся открытым |
| Удалён обязательный пункт без разрешённой замены | `SCOPE_EXCEEDED` либо отказ принятия |
| Проверки A и B ссылаются только друг на друга | Нет достаточного основания принятия |
| Реализация не менялась, но поменялась схема данных | Применимость зависимых свидетельств пересматривается |
