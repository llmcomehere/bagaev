# HOST-1 — хост исполнения: хранилище, события, квитанции, журнал, миграция

**r31, r35 (структурная привязка), r39 (кодирование ключей) · WORKING_DESIGN (D9, D10, D43–D46, D81).** Хост открывает транзакцию точки входа, исполняет Perform ([MACHINE-1](machine.md) MCH-06) и фиксирует результат атомарно. Кроме того, он хранит квитанции, доставляет события, ведёт журнал и выполняет миграции. Эталон — `ref/bagaev_ref/host/`. Правила имеют идентификаторы `HST-nn`. Профиль V1 — один хост, SQLite. Писателей может быть несколько процессов: их сериализует блокировка записи SQLite.

## 1. Хранилище

**HST-01. Файл SQLite** открывается в режиме `journal_mode=WAL` и `synchronous=FULL`: зафиксированная транзакция переживает kill -9.
- Все изменения данных, квитанций, outbox, inbox, журнала и привязки идут через транзакции `BEGIN IMMEDIATE`. На время такой транзакции запись принадлежит одному процессу.
- Исключение — служебные таблицы хоста: они создаются при открытии файла идемпотентно (`CREATE TABLE IF NOT EXISTS`, значения по умолчанию в `meta`) и данных программы не касаются.
- Потеря питания эталоном не проверяется. Её покрывает обещание `synchronous=FULL` самой SQLite.

**HST-02. Таблицы хоста:**

| Таблица | Содержимое |
| --- | --- |
| `t_<EntityId>` | строки таблицы программы `(key, value)`. Имя — по `@id` таблицы, поэтому переименование таблицы в исходнике данные не трогает (D67) |
| `meta` | активная привязка (HST-04): `schema`, `schema_json`, `subscriptions`, `state_version`, `epoch`, `writer_lock` |
| `outbox` | события: `seq` (растёт с 1 без пропусков), полное имя события, полезная нагрузка, источник (`<namespace>:<key>` или `<обработчик>:<seq>`), StateVersion фиксации |
| `inbox` | квитанции обработки: `(обработчик, seq)` → исход |
| `receipts` | квитанции команд: `(namespace, key)` → дайджест запроса, исход, результат (BAG-CJSON-1), StateVersion |
| `journal` | журнал исполнения (HST-12) |

Ключ и значение строки — наблюдаемая форма CANON-11 в байтах BAG-CJSON-1. Порядок строк при чтении — порядок Key (data-values §6), а не порядок вставки. Это временная форма: бинарный кодек значений VALUE-CODEC-V1 не закрыт (BD07). Поэтому в V1 формат хранения не является контрактом совместимости между версиями эталона.

**HST-03. StateVersion** — счётчик долговременных записей (D43), Int64 без переполнения (CANON-07).
- Каждая фиксация увеличивает его на 1: команда (и с `Ok`, и с `Err`), обработка события, миграция, служебная загрузка.
- Отказ до допуска (HST-05) и откат его не меняют.
- Если увеличивать некуда, фиксация отклоняется: `STATE_VERSION_EXHAUSTED`.

## 2. Привязка схемы

**HST-04. Активная привязка** — дайджест схемы данных `digest("data-schema", "1", схема)` (CANON-08). Схема состоит из двух частей:
- `tables`: `EntityId таблицы → {name, key, value, key_shape, value_shape, key_encoding}`;
- `events`: `EntityId события → {name, fields: {поле: тип}, shape}`. Полезная нагрузка outbox — тоже данные хранилища.

Типы записываются текстами CANON-11 (`key`, `value`, `fields` — для отчётов) и **строением** (`*_shape`, `shape`): встроенный тип — имя и строение аргументов; пользовательский — строение записи (поля по порядку с их строением), суммы (теги и строение нагрузки) или opaque (строение представления) без имени типа; регулярная рекурсия — ссылка на охватывающий тип по глубине. Поэтому смена полей типа под прежним именем меняет схему и требует миграции, а переименование типа без смены строения не требует пользовательской функции миграции (r35: прежняя запись только текстами пропускала смену строения под тем же именем). Данные хранилища декодируются по строению: имя типа в записи CANON-11 не сверяется (аргументы запросов — сверяются строго). Вместе с привязкой хранится список подписок `[(обработчик, событие)]`.

`key_encoding` — строение ключа с именами всех пользовательских типов CANON-11, включая вложенные: каждый пользовательский узел оборачивается в `["nominal", текст типа, строение]`; рекурсивная ссылка остаётся ссылкой по глубине. В обоих описаниях строения глубина рекурсивной ссылки — десятичная строка (CANON-02 запрещает числа JSON). Это часть привязки, поскольку поиск, замена и удаление строки используют байты ключа. Переименование вложенного типа меняет привязку даже при прежнем имени внешнего типа ключа. При смене `key_encoding` ключи технически перекодируются по новой программе (HST-15), сохраняя логические ключи и значения. Старая привязка без `key_encoding` требует такого же применения миграции: существующие строки сохраняются, ключи перекодируются и поле добавляется атомарно; это не первая привязка пустой базы.

- Первая программа привязывает пустое хранилище и создаёт таблицы. Пустота перепроверяется под записью: из двух одновременных первых программ привязывает одна, вторая получает обычную сверку.
- Если программа с другой схемой обращается к хранилищу, привязанному к прежней схеме, ответ — `SCHEMA_BINDING_MISMATCH`. Сменить схему можно только миграцией (HST-14, HST-15).
- `epoch` растёт с каждой применённой миграцией. Это поколение привязки, на которое ссылаются guard'ы.

## 3. Команда

**HST-05. Порядок обработки команды** (ядро R16, D44). Шаги 1–6 — отказы до допуска (`REFUSED`): ключ не резервируется, квитанция не пишется, данные не меняются, повтор после исправления допустим.
1. Точка входа существует, это `command` и она `pub`. Иначе `UNKNOWN_ENTRYPOINT` или `ENTRYPOINT_NOT_EXPORTED`.
2. Аргументы — список наблюдений CANON-11 по типам параметров, строго: точный набор полей, строки без суррогатов, коллекции — списки. Иначе `REQUEST_INVALID`.
3. KeyRef соответствует CANON-10 целиком (никаких завершающих символов). Иначе `REQUEST_INVALID`.
4. Политика хоста разрешает вызывающему эту точку входа (HST-09). Иначе `ACCESS_DENIED`.
5. Нет `writer_lock` (иначе `MIGRATION_IN_PROGRESS`) и схема программы совпадает с привязкой (иначе `SCHEMA_BINDING_MISMATCH`).
6. Дайджест запроса: `digest("command-request", "1", {entry, args})`, аргументы — в канонической форме CANON-11.
   - Guard `expected_state_version` — условие одной попытки, а не часть запроса: повтор той же команды с другим guard'ом получает прежнюю квитанцию (модель AUTH-TX-0.1).
   - Предметные ожидаемые ревизии, переданные аргументами, в дайджест входят.
   - Полномочия и вызывающий не входят.

Далее одна транзакция `BEGIN IMMEDIATE`:
- шаг 5 проверяется **повторно**: пока транзакция ждала записи, миграция могла переключить привязку;
- квитанция по `(namespace, key)` ищется **до** guard'а версии:
  - есть, и дайджест тот же — ответ из квитанции с `replayed: true`, без исполнения;
  - есть, но дайджест другой — `IDEMPOTENCY_CONFLICT`;
- `expected_state_version`, если он задан, сравнивается с текущей StateVersion. Несовпадение — `STALE_STATE {expected, actual}`, ключ не резервируется;
- исполняется тело (HST-06).

**HST-06. Исход команды** (OUT-03):

| Исполнение | Исход | Что фиксируется | `final` |
| --- | --- | --- | --- |
| `RETURNED Ok(v)` | `COMMITTED` | записи таблиц, события в outbox, квитанция, журнал; StateVersion + 1 | да |
| `RETURNED Err(e)` | `ABORTED` | только квитанция и журнал; записи тела откатываются до точки сохранения, событий нет; StateVersion + 1 | да |
| `FAULT`, `SEMANTIC_STOP`, `IMPLEMENTATION_STOP` | `ABORTED` | ничего: откат всей транзакции, квитанции нет | нет |

`Err(e)` — окончательный ответ приложения: повтор с тем же ключом вернёт тот же `e`. FAULT не окончателен: повтор с тем же ключом исполнит команду заново. Так уточнена строка OUT-03 «ничего, кроме receipt отказа»: квитанцию отказа получает только `Err`.

**HST-07. Чтение квитанций** ничего не исполняет.
- Квитанция команды (`bag status` с KeyRef):
  - `RESULT` — квитанция есть; возвращаются значение, исход квитанции и StateVersion фиксации;
  - `ABSENT_AT_READ` — квитанции нет на момент чтения; возвращается текущая StateVersion;
  - если в чтении передан запрос (точка входа и аргументы), а квитанция принадлежит другому запросу, ответ — `IDEMPOTENCY_CONFLICT`, как при повторе.
- Квитанция обработки (`bag status --handler H --seq S`): запись inbox даёт `RESULT`, её отсутствие — `ABSENT_AT_READ`.

`UNKNOWN` — состояние клиента, который не получил ответа (OUT-03). Хост его не выдаёт и сам ничего не повторяет. Клиент выясняет исход чтением квитанции или повтором с тем же ключом. Ключи в V1 не истекают (CANON-10): квитанция переживает перезапуски и миграции.

**HST-08. Perform** (MCH-06). Хост исполняет операции точки входа в её транзакции:

| Операция | Атом | Результат |
| --- | --- | --- |
| `std.store.get(t, k)` | `reads t` | `Option<V>` |
| `std.store.contains(t, k)` | `reads t` | `Bool` |
| `std.store.all(t)` | `reads t` | `Map<K, V>` — снимок таблицы |
| `std.store.put(t, k, v)` | `writes t` | `()` |
| `std.store.remove(t, k)` | `writes t` | `()` |
| `std.store.replace_all(t, m)` | `writes t` | `()` — таблица становится равна m |
| `emit E {…}` (`event.emit@1`) | `emits E` | `()` — событие в outbox после фиксации (EFF-10) |

- Чтение видит записи этой же транзакции.
- Перед каждой операцией атом сверяется с **выданными** атомами: это объявленный ряд точки входа без атомов, отозванных политикой хоста. Если атома нет — `IMPLEMENTATION_STOP ACCESS_DENIED` с полем `atom`, переход не публикуется, транзакция откатывается (EFF-11).
- Проверенная программа сама в отказ не попадает. Отказ возникает только из-за политики хоста (`revoke`) или ошибки реализации.

**HST-09. Политика хоста** — JSON `{callers: {вызывающий: [точки входа | "*"]}, revoke: [атомы]}`. Файл по умолчанию — `<корень>/host-policy.json`.
- Без раздела `callers` вызывать можно любую `pub` точку входа.
- `revoke` отзывает атомы у всех исполнений: так включается, например, режим «только чтение» на время обслуживания.
- Права предметной области (кто редактор) — данные приложения (O06), а не политика.

## 4. Запрос

**HST-10. `query`** исполняется в транзакции чтения: снимок согласован, квитанции нет, StateVersion не меняется. Привязка сверяется внутри этой транзакции.
- Операции записи и `emit` отклоняются по EFF-09 ещё до запуска, а на уровне хоста — `ACCESS_DENIED`.
- Результат — наблюдение OUT-01 (`outcome`, `value` или `code`), как у `bag run`.

## 5. События

**HST-11. Доставка** (`bag events deliver`; D9, D46).
- Каждое событие outbox доставляется каждому обработчику с параметром этого типа. При обычной доставке события одного обработчика идут в порядке `seq`.
- Доставка одного события одному обработчику — отдельная транзакция. В ней повторно проверяются замок и привязка (как HST-05 шаг 5) и фиксируются записи обработчика, его события и запись inbox.
- Запись inbox и есть квитанция обработки. Повторная доставка той же пары `(обработчик, seq)` возвращает сохранённый исход с `replayed: true` и не исполняет обработчик (O07, C13).
- FAULT или остановка откатывают транзакцию: событие остаётся недоставленным и видимым в `pending`, а обычная доставка этому обработчику на нём останавливается.
- **Явная доставка** `--seq S` (вместе с `--handler H` или для всех подписчиков) — операция оператора вне очереди. Так обходят событие, на котором обработчик падает, или проверяют устойчивость приложения к переупорядочиванию: при полных снимках (D45) приложение отличает устаревшую ревизию само. Пропущенные события остаются в `pending` и при обычной доставке идут по порядку.
- Отдельной третьей границы ACK в V1 нет. Outbox не очищается: он — журнал событий для replay и аудита.

## 6. Журнал и replay

**HST-12. Журнал.** Каждая фиксация пишет в журнал запись `(вид, ссылка, тело)`, где вид — `command`, `handler`, `migration` или `seed`. Тело исполнения (`command`, `handler`) содержит:
- точку входа и аргументы в форме CANON-11 (для обработчика — `seq` события);
- последовательность операций Perform: имя, ресурс, аргументы и результат (CANON-11 в BAG-CJSON-1);
- для `emit` — полезную нагрузку;
- исход и, у команды, значение.

**HST-13. Replay** (`bag replay --ref`) исполняет ту же программу заново над записью журнала `command` или `handler`.
- Ответы чтений берутся из журнала. Операции, их ресурсы и аргументы, полезные нагрузки событий и результат только сверяются.
- Таблицы хранилища при этом не читаются и не меняются, outbox и журнал не пополняются, внешний мир не вызывается.
- Совпало всё — `REPLAY_MATCH` с числом операций; иначе — `REPLAY_DIVERGENCE` с указанием первого расхождения.
- Записи `seed` и `migration` не воспроизводятся: `REQUEST_INVALID`. Ссылки нет в журнале — `ABSENT_AT_READ`.

Replay проверяет детерминизм и неизменность программы относительно журнала. Он не доказывает, что данные в таблицах соответствуют журналу.

## 7. Миграция

**HST-14. План** (`bag migrate plan`) сравнивает схему активной привязки со схемой новой программы.

Каждой таблице по `EntityId` назначается действие:

| Изменение | Действие |
| --- | --- |
| строение значения и имя таблицы те же | `keep` (имена типов могут измениться) |
| строение то же, имя таблицы другое | `rename` (данные сохраняются) |
| новая таблица | `create` |
| строение значения другое | `migrate`: нужна ровно одна `migration … on <таблица>(old: Old) -> Result<New, E>`, где строение Old равно прежнему строению значения, а New — новому. Old может быть новым типом с прежним строением (`ArticleV1` при эволюции `Article` под прежним именем) |

Проблемы таблиц:

| Проблема | Код причины |
| --- | --- |
| таблица удалена | `TABLE_REMOVED` |
| изменено строение ключа | `KEY_TYPE_CHANGED` с `from`, `to` |
| миграции нет | `MIGRATION_MISSING` с `from`, `to` |
| миграций больше одной | `MIGRATION_AMBIGUOUS` с `from`, `to` |

Любая проблема — отказ `MIGRATION_PLAN_INVALID {problems}`.

`keep` и `rename` означают отсутствие пользовательской миграции значений. Техническая перекодировка ключей при смене `key_encoding` нужна и для этих действий, и для `migrate`. Она сохраняет доступ через `get`, замену единственной строки через `put` и удаление через `remove`; переименование не создаёт второй логический ключ.

Каждому событию по `EntityId` назначается действие: `keep`, `rename`, `create`, `change` (другое строение полей) или `remove`. Изменение типа события допустимо: дренаж (HST-15) гарантирует, что недоставленных событий прежнего типа нет.

Таблицы и события перечисляются в порядке `EntityId`. Идентификатор плана — `digest("migration-plan", "1", {from_schema, to_schema, epoch, state_version, tables, events})`. Если схемы совпадают — `UP_TO_DATE`. В непривязанном хранилище ответ — `MIGRATION_NOT_BOUND`.

**HST-15. Применение** (`bag migrate apply`; D10) — при остановленных писателях:
1. `writer_lock := plan_id` в отдельной транзакции. Команды, доставка и служебная загрузка получают `MIGRATION_IN_PROGRESS`. Замок другого плана даёт `MIGRATION_IN_PROGRESS`, замок того же плана (после сбоя) позволяет продолжить.
2. Дренаж: если по подпискам активной привязки есть недоставленные события, ответ — `MIGRATION_BACKLOG {pending, count}`, замок снимается.
3. Одна транзакция `BEGIN IMMEDIATE`:
   - guard: схема, `epoch`, StateVersion и замок те же, что в плане; иначе `STALE_STATE {expected, actual, reason: binding}`, замок снимается;
   - для каждой таблицы `migrate` и каждой сохранённой таблицы со сменой `key_encoding` (либо без этого поля в старой привязке) строится теневая `s_<EntityId>`: ключи декодируются структурно и кодируются по новому типу, включая вложенные имена. Все строки сохраняются; коллизия ключей — ошибка с откатом, а не замена одной строки другой;
   - в таблице `migrate` значения строк в порядке Key декодируются по Old и проходят через функцию миграции (чистую, с бюджетом); при технической перекодировке без `migrate` байты значений сохраняются. `Err(e)` даёт `MIGRATION_FAILED {table, key, error: e}`; FAULT или остановка — `MIGRATION_FAILED {table, key, error: код, termination}`. Весь переход откатывается вместе с перекодировкой ключей и теневыми таблицами, замок снимается, данные не тронуты;
   - переключение: теневые таблицы заменяют рабочие, создаются новые, записывается новая привязка, `epoch + 1`, `StateVersion + 1`, замок снимается, пишется запись журнала.

Второй `apply` того же плана, запущенный одновременно, ждёт записи и после фиксации первого получает `STALE_STATE`: теневые таблицы между процессами не делятся. `bag migrate abort` снимает замок после сбоя и удаляет теневые таблицы, если они остались. Проверка исполнимых правил контрактов на мигрированных строках в V1 не делается (NOT_YET_EXECUTABLE: контракты пока не исполнимы, Ф6).

## 8. Сбои и восстановление

**HST-16. Точки сбоя.** Переменная окружения `BAG_CRASH_AT=<точка>` завершает процесс как kill -9 (`os._exit(137)`): без отката, без ответа, без закрытия файла.

| Точка | Где | Что видно после перезапуска |
| --- | --- | --- |
| `before_begin` | команда или доставка до `BEGIN` | ничего; повтор исполняет |
| `before_commit` | после всех записей, до `COMMIT` | ничего: SQLite отбрасывает незафиксированное; повтор исполняет один раз |
| `after_commit` | после `COMMIT`, до ответа | всё зафиксировано; повтор с тем же ключом возвращает квитанцию (`replayed: true`), доставка — запись inbox; второго эффекта нет |
| `migration_prepare` | после замка и дренажа, до транзакции переключения | замок стоит, писатели получают `MIGRATION_IN_PROGRESS`; повтор `apply` завершает миграцию, `abort` отменяет её |
| `before_swap_commit` | в транзакции подготовки и переключения, до `COMMIT` | переключения нет, теневых таблиц нет, замок стоит; повтор `apply` завершает |
| `after_swap` | после фиксации переключения | миграция применена; повтор даёт `UP_TO_DATE` |

Восстановление ничего не угадывает: исход определяется по квитанции, записи inbox или привязке.

## 9. Команды и наблюдения

**HST-17. CLI эталона:**
- `bag run <корень> <точка входа> --db F [--args JSON] [--namespace N --key K] [--caller C] [--policy P] [--expected-state-version V]` — `command` или `query`;
- `bag status --db F --namespace N --key K [<корень> --entry E --args JSON]` и `bag status --db F --handler H --seq S`;
- `bag events deliver <корень> --db F [--handler H] [--seq S]`;
- `bag replay <корень> --db F --ref R`;
- `bag migrate plan|apply|abort <корень> --db F`;
- `bag seed <корень> --db F --table T --rows JSON` — служебная загрузка фикстур одной транзакцией с записью в журнал. Это не точка входа программы;
- `bag state <корень> --db F`.

**Формы наблюдений** (поля JSON; значения — CANON-11; числа хоста — целые JSON). Пояснение `detail` допустимо в любом ответе и в сравнение L2 не входит.

| Ответ | Поля |
| --- | --- |
| отказ | `outcome: REFUSED`, `code`, `data` — если у кода есть данные (ниже) |
| команда исполнена | `outcome: COMMITTED \| ABORTED`, `value`, `final: true`, `replayed`, `state_version` |
| команда не окончательна | `outcome: ABORTED`, `final: false`, `replayed: false`, `termination`, `code`, у FAULT — `site` и, если есть, `data` |
| запрос | наблюдение OUT-01 без `effects` |
| квитанция команды | `outcome: RESULT`, `value`, `receipt_outcome`, `state_version` фиксации; или `outcome: ABSENT_AT_READ`, `state_version` текущая |
| квитанция обработки | `outcome: RESULT`, `handler`, `seq`, `receipt_outcome`; или `ABSENT_AT_READ`, `state_version` |
| доставка | `outcome: DELIVERED`, `deliveries` — по элементу на попытку в порядке обработчиков (по имени) и `seq` |
| элемент доставки | исполнено: `handler`, `seq`, `outcome: COMMITTED`, `replayed: false`, `state_version`; повтор: `handler`, `seq`, `outcome` из inbox, `replayed: true`; сбой: `handler`, `seq`, `outcome: ABORTED`, `termination`, `code`, у FAULT `site`; отказ замка или привязки — объект отказа |
| replay | `outcome: REPLAY_MATCH`, `ref`, `operations`; `REPLAY_DIVERGENCE`, `ref`; `ABSENT_AT_READ`, `ref` |
| план | `outcome: PLANNED`, `epoch`, `state_version`, `tables`, `events`, `plan_id`, `from_schema`, `to_schema`; `UP_TO_DATE` — те же поля с пустыми `tables`, `events` |
| применение | `outcome: APPLIED`, `plan_id`, `epoch`, `state_version`, `rows` (число строк, прошедших пользовательскую функцию миграции; техническая перекодировка ключей не увеличивает счётчик), `tables`, `events` |
| отмена | `outcome: ABORTED \| NO_MIGRATION`, `lock`, `dropped` (имена удалённых теневых таблиц) |
| загрузка | `outcome: COMMITTED`, `rows`, `state_version` |
| состояние | `state_version`, `epoch`, `tables` (полное имя → пары `[ключ, значение]` в порядке Key), `outbox` (`seq`, `event`, `payload`), `inbox` (`handler`, `seq`, `outcome`), `pending` (`handler`, `seq` по подпискам активной привязки без записи inbox) |

Данные отказов:
- `IDEMPOTENCY_CONFLICT {namespace, key}`;
- `STALE_STATE {expected, actual}`, у миграции ещё `reason`;
- `ACCESS_DENIED {entry, caller}` при допуске; `{atom}` у остановки Perform;
- `UNKNOWN_ENTRYPOINT {name}`, `ENTRYPOINT_NOT_EXPORTED {name}`;
- `MIGRATION_IN_PROGRESS {lock}`, `MIGRATION_BACKLOG {pending, count}`, `MIGRATION_FAILED {table, key, error[, termination]}`, `MIGRATION_PLAN_INVALID {problems}`.

`plan_id`, `from_schema`, `to_schema` и `lock` — дайджесты. В сравнение L2 корпуса они не входят: их байты зависят от текстов схем, а смысл проверяется исходами (HST-14).

**HST-18. `test` с эффектами** исполняется на отдельном пустом хранилище в памяти, привязанном к схеме программы. Тест видит только свои записи, по окончании хранилище отбрасывается (EFF-09).

**HST-19. Жизненный цикл ресурсов.**
- Соединение с хранилищем, транзакция и точка сохранения принадлежат хосту и живут в пределах одного исполнения точки входа. Любой исход (возврат, FAULT, остановка, отказ Perform, исключение реализации) закрывает транзакцию фиксацией или откатом. Открытой транзакции после ответа не остаётся.
- У программы V1 нет host handles, capability-значений и финализаторов (EFF-11, D87): закрывать ей нечего, и порядок освобождения не наблюдается.
- Значения неизменяемы и не имеют идентичности. Освобождение памяти не наблюдаемо. Исчерпание пределов реализации (глубина значения) — `IMPLEMENTATION_STOP RESOURCE_LIMIT` (MCH-02): транзакция откатывается, квитанции нет.
- После сбоя процесса (HST-16) ресурсы не восстанавливаются: SQLite отбрасывает незафиксированное вместе с теневыми таблицами миграции, замок снимает повтор `apply` или `abort`.

## 10. Снятые противоречия

| Вопрос | Источники | Решение HOST-1 |
| --- | --- | --- |
| Резервирует ли `Err` ключ | OUT-03 (квитанция отказа) и модель A09 (Err не фиксирует ничего) | резервирует: квитанция `ABORTED` (HST-06). Модель R07 расходится в этом, мост отмечает расхождение |
| Меняет ли `Err` состояние | EFF-09 («Err и Fault ничего не меняют») | данные не меняет, квитанцию и StateVersion — да (HST-03, HST-06); EFF-09 уточнён в r31 |
| Третья граница ACK | D46 (ack отдельно) и V1 одного хоста | нет: запись inbox — квитанция обработки (HST-11) |
| Порядок событий | services.md (на усмотрение хоста) и D45 | по `seq` для каждого обработчика, остановка на первом сбое; внеочередная доставка — только явная операция оператора (HST-11) |
| Словарь статуса | R16 (4 значения), R24 (5) | `RESULT` / `ABSENT_AT_READ` у хоста, `UNKNOWN` — состояние клиента (HST-07) |
| Дайджест запроса | модель: `json.dumps` | CANON-08 над BAG-CJSON-1 (HST-05) |
| Guard версии в дайджесте | R16 (ожидаемые ревизии в запросе) и модель (guard не входит) | guard StateVersion — условие попытки, не входит; предметные ревизии в аргументах — входят (HST-05) |
| FAULT в команде | OUT-03 «receipt отказа» | квитанции нет, повтор исполняет заново (HST-06) |
| Тестовая копия хранилища | EFF-09 («тестовая копия») | пустое хранилище в памяти, привязанное к схеме (HST-18) |
