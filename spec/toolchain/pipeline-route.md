# Сквозная проверка и порядок реализации R21

**Статус: 29 классов реальной интеграции NOT_RUN.** Полный список с setup, независимым oracle и expected outcome — [integration-cases.json](../../registry/data/toolchain/pipeline-integration-cases.json). Это проект процедуры, не фактическое испытание языка. Ни один input grammar/IR не подставлен из JSON research model.

## 1. Обязательные реальные входы

Нужны exact released T03 grammar/lexer/recovery/CST/SyntaxIR/source map codecs; T02 identity contract; T04 type/value/nominal rules и executable checker; T05 finite effect/adapters/obligation rules; T06 reference machine, work/cancel observation domain; R19 FormatContracts/MeaningLock; R20 actual Lock/InterfaceClosure/BuildRecipe/BuildPlan; seven admitted compiler stage builds/checkers и reference runtime target.

В availability manifest каждой зависимости фиксируются exact content/native identity, producer, operation support и required coverage. Missing dependency даёт INPUT_NOT_READY с перечнем missing refs; unsupported exact semantic version — UNSUPPORTED. Это не failure программы и не оправдание создать другую grammar под тем же именем. До допуска stage каждый V1 feature ledger row должен быть либо покрыт exact input/output/error/cost rule, либо давать явный declared diagnostic. Исключение в эксперименте не удаляет функцию V1.

## 2. Порядок реализации

| Шаг | Конкретный результат | Проверка выхода |
|---|---|---|
| 1 | Byte/object store, closed metadata codecs, independent snapshot capture, subject checker | Hash/native identity, strict refs, no generated bytes in source, recipe/lock/plan acyclic graph |
| 2 | One canonical stage harness, status/blame/diagnostics, limits/cancel and immutable output commit | No missing/foreign/recovery input reaches successful later stage; failed stage never emits executable |
| 3 | Реальные parser + lexical resolver под released T03/T02 | Lossless CST coverage, exact names/IDs, full scopes/negative lookups and source-bound diagnostics |
| 4 | Type + effect checkers под T04/T05 | Full branch checking, scoped unification, declared latent types and least fixed point |
| 5 | Reference lowering + exact module linker | Hygienic ordered forms, charge/cancel derivation, complete link closure and ABI checks |
| 6 | Canonical interpreter image encoder + independent loader | Exact decode roundtrip, source-to-output trust/recompute proof, target admission |
| 7 | Exact-input cache + origin/backward index + editor adapters | Same full source/context or miss, stale diagnostics rejected, ambiguity retained, current cache work/cancel accounted |
| 8 | Real durable publication, build/release integration and fault injection | Generation CAS, exact receipt recovery, enforced inputs and measured independent reproduction |

Шаги 3–6 можно выполнять параллельно по закреплённым interfaces; шаг2 не требует выдумать всю grammar. Native backend, оптимизатор, полный FFI и stdlib остаются отдельными задачами. No-op optimizer для reference target не закрывает T13-C03 автоматически.

## 3. Независимый oracle

До запуска implementation для каждого case сохраняются exact inputs, all upstream versions, expected full intermediate outputs/diagnostics/lineage и способ их независимого получения. Для source parser это вручную проверенный derivation/corpus по grammar; для scopes — lexical table; для types/effects — constraints/least sets; для lowering — rule instantiation и reference outcomes; для linker — exact inventory matching; для emit — independent decoder и trusted relation к source. Дополнительные differential runs допустимы, но общий codebase двух реализаций не делает их oracle независимым.

Equality domain указан явно: bytes, native semantic representation, source/provenance relation, runtime observation или current authority outcome. Для claims о runtime equivalence сравниваются logical cost/cancel/effect prefix/error/state outcomes, а не только scalar result. Для build reproduction сравниваются actual raw artifact bytes под exact supported environment; normalized copy имеет иной ref и отдельный transformation contract.

Фактический report фиксирует invocation IDs, input/output content refs, immutable provider/checker versions, expected/actual, failures и ограничения. `NOT_RUN`, `INPUT_NOT_READY`, `UNKNOWN`, `UNSUPPORTED` сохраняются различными. Stage3 всего T13-C01 требует coverage всех его stage boundaries на реальном объявленном предмете; finite subset не заменяет этого.

## 4. Связь с текущим опытом

PIPELINE-SLICE-0.1 реализует семь стадий для восьми JSON expression forms. Его test inputs содержат complete source text, toy type/effect tables и explicit imported objects. Это реальная ограниченная трансформация и проверка, но не source grammar bagaev. Он не исполняет emitted instructions, не доказывает runtime budgets/cancel/optimizer equivalence, использует opaque meaning/lock labels и не проверяет full R19/R20 contracts.

Independent report (`r21:results/pipeline-report.json`) сравнивает полные результаты, включая hashes/payloads/diagnostics. Его cache verification полностью recompiles; это проверка binding/corruption defense, не speed benchmark. Constructed cache/artifact fixtures имеют явно ограниченную историю. Root metadata probes отдельно проверяют schema/local invariants на synthetic refs без настоящих target payloads. Ни один из этих результатов не заменяет 29 real integration classes.

Примечание к составу: экспериментальные пакеты R16–R23 не включены; упоминания их проверок описывают границы метода, а не результаты запуска этого пакета.
