# LNK-0.2 · Влияние изменения и достаточный контекст

**DRAFT · 22 октября 2026.** Владельцы согласования: T09/T10/T11/T12. [Вход в ТЗ](README.md). Уточняет A02–A05 и boundedContext; [модели записей](01-records-and-invariants.md) и [правила обновления](02-extraction-and-refresh.md) являются входами.

## 1. Проверяемый результат анализа

`ImpactReport` отвечает: какие обязательства требуется пересмотреть при переходе от base к candidate; по каким отношениям они найдены; что исключено и на каком основании; какая часть ещё неизвестна. Это отчёт относительно ChangeContract, ScopeRef, observation model и версии политики.

В отчёте различаются:

- `in_scope`: последствия требуют работы или проверки;
- `excluded_with_basis`: конкретный путь закрыт действующим основанием;
- `unknown`: нет достаточного вывода о влиянии либо о допустимости исключения;
- `frontier`: анализ этого пути ещё не выполнен из-за бюджета или незавершённого задания.

Само нахождение зависимости не означает неисправность потребителя. Оно назначает обязательство проверить сохранение его нужных свойств. Отсутствие обнаруженного пути не закрывает пробел покрытия.

## 2. Связь как описание используемых гарантий

Для авторства предлагается различать представления данных, доступные через проверяемые операции:

| Потребитель | Наблюдение, которое ему может быть достаточно предоставить | Что требуется обосновать |
| --- | --- | --- |
| Счётчик авторов | Количество участников | Нет иных доступов; ошибки/эффекты и область входов учтены |
| Поиск по соавтору | Множество идентификаторов | Порядок не участвует в результате или иной учитываемой гарантии |
| Подпись статьи | Упорядоченные участники и отображаемые имена | Все участники сохранены, порядок и получение имён определены |
| Экспорт | Контракт конкретного формата, в том числе состав и порядок | Действительный сериализатор выполняет требование, а не только читает массив |

Эта таблица — проект гранулярности, не готовое доказательство независимости произвольного кода. Например, поиск может обращаться к первому автору для ранжирования: тогда порядок тоже значим. Счётчик может иметь ограничение по времени, а способ получения количества — линейную стоимость: такая гарантия должна присутствовать в модели наблюдений, если заявлена.

Для V1 предпочтительны немногочисленные проверенные операции представления. Тонкий вывод свойств произвольной функции остаётся отдельным исследованием. Прямой доступ к полному объекту, неизвестный вызов или утечка представления расширяет UseSummary.

## 3. Когда можно закрыть обязательство или путь

У закрытия конкретного обязательства два допустимых вида основания:

1. **Прямое сохранение:** достаточное свидетельство, что точное обязательство потребителя сохраняется на кандидате в нужной области.
2. **Невлияние по наблюдениям:** полное описание использования потребителя и полный верхний охват изменения в общей проверенной модели наблюдений позволяют установить, что потребитель не наблюдает изменение.

Проверка по facets выполняется только при всех условиях:

- UseSummary относится к точной ревизии потребителя, обязательству и области; полнота проверена допустимым механизмом.
- DeltaSummary относится к точной паре base/target и не оставляет неучтённых значимых изменений.
- Оба описания используют совместимые версии observation model и facet registry.
- Учтены guard, frame, alias, эффекты, ошибки, допустимые входы и другие наблюдения, входящие в обязательство.
- Правило разделения/корреляции свойств определено этим registry; имена facets сами по себе не определяют независимость.
- Все основания целы, применимы, достаточны и положительны по процедуре A03.

Только после этого допустима проверка непересечения консервативных множеств. Если любое условие не установлено, используется TOP либо отдельное unknown; путь не исключается.

```text
boundaryDecision(binding, delta, base, target, policy):
    require binding identifies exact consumer, obligation, path and scope
    if not bindingMatchesExactSubjectsAndBothDomains(binding, base, target):
        return KEEP(reason=SUBJECT_OR_DOMAIN_MISMATCH)
    direct := assessPreservationEvidence(binding, base, target, policy)
    if supports(direct):
        return CLOSE_OBLIGATION(binding.obligation, direct)
    use := binding.use
    if not exactScopesAndModelsMatch(use, delta, binding):
        return KEEP(reason=MODEL_OR_SCOPE_MISMATCH)
    if not checkedComplete(use) or not checkedComplete(delta):
        return KEEP(reason=INCOMPLETE_SUMMARY, aspects=TOP)
    if unresolvedGuardOrChannel(use, delta):
        return KEEP(reason=UNRESOLVED_CHANNEL, aspects=TOP)
    result := registryNonInterferenceRule(use, delta, binding.obligation)
    if result has a sufficient applicable positive basis:
        baseline := assessBaselineSatisfaction(binding, base, policy)
        transfer := assessTransfer(baseline, result, binding, target, policy)
        if supports(baseline) and supports(transfer):
            return CLOSE_OBLIGATION(binding.obligation, baseline + transfer)
        return NO_NEW_IMPACT_FROM_PATH(result.basis, obligation_still_open=true)
    return KEEP(reason=RELEVANT_OR_UNKNOWN)
```

Прямое сохранение и невлияние различимы в отчёте. Сценарный тест может подтвердить сохранение в области сценария, но не получить автоматически силу общего невлияния. Отрицательный результат проверки сохраняет противоречие, даже если другое свидетельство положительно.

Невлияние само по себе не устанавливает истинность требования. Оно позволяет не пересматривать конкретный путь, но закрытие обязанности требует действующего положительного основания на base и проверенного переноса на target либо прямого основания на target. Новая или усиленная обязанность, новый домен и новая политика не наследуют подтверждение автоматически. Отсутствие новых изменений не исправляет прежний дефект.

**Закрытие обязательства не закрывает отношение целиком.** Из отношения отдельно выводятся обязанности потребителя и возможные изменения его выходных наблюдений. Доказательство «выход — корректный JSON» не подтверждает сохранение значений JSON и не закрывает обязанность поискового индекса учитывать всех авторов. Для остановки передачи выходного delta требуется основание сохранения именно соответствующих выходных наблюдений, включая нужные эффекты и ошибки. При его отсутствии выходной delta остаётся TOP, даже если одно обязательство уже закрыто.

Область сопоставления включает допустимые домены **обеих** версий. Расширение входного домена не покрывается доказательством на прежнем подмножестве. Проверенная привязка use к одной обязанности не переносится на соседние обязанности или другие пути.

## 4. Исходные точки и направления распространения

Начальный набор включает изменённые определения/контракты/схемы/конфигурации, добавленные и удалённые отношения, изменённые основания анализатора, новые обязательства и переходы ChangeContract. Изменение состава проекта также может менять ответы на прежние отрицательные запросы и создавать новые исходные точки.

Рабочий граф — объединение base и candidate с метками сторон. Одинаковый EntityId помогает сопоставлять ревизии; split/merge требуют LineageRecord. Произвольного сопоставления по похожему имени нет.

| Отношение | Распространение при соответствующем изменении |
| --- | --- |
| `consumer calls provider` | От изменения требуемых гарантий provider к consumer; изменённый consumer далее имеет собственный delta |
| `consumer reads resource` | От изменённого ресурса/схемы к consumer |
| `producer writes resource` | От изменённого эффекта producer к resource; затем к читателям и другим зависимым обязательствам |
| `producer emits event` | От изменённого выпуска/смысла события к event |
| `handler consumes event` | От изменённого события к handler, затем к его возможным эффектам |
| `implementation implements clause` | От правки реализации к пересмотру соответствия clause; от правки clause — к ответственным реализациям |
| `consumer requires clause` | От изменения clause или его основания к consumer |
| `check checks subject` | От изменения subject/предпосылок к применимости проверки; изменение самой проверки также требует пересмотра её достаточности |
| `view derived_from source` | От изменения source к пересчёту view и анализу изменения его наблюдений |
| `successor supersedes predecessor` | Через явное отображение обязательств; неразрешённый перенос остаётся открытым |

Для каждого вида нужна полная таблица поддержанных changed facets и правил преобразования delta. По умолчанию изменение зависимого компонента имеет TOP. Пересечение used facets с delta поставщика не даёт автоматически точный delta выходов потребителя.

## 5. Алгоритм анализа LNK-I01

```text
impact(base, candidate, changeContract, scope, policy, budget):
    requireExactVersionsAndConsistentGenerations()
    graphs := unionTagged(base.graph, candidate.graph)
    report := obligations(changeContract) + coverageGaps(graphs, scope)
    work := deterministicSeeds(base, candidate, changeContract)
    universe := finiteKeys(graphs, changeContract, fixedScopePartitions(scope))
    states := map with default UNSEEN
    while work not empty:
        if budget exhausted:
            return persist(INCOMPLETE, report, frontier=work)
        item := popStable(work)
        key := resolveInUniverseOrWiden(item.key, universe)
        if key cannot be resolved soundly:
            retainFrontierAndGap(report, item); continue
        effective := validateOrTOP(item, base, candidate, key, policy)
        prior := states[key]
        accumulated := join(bottom if prior is UNSEEN else prior, effective)
        if prior is not UNSEEN and accumulated equals prior: continue
        states[key] := accumulated
        retainOwnObligations(report, key, accumulated)
        relations := typedRelevantRelations(graphs, key, accumulated)
        retainQueryProvenanceAndGaps(report, relations.queryRecord)
        for relation in stableOrder(relations):
            guardState := evaluateForBothSides(relation, base, candidate)
            if inactiveForBothSidesWithValidBasis(guardState):
                retainConditionalBoundary(report, relation, guardState)
                continue
            bindings := deriveConsumerObligations(relation, key,
                                                  accumulated, changeContract)
            retainBindingCoverageAndGaps(report, bindings)
            for binding in stableOrder(bindings):
                decision := boundaryDecision(binding, accumulated.delta,
                                             base, candidate, policy)
                retainExactObligationDecision(report, binding, decision)
            flow := transferOutputsAndOtherReasons(relation, accumulated,
                         exactOutputPreservationBases, default=TOP)
            retainFlowDecisionAndBasis(report, relation, flow)
            enqueueAllOpenFlows(work, flow, universe)
    return persist(report, completeOnlyInDeclaredCoveredScope(report))
```

Guard, ложный только в candidate, не скрывает прежнюю активную связь: её удаление само может иметь последствия. Guard, истинный только в candidate, создаёт новый путь. Отсутствие вычислимого условия сохраняет возможную зависимость. Наблюдение false в одном запуске не закрывает статический путь.

Рабочий ключ включает сущность и ревизионную пару/сторону, вид потока либо точное обязательство, а также заранее определённое разбиение области. До прохода фиксируется конечная вселенная этих ключей. Transfer не создаёт бесконечные новые области вида `x > 1`, `x > 2`, …: используется проверенное расширение к существующей области с TOP либо сохраняется frontier/INCOMPLETE. Конечность одного графа без этого ограничения недостаточна для обещания неподвижной точки.

Состояние ключа содержит верхнюю границу возможного delta и конечное множество причин пересмотра: изменения структуры, guard, обязательства, основания и политики. Неполные или неприменимые delta превращаются в TOP **до** сравнения и объединения. Join объединяет возможные изменения и причины; непроверенная составляющая поглощает узкие bounds. Все последующие запросы и transfer работают с накопленным состоянием, а не с последним пришедшим фрагментом. UNSEEN отличается от уже обработанного пустого набора, поэтому первое посещение с изменённым обязательством не теряется.

При конечной вселенной ключей, конечном registry и монотонном join высота состояния конечна. TOP поглощает более узкие значения; бюджет всё равно ограничивает фактическую работу. Новое основание, позволяющее уменьшить ранее найденную область, проверяется отдельным проходом; прежние обязательства не исчезают внутри текущего прохода без записи решения. `deriveConsumerObligations` обязан обосновать полноту вывода в поддержанном профиле; неизвестное соответствие оставляет gap, а не пустой список обязанностей.

Циклы программы допустимы и обрабатываются worklist/SCC. Циклическое обоснование исключения недопустимо. Стоимость обхода графа и стоимость проверяющих процедур учитываются отдельно. Проверяющая процедура может вернуть timeout/unknown, что оставляет путь открытым.

## 6. Пустой поиск и отрицательная зависимость

Допустим, прежний запрос «какие обработчики получают AuthorshipChanged?» вернул ноль результатов. У него должны сохраниться перечень проверенной области, stamps состава и релевантных проекций, параметры поиска и coverage. После добавления обработчика запрос пересчитывается.

Если существующий обработчик ранее получал другое событие, а теперь получает AuthorshipChanged, изменения membership недостаточно: состав элементов прежний. Поэтому QueryFootprint учитывает и признаки, по которым отбирались кандидаты. Равным образом чтение несуществующего имени зависит от состояния соответствующей области разрешения имён.

NoMatchObservation может участвовать в основании невлияния только после проверки покрытия и точного вопроса. Пустой ответ по доступной части закрытого от агента проекта не позволяет объявить отсутствие закрытых потребителей.

## 7. Контекст как учёт обязательных путей

Цель ContextPack — дать достаточно сведений для конкретного следующего действия при сохранении всех обязательств работы. Предлагается сохранять `ContextCoverage`: соответствие каждого относящегося к шагу обязательства и пути одному из состояний:

| Состояние | Содержание |
| --- | --- |
| `expanded` | Точная версия нужной реализации/данных включена в пакет |
| `boundary` | Есть интерфейс, достаточное действующее основание границы и его предпосылки |
| `pending` | Сохранены ссылка, причина и действие для продолжения |
| `blocked` | Не установлен охват анализа, нет доступа либо невозможно выполнить требуемую проверку |

Контекст содержит base/candidate, ChangeContract, GraphRef/ScopeRef, policy, точные QueryRecords анализа, корневые обязательства, недоступные зависимости в разрешённом представлении и frontier. Локальная выдача ссылается на полный WorkState; бюджет не удаляет его записи.

Алгоритм выбирает обязательную оболочку, затем раскрывает пути в стабильном порядке. Внутренности компонента заменяются границей только после процедуры boundaryDecision. Превышение бюджета возвращает incomplete и возможное разбиение шага. Минимальный по размеру пакет не обещается: сначала нужна проверяемая достаточность, оптимизация отбора развивается отдельно.

Пробел можно отнести к другому шагу только по сохранённому основанию разделения. Неустановленная принадлежность пробела блокирует ready_for_step. Готовность шага не означает завершения всех обязательств ChangeContract и не разрешает accept.

## 8. Интерфейс объяснений

| Операция | Обязательные параметры | Результат |
| --- | --- | --- |
| `relations` | graph/generation, entity ref, direction, kinds, scope, access context | Точные отношения, происхождение, coverage, query record |
| `whyAffected` | impact report ref, obligation/item ref | Пути, изменённые свойства и консервативные шаги вывода |
| `whyExcluded` | impact report ref, boundary ref | Вопрос, основание, проверенные предпосылки и условия применимости |
| `remainingUnknown` | report/work ref, scope | Gaps/frontier с причинами и допустимыми следующими действиями |
| `contextForStep` | work revision, step ref, budget, access context | ContextPack, ContextCoverage и ready/incomplete |

Это проекты семантических операций; формат транспорта согласуется с T12. Результат любого запроса закрепляет версию. Выбор текущей версии допускается как удобство интерфейса, но ответ обязан сообщить фактически выбранный GraphRef/SnapshotId.

Ошибки: `GENERATION_MISMATCH`, `STALE_INPUT`, `UNSUPPORTED_RELATION`, `SCOPE_INCOMPLETE`, `MODEL_MISMATCH`, `EVIDENCE_NOT_APPLICABLE`, `ACCESS_BLOCKED`, `BUDGET_EXHAUSTED`. Unknown и incomplete не выдаются как пустой успешный полный список. Ошибка частного запроса не стирает сохранённый отчёт работы.

## 9. Принятие и конкурирующие изменения

Перед accept повторно проверяются применимость оснований, полнота обязательной области, отсутствие противоречий, точные ревизии работы/контракта/политики и текущие полномочия. CAS по принятому head и work revision остаётся обязательным.

Проверенные результаты запросов либо неизменяемы в принятом snapshot, либо имеют условия, повторно проверяемые при принятии. Новая версия коллекции, обнаруженная перед записью, требует пересчёта. Не допускается проверить отсутствие потребителей, принять появление нового потребителя и затем использовать прежний вывод для той же принимаемой версии.

Принятие исходника не активирует runtime и не выполняет миграцию. Смена конкретных StateVersion/ActiveBinding регулируется ранее определённым протоколом перехода.

## 10. Граница результатов конечной модели

Проверочная модель задаёт facets и completeness certificates как синтетические входы. Она может обнаружить потерю invalidation, несогласованность индексов или неверное правило остановки на своей конечной области. Она не устанавливает полноту реального UseSummary, корректность IR extraction либо невлияние произвольного кода.

R02 связывает представления ресурса с исполнимым исследовательским AST и автоматически извлекает UseSummary; полный контракт и границы приведены в [главе 05](05-executable-profile.md). Фактические результаты принадлежат ограниченному профилю. Они не доказывают преимущества языка или завершённость обязательственного worklist LNK-I01.

## 11. Граница исключения в R02

`EXCLUDED` означает сохранение полного исхода при неизменной программе и закреплённых предпосылках в сравнении двух допустимых состояний OBS-0.1. Исход включает значение либо ошибку и упорядоченную трассу. Одинаковая ошибка тоже может быть сохранённым исходом: из исключения не следует работоспособность или satisfaction требования.

Изменённое/добавленное требование остаётся `OPEN`; удалённое — `REMOVAL_OPEN`. Старое неизменное требование имеет `UNCHANGED_UNASSESSED`. Изменение кода, конфигурации или провайдера требует пересмотра даже при неизменных данных. Неполный use имеет приоритет `UNKNOWN` над исключением. Проверка ограниченных преобразований программ и их сохраняющих законов перенесена в R03; она не будет опираться только на совпадение нескольких запусков.
