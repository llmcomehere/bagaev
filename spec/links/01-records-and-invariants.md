# LNK-0.2 · Записи, свойства и инварианты

**DRAFT · 22 октября 2026.** Владельцы согласования: T02/T03/T05/T08. [Вход в ТЗ](README.md). Документ уточняет [модель программы](../architecture/01-program-model.md), сохраняя разделение исходников, смысловых обязательств, исполнения и свидетельств.

## 1. Предлагаемое устройство

Канонический граф хранит типизированные отношения между точными ревизиями. Источники фактов — поддержанные операции IR, явные декларации и наблюдения исполнения; их происхождение различается. Прямой и обратный индексы дают доступ к тем же отношениям. Самостоятельно редактируемого «обратного ребра» нет.

Рядом со связью хранится описание использования: какие гарантии поставщика нужны конкретному потребителю. Полное описание использования позволяет остановить распространение отдельных изменений. Неполное описание расширяет область рассмотрения.

Граф программы и граф зависимостей анализатора — разные структуры. Первый содержит, например, `Export reads Authorship`. Второй сообщает, какие исходники, реестры, конфигурации и результаты запросов использовал анализатор при получении этого отношения. Изменение второго графа определяет, когда пересчитывать первый.

## 2. Идентичность и поколения

| Обозначение | Точный смысл |
| --- | --- |
| `EntityId` | Устойчивая идентичность сущности в пределах явно определённого пространства |
| `RevisionRef` | EntityId и точная неизменяемая ревизия определения |
| `ArtifactRef` | Вид, версия формата и хеш канонических байтов артефакта |
| `GraphRef` | Ссылка на неизменяемое содержимое графа, отчёта покрытия и метаданных извлечения |
| `GraphGeneration` | Согласованный набор GraphRef и построенных для него индексов; публикация отдельно делает его доступным через текущий указатель |
| `ScopeRef` | Зафиксированная область анализа: корни, реестры, пакеты, конфигурация, границы доступа и внешнего мира |
| `SnapshotId` | Снимок программы, выбирающий согласованные source/IR/contract/schema/graph refs |

Переименование сохраняет EntityId. Равные байты двух объектов не объединяют их предметную идентичность. GraphRef идентифицирует содержимое; generation задаёт согласованность обслуживающих индексов. Хеш не доказывает истинность полученного утверждения.

В [Unison](https://www.unison-lang.org/docs/the-big-idea/) определение адресуется хешем синтаксического дерева, а имя хранится отдельно. Для bagaev используем полезное разделение имени и неизменяемого содержимого, сохраняя дополнительный стабильный EntityId для эволюции предметной сущности. Это выбранная комбинация, не заявление о новизне адресации.

## 3. Каноническое отношение

Существующая `Edge` расширяется через qualifiers и ссылки на вспомогательные неизменяемые записи:

| Поле | Требование |
| --- | --- |
| `edge_id`, `edge_revision` | Однозначная идентичность записи; происхождение переходов сохраняется |
| `kind` | Один поддержанный вид: calls, reads, writes, emits, consumes, implements, requires, checks, derived_from, supersedes |
| `source_ref`, `target_ref` | Точные ревизии; типы концов проверяются правилом отношения |
| `site_ref` | Операция IR/декларация, из которой получена связь; для наблюдения — место в трассе |
| `qualifiers.use_ref` | Ссылка на UseSummary, если потребление свойств определено |
| `qualifiers.guard_ref` | Условие существования зависимости и область его оценки |
| `qualifiers.modality` | possible, established_for_scope либо observed; наблюдение не заменяет консервативный статический охват |
| `provenance_ref`, `input_refs[]` | Кто и каким правилом получил отношение, на каких точных входах |
| `coverage_ref` | Поддержанные конструкции, границы, пробелы и область вывода |

Несколько мест использования одного ресурса сохраняют отдельные site/provenance. Агрегированная выдача может объединять их для интерфейса, но обязана сохранять пути к исходным записям. Неизвестная цель представляется специальной записью/Gap, не обычной сущностью с произвольно назначенным ID.

Структурное утверждение «в декларации указан implements» точно устанавливает наличие декларации. Содержательное утверждение «реализация выполняет требование» требует отдельного свидетельства.

## 4. Используемое свойство и представление ресурса

Предлагается выражать доступ к смысловому ресурсу через типизированные операции/представления. Примеры для авторства: количество авторов, множество участников, упорядоченные участники, отображаемые подписи. Это проект интерфейса, не утверждённый синтаксис.

Операция, получившая только количество, не должна иметь скрытый доступ к порядку или полному объекту. Если полный объект утекает через alias, callback, FFI или неизвестную операцию, узкое описание использования теряет основание. Обычные методы доступа могут реализовывать такие представления, если их контракты и эффекты проверяемы.

| `UseSummary` | Содержание |
| --- | --- |
| `consumer_ref`, `provider_ref`, `site_refs[]` | Точная реализация потребителя, поставщик и места использования |
| `obligation_refs[]` | Конкретные обязательства, относительно которых оценивается достаточность |
| `observation_model_ref` | Версия модели наблюдений: значения, ошибки, эффекты, порядок, завершение и учитываемые ресурсы |
| `facet_registry_ref`, `used_facets[]` | Словарь наблюдаемых свойств и консервативное множество используемых свойств |
| `guard_ref`, `domain_ref`, `frame_ref` | Условие, допустимые входы и границы затрагиваемого состояния |
| `completeness_basis_refs[]` | Проверяемые основания полноты, привязанные к конкретным входам и правилу |
| `assurance` | declared, observed, checked либо unknown; статус checked выдаёт разрешённый проверяющий механизм |
| `unresolved_channels[]` | Неучтённые чтения, эффекты, выходы, alias и внешние взаимодействия |

Набор facets — верхняя оценка всех свойств, значимых для выбранного наблюдения. Поле нельзя сузить вручную и получить тем самым разрешение исключить компонент. Если полнота не установлена, анализ использует `TOP`: изменение может затрагивать любой значимый аспект.

Встроенный `checked` относится только к уже существующим входам IR/контрактов и правилу предварительного анализа. Применимость такого результата к готовому snapshot устанавливается внешней оценкой; обратная ссылка на ещё не созданный snapshot запрещена. Проверка одного `obligation_ref` не закрывает остальные обязательства и изменение выходных наблюдений потребителя.

В [MLIR](https://mlir.llvm.org/docs/Rationale/SideEffectsAndSpeculation/) эффекты описываются относительно ресурсов, а особенности спекулятивного выполнения учитываются отдельно. Это полезная опора для явных взаимодействий; такое описание само по себе не решает задачу бизнес-свойств и точного alias-анализа bagaev.

## 5. Словарь свойств и описание изменения

Facet имеет ID, ревизию определения, функцию наблюдения либо формальное свойство, область применимости и правила совместимости/включения. Разные названия facets не доказывают независимость. Словарь должен задавать допустимое правило разделения наблюдений и зависимости между свойствами.

Для небольшого опыта можно зафиксировать наблюдения `member_set`, `ordered_members`, `cardinality`, `display_labels`. Перестановка может сохранить множество и количество, меняя порядок. Добавление человека меняет состав; равенство остальных наблюдений требуется установить отдельно. Смена схемы может менять доступность операции, ошибки или допустимый вход, даже если демонстрационные значения совпадают.

`DeltaSummary` содержит base/target refs, выбранную область, observation model и facet registry, `possibly_changed_facets`, отдельно установленные сохранённые свойства, методы получения и `unknown_channels`. Полный верхний охват означает: за пределами possibly_changed не изменилось ни одно наблюдение, значимое в объявленной области. Утверждение ограничено проверенной моделью.

Для произвольной правки тела функции безопасное исходное значение — TOP. Неизменная сигнатура, похожий текст или объяснение LLM не устанавливают семантическую эквивалентность. Узкое изменение допускается по проверяемому правилу поддержанной операции или отдельному достаточному основанию сохранения остальных свойств.

Контракт изменения определяет разрешённую задачу. Он не является автоматически полным описанием фактического delta. Любое изменение предпосылок, ошибок, разрешений, схемы или внешней конфигурации включается в анализ либо остаётся unknown.

## 6. Условия существования связи

`Guard` содержит выражение в поддержанной логике, точные входы, область, метод оценки и результат true/false/unknown. Для первого профиля допустимо исключать ветвь по зафиксированному параметру сборки или конфигурации в определённом snapshot.

False сохраняет зависимость от входов условия. Смена конфигурации пересматривает вывод. False, наблюдавшийся в одном запуске, не исключает ветвь для всех запусков. Для runtime-зависимого или неизвестного условия статический граф сохраняет возможную связь. Доказанная невозможность во всей нужной области требует отдельного основания с этой областью.

Нетронутый исходник при изменении config/extractor/пакета может породить другой граф. Хеш одного файла недостаточен для повторного использования анализа.

## 7. Происхождение запроса, включая пустой результат

`QueryRecord` хранит query definition revision, параметры, GraphRef/ScopeRef, результат, gaps, статус покрытия и `QueryFootprint`. Кеш запроса находится вне snapshot. Повторное использование создаёт оценку применимости к целевой версии; историческая запись не переписывается.

`QueryFootprint` включает прочитанные значения, выполненные подзапросы, условия ветвления, **состав перечисленных коллекций**, проверенные признаки всех рассматривавшихся кандидатов, lookup misses и ограничения доступа. Если результат пуст, footprint всё равно должен описывать, где и по каким правилам искали.

Отдельная `NoMatchObservation` фиксирует query ref, пустой результат и его область. Это наблюдение отсутствия совпадения в определённом поиске. Для заключения об отсутствии зависимости дополнительно нужны полнота модели отношений, покрытие, действующие предпосылки и нужный класс основания по политике.

Первый вариант использует консервативные stamps всей области и её анализируемых проекций. Позднее допустимы индексы диапазонов, если обновление записи, переставшей либо начавшей удовлетворять предикату, обязательно меняет нужный stamp. Подробный алгоритм дан в [следующей главе](02-extraction-and-refresh.md).

## 8. Snapshot, свидетельства и отсутствие циклов

Порядок построения: точные исходные определения → типизированные артефакты → структурные отношения и анализ их входов → GraphRef → SnapshotId. Запись внутри графа не содержит будущий ID этого snapshot.

Предварительный результат статического анализа может связываться с уже имеющимися IR/contract/config refs. Поздние EvidenceRecord, EvidenceAssessment, QueryRecord и AcceptanceRecord ссылаются на готовый snapshot извне. Они не меняют хеш проверяемой программы.

Наличие полного индекса не доказывает полноту покрытия. Наличие полного покрытия не доказывает выполнение требования. Наличие подходящего свидетельства не предоставляет полномочия выполнить изменение или внешний эффект.

## 9. Инварианты подсистемы

1. Каждый опубликованный индекс построен для того же GraphRef и generation, что обслуживаемый запрос.
2. Для каждой канонической Edge есть согласованное прямое и обратное представление; тип и происхождение сохраняются.
3. Старые ревизии доступны для исторического запроса, пока действует объявленная политика хранения.
4. Пустой результат не имеет пустого footprint, если запрос выполнял перечисление или проверку отсутствия.
5. Добавление элемента и изменение признака ранее неподходящего элемента пересматривают зависимый поиск.
6. Область запроса и область вывода различимы; непокрытые механизмы и скрытые входы сохраняются.
7. Недоказанный footprint либо delta расширяется до TOP; unknown не становится независимостью.
8. Два разных facet ID не считаются независимыми без общего правила наблюдений.
9. Изменение guard, extractor, формата, политики или config входит в invalidation.
10. Неизменность результата анализатора сравнивается вместе с покрытием, gaps и значимой метаинформацией.
11. Для основания остановки проверяется точное обязательство, область и действительность всех предпосылок.
12. Принятие кода и активация runtime остаются отдельными операциями по прежнему контракту.

## 10. Открытые интеграционные решения

До принятия нужны: полная таблица IR→relation/use; хранение ID в исходнике; точная модель alias/FFI; семантика поддержанных представлений и facets; формат машинно проверяемого completeness basis; политика access-sensitive queries; реализация атомарной публикации; стоимость stamps на больших проектах. Эти вопросы имеют владельцев в T02/T03/T05/T08/T09/T12 и не закрываются успехом ограниченной Python-модели.

## 11. Уточнение R02: зависимые наблюдения

В исследовательском [OBS-0.1](05-executable-profile.md) порядок, множество и количество определяются функциями одного состояния ресурса. Delta получается сравнением результатов этих функций на конкретной паре состояний; имена наблюдений не трактуются как независимые координаты. Ошибка чтения входит в результат наблюдения. Равенство значений на примерах не является основанием для произвольного изменения схемы или кода провайдера.

Use автоматически извлекается из закрытого типизированного AST. Он сохраняет strict initializer, условия, обе ветви, возможные ошибки и эффекты. Данные `Consumer` фиксируются глубоко, а AST, полная конфигурация, revision провайдера, требования и revision профиля входят в основания применимости. OBS-0.1 не реализует все записи и полномочия общей схемы этой главы.
