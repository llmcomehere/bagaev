# LNK-0.2 · Исполнимый исследовательский профиль OBS-0.1

**DRAFT · R02 · 22 октября 2026.** Профиль конкретизирует получение UseSummary из программы и проверку сохранения наблюдений. Он не является синтаксисом или реализацией существующего bagaev. Владельцы интеграции: T03/T04/T05/T08/T09. [Вход в ТЗ](README.md).

## 1. Предмет и граница

Вход — конечное дерево выражений в JSON, закрытая семантика операций, точная конфигурация, привязка поставщика и ссылки на требования. Дерево проверяется по типам и исполняется над неизменяемым состоянием ресурса. Из этого же дерева отдельный проход автоматически выводит описание нужных наблюдений. Готовый список зависимостей не является доверенным входом обычного анализа.

Конкретный формат API и диагностики реализации закреплён в [API.md](../../models/r07-core/experiments/observation-profile/API.md); исполнение и анализ — в [engine.py](../../models/r07-core/experiments/observation-profile/engine.py). Они образуют проверяемый исследовательский профиль. Полный IR языка, текстовый parser, линкер, рекурсия, изменяемая память и произвольный FFI в него не включены.

## 2. Ресурс и наблюдения

Состояние Authorship содержит упорядоченные уникальные строковые ID участников и необязательную ошибку чтения. Отсутствие ресурса представляется отдельно. Пустой доступный список разрешён в исследовательском домене для проверки ошибок и требований непустоты; это не меняет предметный инвариант основного опыта T15.

| Наблюдение | Доступный ресурс | Отсутствие или ошибка чтения |
| --- | --- | --- |
| `ordered_members` | Последовательность ID в исходном порядке | Точный исход ошибки |
| `member_set` | Множество тех же ID | Точный исход ошибки |
| `count` | Число ID | Точный исход ошибки |
| `read_status` | Успех | Точный статус ошибки |

Наблюдения значений тотализируются: ошибка является частью сравниваемого исхода. Отсутствующий ресурс не подменяется доступным пустым списком. `read_status` позволяет явно наблюдать статус без получения самого представления.

Множество и количество определяются последовательностью; при уникальности участников количество определяется множеством. Произвольное пересечение имён независимых facets не используется. Для конечного ресурсного перехода вычисляются сами функции наблюдения на обеих сторонах.

## 3. Выражения и исполнение

Закрытый формат конструкторов AST, имена полей и правила типов приведены в API.md. Int-литералы ограничены signed 64-bit; строки содержат Unicode scalar values. Нарушения дают `INTEGER_OUT_OF_RANGE` / `INVALID_UNICODE_SCALAR` до хеширования или исполнения. Группы операций имеют следующие правила:

| Операции | Правило |
| --- | --- |
| Константа, локальная переменная | Проверенный тип значения; лексическое разрешение имени |
| Чтение представления | Чтение выбранного наблюдения; определённая ошибка недоступности |
| Чтение config | Только объявленный закреплённый логический параметр |
| `let` | Строгое вычисление initializer, затем тела в расширенном окружении |
| `if` | Логическое условие, одинаковый тип ветвей, выполнение только выбранной ветви |
| `contains`, `size`, `to_set`, `head`, `eq` | Закрытые детерминированные операции с проверенными типами аргументов |
| `pair`, `tuple`, `seq` | Определённый порядок вычисления; seq возвращает последний результат |
| `emit` | Вычисление значения, добавление события в локальную упорядоченную трассу, продолжение |
| `fail` | Определённая ошибка, останавливающая дальнейшее вычисление |
| `opaque` / `unknown` | Явный выход за закрытую семантику; неполное исполнение и TOP в анализе |

`head` пустой последовательности имеет определённую ошибку. Ошибка в initializer не исчезает от неиспользования связанного имени. Если ошибка возникла после emit, уже полученная трасса сохраняется; ошибка при вычислении значения emit не добавляет событие. Opaque не исполняет произвольный host-код.

Наблюдаемый результат включает статус, значение либо ошибку, упорядоченную трассу и полноту исполнения. Два неполных исхода не считаются достаточным доказательством одинакового поведения. Сохранение только возвращаемого значения не позволяет игнорировать ошибку или эффект.

## 4. Автоматический проход use

Исходный вариант выводит общую консервативную границу для всей наблюдаемой трассы. Он не обещает минимальное множество зависимостей.

```text
infer_use(node, lexical_environment):
    typecheck node and its required inputs
    const                  -> empty
    read(view)             -> need(view, read outcome)
    var(name)              -> no new resource read; initializer is retained by let
    let(name, init, body)  -> union(use(init), use(body with binding))
    if(c, a, b)            -> union(use(c), use(a), use(b))
    closed operation      -> union(use of all evaluated operands)
    emit(value, next)     -> union(use(value), use(next))
    opaque / unknown      -> TOP with an explicit reason
```

Условие и обе runtime-ветви входят в статическое описание. Наблюдение одной выбранной ветви не заменяет этот охват. Для let и seq сохраняются зависимости исполняемых подвыражений, включая ошибки и эффекты результата, который далее не используется.

В этом проходе переменная читает уже вычисленное локальное значение. Её источник учтён строгим initializer окружающего let, поэтому отдельная операция var не добавляет нового чтения ресурса. Анализ открытого тела отдельно от его связывания не поддерживается; при будущей модульной мемоизации окружение станет явным входом.

На старте нет сужающего переписывания `size(read(ordered_members))` в `read(count)`. Первое выражение может иметь более широкое описание, чем второе. Такое ложное включение в область проверки допустимо; ложное исключение — дефект. Проверенные законы переписывания могут быть добавлены отдельным решением с учётом ошибок и эффектов.

## 5. Точный ресурсный delta

```text
exact_delta(before, after):
    validate the common resource domain
    for observation in the fixed registry:
        record observe(before), observe(after), and their equality
    return complete comparison of this exact state pair
```

Полнота здесь означает полный перечень наблюдений данного профиля для конкретной пары состояний. Это не вывод семантической разницы произвольного кода и не доказательство поведения на всех будущих входах.

Для неизменной закрытой программы достаточный критерий сохранения её наблюдаемого исполнения — равенство каждого наблюдения из автоматически полученного use при одинаковых внешних предпосылках. Исследовательская записка содержит структурный аргумент и границу его подтверждения.

## 6. Применимость и результат решения

Consumer имеет устойчивый ID, точную ревизию канонического AST, зафиксированную конфигурацию, ревизию привязки поставщика и точные ссылки на требования. Ревизия AST вычисляется из содержания; служебное имя не подменяет версию. Метод анализа и observation registry также являются предпосылками.

| Условие | Допустимый результат |
| --- | --- |
| Программа закрыта, контекст совпадает, все нужные наблюдения равны | Исключение нового влияния этого ресурсного перехода |
| Нужное наблюдение изменилось | RECHECK; это ещё не доказательство дефекта |
| Код, config или provider изменились без отдельного основания эквивалентности | Консервативный пересмотр |
| Новый, изменённый или удалённый requirement ref | Отдельное открытое обязательство |
| Неполный use или opaque-канал | UNKNOWN/TOP |
| Неверный тип или неподдержанный формат | Диагностика; не успешный пустой граф |

Исключение влияния не означает удовлетворённость требования. Этот профиль не принимает программу, не выдаёт capability и не активирует runtime. Требования в нём представлены точными ссылками; их свободный текст не интерпретируется как автоматически истинный предикат.

## 7. Автоматическое извлечение проекта и актуализация

Project задаёт конечный реестр потребителей. Извлечение самостоятельно проходит их AST, получает use и строит отношения к ресурсу. Константный потребитель может не иметь отношения чтения; opaque-потребитель оставляет gap, даже если явного read нет.

Изменение существующего nonconsumer в consumer, новый consumer и удаление consumer учитываются текущим реестром и ревизиями программ. Поддержанный incremental путь повторно использует summary при равенстве полного stamp конкретного потребителя: AST, закреплённого config, provider, requirements и версии профиля. Реестр проекта перечисляется заново, удалённые записи не копируются. Перед reuse старый граф проверяется полным извлечением, поэтому счётчик reuse не означает ускорения всей операции. Это консервативная реализация проверки применимости.

Старые и новые отношения сохраняются для анализа удаления. Исчезновение чтения из нового AST не закрывает прежнее обязательство потребителя и не позволяет забыть его старый путь. Согласованность full/incremental проверяется отдельно от наблюдаемой семантики.

## 8. Приёмка исследовательского фрагмента

Фактические результаты находятся в [отчёте R02](../../models/r07-core/results/observation-profile/report.json). Должны выполняться независимые группы проверок:

1. Ручные ожидаемые значения, ошибки, трассы и решения для ключевых программ.
2. Согласованность основного интерпретатора с [независимым oracle](../../models/r07-core/experiments/observation-profile/oracle.py), который не импортирует engine.
3. Для всех исключённых переходов объявленного конечного корпуса — равенство полного наблюдаемого исполнения по oracle.
4. Наличие полезных исключений: перестановка сохраняет прямые представления множества и количества, сохраняя необходимость рассмотрения порядка.
5. Версии кода/конфигурации/поставщика/требования и изменения реестра не теряются из актуализации.
6. Намеренные ошибочные политики действительно дают отличающийся неверный вывод.

Отчёт сохраняет хеши файлов, область перебора, реальные количества решений и контрпримеры ошибочных политик. `research_ast_execution=true` относится только к этому профилю; `bagaev_execution=false` и `hypothesis_tested=false` сохраняются. Успех R02 не объявляет завершёнными T03/T04/T05/T08/T09 или сквозной T15.

## 9. Следующий вопрос

Для дальнейшего сужения после правок кода нужны проверяемые правила сохранения наблюдений, действующие на всей объявленной области входов. Совпадение на конечных примерах не должно становиться таким правилом. Следующая итерация должна определить хотя бы один ограниченный закон преобразования, его предпосылки и отказ при изменении ошибок/эффектов; композиция нескольких потребителей потребует отдельного переноса этих оснований.
