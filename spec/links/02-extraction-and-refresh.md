# LNK-0.2. Извлечение и обновление связей

**Статус: DRAFT.** Это проект контракта для ограниченного профиля V1, а не описание готовой реализации или завершение T08. Слова «должен» и «запрещено» задают требования к будущей реализации. Согласование: [записи и инварианты](01-records-and-invariants.md), [влияние и контекст](03-impact-and-context.md).

## 1. Область и результат

Подсистема строит канонический неизменяемый `GraphGeneration` из зафиксированных исходных артефактов, конфигурации и определений извлекателей. Прямые и обратные индексы — представления одного набора `Edge`, а не независимо редактируемые источники истины. Обновление создаёт новое поколение; историческое не переписывается.

Предметный граф отношений программы отличается от графа зависимостей вычисления запросов. Последний нужен для инвалидирования кэша. Обход уже известных предметных рёбер не заменяет поиск новых источников и потребителей.

В V1 используются консервативные токены всей проверяемой коллекции. Точные интервальные и многомерные зависимости допускаются позднее, после определения и проверки правил их обслуживания. Стоимость обновления может достигать стоимости полного извлечения поддержанного профиля; гарантии малой области пересчёта нет.

## 2. Входы, происхождение и хеширование

`SourceManifestRef` адресует неизменяемое описание исходников/IR, идентичностей, схем, реестров входов, locks и конфигурации. Манифест не включает создаваемый граф и будущие свидетельства. Чтение несогласованно меняющейся рабочей папки не удовлетворяет этому контракту.

Извлекатели выполняются детерминированно через отслеживаемый API чтения. Время, случайность, сеть и живое runtime-состояние недоступны как неявные входы. Необходимое наблюдение сначала фиксируется отдельным входным артефактом с областью и версией. Пользовательский runtime-код ради извлечения произвольно не исполняется.

| Источник | Смысл связи | Ограничение |
|---|---|---|
| `structural` | Вывод поддержанного анализа исходника/IR | Полнота только относительно профиля, области и допущений |
| `declared` | Явная декларация человека или модели | Сохранение декларации не подтверждает её истинность |
| `observed` | Событие конкретного исполнения | Не исключает другие возможные исполнения |

Каноническое происхождение содержит метод, версию производителя и точные входы. Время запуска, cache hit, адрес процесса и порядок планирования остаются внешними метаданными. Новое свидетельство о существующем snapshot не меняет граф внутри него. Встроенная ссылка на наблюдение допустима только на уже существующий входной артефакт, без цикла через создаваемый snapshot.

Порядок построения: `SourceManifest → Edge/coverage → GraphGeneration → Snapshot`. Query records и evidence находятся вне этой цепочки и ссылаются на уже известные `GraphRef`/`SnapshotId`. Граф не содержит обратной ссылки на кэш, включающий его собственный хеш. Хеширование использует каноническую сериализацию из общей спецификации; тестовый oracle сравнивает также канонические значения, а не только отпечатки.

## 3. Записи запросов

Схема `Edge` и `GraphGeneration` определяется соседним документом. Следующие записи обслуживают вычисление и хранятся **вне snapshot**; их потеря должна приводить к пересчёту, а не потере семантики.

| Запись | Обязательные поля |
|---|---|
| `QueryDefinitionRef` | `query_id`, `definition_version`, `code_hash`, `result_schema_ref` |
| `QueryKey` | `definition_ref`, канонические `arguments` |
| `QueryFootprint` | `source_manifest_ref`, `ordered_reads[]`, `extractor_ref`, `config_ref`, `profile_ref`, `closure_status` |
| `QueryResult` | `value`, детерминированное `provenance`, `coverage`, `gaps[]` |
| `QueryCacheRecord` | `record_id`, `graph_ref`, `query_key`, точные версии входов и условий, `result_ref`, `footprint_ref` |
| `ReuseRecord` | исходная запись, целевые `source_manifest_ref` и `graph_ref`, проверенные наблюдения |

До запечатывания используются внутренние staging-записи без выдуманного `GraphRef`. После вычисления канонического графа создаются внешние привязки к полученному `GraphRef`; старые записи сохраняют прежний предмет.

`closure_status=tracked` означает, что все внешние чтения данного вычисления прошли разрешённый API. `unknown` не разрешает переиспользование. Отсутствующий авторский список зависимостей не доказывает независимость: footprint формируется инструментированным выполнением, а не доверием к пустой декларации.

Ключ запроса использует стабильную идентичность предмета и явные аргументы. Целевой манифест задаёт контекст выполнения; его смена не должна автоматически превращать каждый прежний запрос в несопоставимый ключ. Однако значение аргумента, действительно являющегося точной ревизией, нельзя подменять логическим именем ради попадания в кэш. Переименование имени, переназначение alias и исчезновение сущности проходят через соответствующие отслеживаемые таблицы. Номер выделения объекта в памяти не служит межсессионным идентификатором.

### 3.1. Типы наблюдений

| Наблюдение | Состав |
|---|---|
| `ValueRead` | Ключ входа, точный `ArtifactRef/RevisionRef`, наблюдавшийся токен |
| `LookupRead` | Коллекция, ключ, версия слота, `present(ref)` либо `absent` |
| `CollectionRead` | Коллекция, selector/projection refs, membership token, selector-content token, projection-content token |
| `QueryRead` | Ключ подзапроса, наблюдавшийся канонический результат |

`membership_token` меняется при вставке, удалении и изменении ключа кандидата. Content tokens покрывают значения, читаемые selector и projection, **для всех проверенных кандидатов**, включая несовпавшие. В V1 оба content token равны консервативному токену полного содержимого коллекции. Изменение прежнего nonconsumer в consumer инвалидирует пустую выборку, даже если набор ключей прежний.

Ключевой инвариант: если изменение может изменить выборку, должно измениться хотя бы одно её наблюдаемое основание. Хеш только возвращённых элементов этому инварианту не удовлетворяет. Для derived-индекса требуется такая же зависимость от исходной коллекции; индекс не может подтверждать собственную полноту одним своим номером.

Токен определяется содержимым и схемой конкретной коллекции либо адресует её неизменяемую версию. Счётчик, который можно сбросить после перезапуска, недостаточен. Чтение размера, существования элемента, первого элемента или порядка также считается чтением коллекции. Для сортированной выборки в содержимое входят ключ сортировки и правило разрешения равенства. Для нескольких коллекций записываются основания каждой стороны соединения, включая сторону, пока не давшую ни одного совпадения.

## 4. Корни, отсутствие и условия

`enumerateRoots` — отслеживаемый запрос, читающий полный реестр потенциальных входов, конфигурацию отбора и реестр извлекателей. Новый модуль, новое определение производителя либо изменение исключений должны приводить к рассмотрению нового набора корней. Выходы удалённых корней не копируются в текущее поколение.

Lookup miss сохраняется как чтение слота: вставка по этому ключу инвалидирует `absent`. Пустой range/selector сохраняет `CollectionRead`, определение запроса и описание покрытия. Отрицательное наблюдение допустимо представить как `NegativeDependency(kind, query_key, footprint_ref)`; самостоятельный бесконтекстный факт «ребра нет» запрещён.

`whyNot` возвращает один из различимых результатов: `none_in_declared_scope`, `outside_scope`, `incomplete`, `unsupported`. Первый разрешён только для завершённого поддержанного запроса в точной области. Для кандидата вне разрешённой области доступа нельзя сообщать ложный `none_in_declared_scope`; ответ сохраняет ограничение видимости без раскрытия скрытого содержимого.

Описание покрытия обязано назвать перечень поддержанных конструкций, границы внешних ресурсов и правило перечисления кандидатов. Фраза «проверены все найденные файлы» недостаточна без основания полноты самого перечисления. Пробел должен указывать затронутую область и виды выводов, которые он не позволяет делать. Неподдержанная конструкция внутри требуемой области сохраняется как пробел даже тогда, когда известная часть анализа нашла полезные положительные связи. Удаление пробела требует нового основания или явного изменения согласованной области задачи.

Установленный `false` разрешает исключить отношение только для **зафиксированной конфигурации** данного профиля. Конфигурация и правило вычисления guard входят в footprint. Runtime-условие или неизвестный guard сохраняют потенциальную связь `may`. Отсутствие события в наблюдавшейся трассе не удаляет структурную потенциальную связь.

PUG обосновывает полезность явного домена для объяснения отсутствующих ответов; здесь это применено как ограничение области `whyNot`, без переноса полноты SQL/Datalog на произвольную программу: <https://arxiv.org/pdf/1808.05752.pdf>, §4.1–4.3.

## 5. API и ошибки

Названия обозначают проект интерфейса, а не существующие команды.

| Операция | Вход | Выход |
|---|---|---|
| `extractFull` | SourceManifestRef, locks, профиль, budget | TentativeBuild: результаты, coverage, gaps, frontier |
| `refresh` | Прежний GraphRef, целевые входы, locks, budget | TentativeBuild и причины переиспользования/пересчёта |
| `inspectQuery` | Точный GraphRef, QueryKey, допустимая область, budget | Result, coverage, gaps; при незавершении frontier |
| `publish` | build_id, target_slot, expectedGraphRef, expectedSourceManifestRef, operation_id | Атомарный receipt либо конфликт |

| Код | Значение и восстановление |
|---|---|
| `STALE_SOURCE` / `STALE_GRAPH_HEAD` | Guard публикации не совпал; выбрать актуальные входы и пересчитать необходимые основания |
| `GENERATION_MISMATCH` | Граф и индекс/обязательная проекция разных поколений; перечитать единый bundle |
| `CACHE_UNUSABLE` | Неверный формат, повреждение или непроверяемые входы кэша; разрешён полный пересчёт |
| `UNTRACKED_READ` / `UNSUPPORTED_QUERY` | Внешнее чтение вне API либо неподдержанный запрос; явный отказ/пробел |
| `QUERY_CYCLE` / `INVALID_EDGE` | Неопределённая рекурсия запросов либо нарушение схемы отношения; исправить производителя |
| `BUDGET_EXCEEDED` | Сохранить frontier; не превращать частичный результат в отрицательный ответ |
| `OPERATION_KEY_REUSED` | Идентификатор публикации повторён с другими аргументами; прежний receipt не применим |
| `INCOMPLETE_COVERAGE` | Есть пробелы; нельзя использовать результат для требующего полноты исключения |

Публикация поколения не означает принятие изменения программы или разрешение эффекта. `inspectQuery` не изменяет пользовательскую программу и не исполняет её эффекты; служебное заполнение кэша не меняет содержимое snapshot.

## 6. Валидация и повторное выполнение

```text
ensure(key, target, cache, budget):
    fail QUERY_CYCLE if key is on evaluation stack
    charge(budget)
    if currentStage already contains key: return its result
    old := cache.lookup(key)
    if old is intact and all definition/config/extractor versions match
       and old.footprint.closure_status == tracked:
        valid := true
        for observation in old.ordered_reads:
            now := validateObservation(observation, target, ensure)
            if now is different or unknown:
                valid := false
                break
        if valid:
            return stageValidatedReuse(old, target)
    fresh := executeThroughTrackedAPI(key, target, budget)
    validateResultSchema(fresh)
    replaceStageRecord(key, fresh.result, fresh.ordered_reads)
    return fresh.result

refresh(priorGraph, target, locks, budget):
    require immutable target and exact locks
    stage := isolatedBuild(target)
    roots := ensure(rootInventoryKey, target, priorCache, budget)
    for root in stableOrder(roots): ensure(root, target, priorCache, budget)
    active := reachableFromCurrentRoots(stage.queryRecords)
    result := assemble(active.currentResults)
    require all required queries finished
    bundle := canonicalGraphAndIndexes(result)
    require exactForwardReverseAgreement(bundle)
    return sealTentative(bundle, result.coverage, result.gaps)
```

`validateObservation` сравнивает актуальные токены базовых входов; для `QueryRead` сначала обеспечивает актуальность подзапроса. Проверка прежних чтений идёт в записанном порядке и прекращается на первом изменившемся основании: последующие ветки могут стать ненужными.

После повторного выполнения footprint **полностью заменяется**, даже если result не изменился. Разрешённое backdating сравнивает `value + provenance + coverage + gaps`, а не только набор рёбер. Изменившийся gap не исчезает из-за равенства положительных результатов. Зависимости от старой ветки не остаются текущими по причине равенства результатов; история сохраняется отдельно.

При переносе результата его исходное происхождение остаётся исходным. Новая запись валидации указывает целевой манифест и проверенные условия переноса; она не выдаётся за новый запуск извлекателя. Если меняется доступная пользователю часть объяснения, меняется и соответствующий результат запроса. Разделение результатов на независимо наблюдаемые проекции может уменьшить пересчёт, но требует отдельных явно определённых ключей и сравнений. По умолчанию V1 сравнивает весь описанный результат.

Эта организация согласуется с механизмом смены динамических зависимостей Adapton (§5.2): <https://matthewhammer.org/adapton/adapton-pldi2014.pdf>. Остановка распространения при равном результате опирается на red–green-подход Salsa: <https://salsa-rs.github.io/salsa/reference/algorithm.html>. Для bagaev это требование к проектируемой реализации, не полученная автоматически гарантия библиотеки.

## 7. Атомарное поколение

До публикации граф и индексы приватны для build. Читатель выбирает один `GraphRef` и удерживает его на протяжении запроса; чтение «последнего индекса» независимо от выбранного графа запрещено.

```text
publish(build, slot, expectedGraph, expectedSource, operationId):
    require build is sealed and its referenced objects are durable
    atomically:
        if receipt exists for operationId:
            require identical request else OPERATION_KEY_REUSED
            return receipt
        require slot.source == expectedSource == build.source else STALE_SOURCE
        require slot.graph == expectedGraph else STALE_GRAPH_HEAD
        slot.graph := build.GraphRef
        persist receipt(operationId, requestDigest, build.GraphRef)
    return receipt
```

Сбой до атомарного переключения оставляет прежнее поколение доступным. После состоявшегося переключения потерянный ответ восстанавливается по receipt; новое извлечение не требуется лишь из-за потери ответа. Неполный build сохраняется для продолжения без публикации как завершённого. Завершённое извлечение с явными coverage gaps может быть доступно для инспекции, но не получает статус полного покрытия.

Возврат прежнего receipt подтверждает исторически выполненную публикацию; он не утверждает, что это поколение всё ещё является текущим. Смена head другой операцией не отменяет запись. Чтение receipt подчиняется действующему доступу. Конкретный способ атомарности — транзакционное хранилище либо журнал — должен обеспечить совместную видимость указателя и receipt; файл со случайно записанным новым номером поколения этому требованию не соответствует.

## 8. Терминация и conformance

V1 требует конечного манифеста, конечных коллекций и определённых завершающихся производителей. Цикл вычисления запросов без отдельной спецификации фиксированной точки отклоняется; циклы предметных отношений сами по себе разрешены. Учёт шагов, памяти и размера выдачи ограничивает неисправный производитель. Превышение бюджета оставляет неизвестность, а не успех.

Конечный корпус должен проверять минимум:

1. Пустую выборку, затем добавление нового потребителя через новый корень.
2. Прежний nonmatch, ставший match без изменения membership.
3. Lookup miss, затем вставку и удаление записи по тому же ключу.
4. Смену динамической ветки с равным результатом, затем изменение нового входа.
5. Смену extractor/config при прежних исходниках; появление связи либо нового gap.

После каждого шага строятся полный результат с пустым кэшем и incremental-результат. Сравниваются канонические отношения, qualifiers, provenance, coverage/gaps и ответы прямых/обратных/отрицательных запросов. Для одинакового определения производителя проверяется нормализованный footprint; разные истории, приводящие к одному манифесту, должны давать один результат. Полный путь не использует incremental-инвалидирование, иначе оба пути могут разделить одну ошибку.

Отдельные трассы проверяют crash до/после CAS, смешанное поколение, повреждение кэша и бюджет. Fault injection поочерёдно отключает membership, content nonmatches, обновление footprint и version guards: соответствующие контрпримеры обязаны обнаруживать ошибку. Результаты такого корпуса характеризуют только проверенные правила и входы. Статусы `IMPLEMENTED`, `VERIFIED` и завершение T08 из наличия этого документа или fixtures не следуют.


## 9. Проверенный исследовательский срез R02

[Исполнимый профиль](05-executable-profile.md) получает рёбра из AST каждого потребителя всего объявленного registry. Повторное использование summary требует полного равенства входного stamp данного потребителя. Новый manifest каждый раз охватывает весь текущий registry; удалённые рёбра остаются в объединении старого и нового графов для анализа.

Прежний граф проверяется полным повторным извлечением перед reuse. Это обеспечивает прозрачный исходный алгоритм для проверки корректности; экономия вычислений этим опытом не установлена. Здесь ещё нет tracked query DAG из разделов выше, durable публикации с восстановлением или доказанной полноты registry относительно реального репозитория. Эти различия не позволяют подставлять результат R02 вместо полной приёмки T08.
