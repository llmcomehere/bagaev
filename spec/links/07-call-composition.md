# 07. Композиция зависимостей через вызовы · R04

**LNK-0.4 · DRAFT · CALL-0.1.** Эта глава дополняет главы 01–06. Она задаёт исследовательский контракт статических вызовов и переноса use между несколькими потребителями. Полный язык V1 не сводится к этому профилю. Точные Python-записи и коды ошибок находятся в [API](../../models/r07-core/experiments/call-profile/API.md); выбор подхода — в исследовании.

## 1. Решаемая задача и граница

R02 получает use из одного закрытого AST. R03 уточняет его проверенными законами. Для реальной программы этого недостаточно: потребитель вызывает функцию, та — другую функцию, и изменение нижнего определения должно достигать всех затронутых потребителей. При этом нельзя потерять вычисление аргументов, перепутать версии определений или принять неизвестную зависимость за отсутствие зависимости.

CALL-0.1 добавляет к OBS-0.1 только статический типизированный вызов. Сохраняются один immutable Authorship, точная compile-config, встроенный provider/v1 и наблюдаемый результат OBS: статус, значение либо ошибка, упорядоченная trace, полнота. Время, память и число внутренних шагов в эту эквивалентность не входят. Предложения о ресурсных лимитах V1 должны быть оформлены отдельно; их нельзя вывести из этого опыта.

Не определяются динамический dispatch, closures, функции как значения, host I/O, рекурсивная семантика, persistent incremental cache и исполнение bagaev. Рекурсивная или внешняя граница остаётся явной неполнотой. Допустимы только ограниченные входы, перечисленные в API.

## 2. Исходные записи и пространства имён

`Program` состоит из одного `Consumer` и `Registry` определений. Consumer содержит stable ID, AST, compile-config, provider revision и requirements. Function содержит stable ID, упорядоченные параметры с типами, тип результата и тело. Отсутствующее тело означает объявленную внешнюю функцию. Отсутствующий ID в registry означает неразрешённый поиск; это другой случай.

Конструктор вызова имеет четыре обязательных поля:

```json
{"op":"call","target":"function-id","args":[],"type":"int"}
```

Target — точный stable ID. Он не вычисляется из строки во время исполнения. Аннотация `type` обязательна и для найденной, и для отсутствующей функции. При найденном определении проверяются арность, тип каждого аргумента, совпадение аннотации результата с сигнатурой и соответствие тела объявленному типу. При отсутствии определения аннотация позволяет продолжить структурный анализ, но не подтверждает существование функции или её поведение.

Локальные имена и stable IDs функций принадлежат разным пространствам. Аргументы видят caller scope. Тело функции видит только параметры и собственные lexical lets. Начальное значение let проверяется и вычисляется до добавления нового binding; shadowing не меняет предыдущую область видимости. Alias предназначен для представления пользователю и не участвует в наблюдаемой семантике этого профиля.

Входные записи глубоко фиксируются. Автоматически вычисленные revisions и stamps не заменяются присланным use или произвольной строкой с обещанием совместимости. Повторное создание записи через `dataclasses.replace` не обходит проверку.

## 3. Статическая проверка и прямое исполнение

### 3.1. Полнота проверки входа

`validate_program` проверяет entry и каждое объявленное тело, включая невыбранные ветви и неиспользуемые функции. Это отделено от выделения достижимых зависимостей. Корректная unrelated функция не расширяет use entry; некорректная функция в переданном registry вызывает диагностический отказ всего входа.

Для проверки тела достаточно сигнатур других функций. Проверка типов не требует рекурсивного раскрытия тел: повторный вызов не превращается в бесконечный type checking. Однако наличие достижимого цикла делает анализ поведения неполным. Недопустимый вход, неполный анализ и известная ошибка исполнения — разные результаты.

### 3.2. Порядок вычисления вызова

Прямой интерпретатор не исполняет результат expansion. Он работает с исходным CALL AST:

```text
evaluate_call(call, caller_env, active_body_calls):
    values := []
    for argument in call.args, from left to right:
        result := evaluate(argument, caller_env, active_body_calls)
        append result.trace to current trace
        if result is error or unknown:
            return result with accumulated trace
        append result.value to values

    definition := lookup(call.target)
    if missing: return unknown MISSING_CALLEE with accumulated trace
    if external: return unknown EXTERNAL_CALLEE with accumulated trace
    if target already in active_body_calls:
        return unknown CALL_CYCLE with accumulated trace

    callee_env := bind definition.params to values
    return evaluate(definition.body, callee_env,
                    active_body_calls plus target), preserving trace
```

Каждый аргумент вычисляется один раз, даже если параметр не используется либо используется несколько раз. Ошибка первого аргумента прекращает вычисление остальных и тела. Известный результат тела не отменяет уже выполненные эффекты аргумента.

Target попадает в active stack **после** вычисления аргументов. Поэтому `f(f(x))` с нерекурсивным `f` допустим: внутренний вызов завершён до входа во внешнее тело. Это существенно отличается от настоящего вызова `f` из активного тела `f`.

Unsupported provider не исполняется под видом provider/v1: он даёт явный unknown. Статический use остаётся incomplete и тогда, когда неизвестная ветвь в конкретном запуске не выбрана.

## 4. Модульный summary и его предпосылка

Для каждого тела выводится `FunctionSummary`: definition revision, result type, use, транзитивные lookup bindings и их stamp. Use сохраняет все категории OBS: необходимые наблюдения ресурса, возможные ошибки, эффекты, config keys и причины неполноты.

Основное правило:

\[
U(\operatorname{call}\ f(a_1,\ldots,a_n))
= U(a_1)\cup\cdots\cup U(a_n)\cup U_{body}(f).
\]

Union применяется ко всем категориям summary, а не только к чтениям данных. Для отсутствующей, внешней или циклической цели добавляется соответствующая причина incomplete. Для неизвестных операций сохраняются правила OBS. Анализ ветвлений консервативно учитывает обе ветви.

Summary тела имеет условную интерпретацию: при неизменных семантических предпосылках, **равных значениях параметров** и равных требуемых наблюдениях ресурса тело сохраняет наблюдаемый результат в области модели. Совпадения типов параметров недостаточно. Использование переменной-параметра само по себе не создаёт чтение Authorship; происхождение её значения учитывается в use аргумента на месте вызова.

Пример: `constant(x) = 0` не читает `x`. Но `constant(effect("A", read_members()))` всё равно выполняет аргумент и его эффект. Нулевой use тела не даёт нулевой use вызова. Аналогично `twice(x)` не позволяет вычислять effectful аргумент повторно при каждом чтении параметра.

Эта версия не выводит demand к отдельным свойствам параметра. Если `count(xs) = size(xs)`, а caller передаёт `read ordered_members`, обычный модульный анализ сохраняет зависимость от порядка. Это сознательная консервативность. Проталкивание уточнения через параметр потребует собственного закона, условий и checker; R03 не предоставляет такое правило автоматически.

В рамках одного анализа summary тела можно переиспользовать с теми же точными предпосылками. Это не контракт сохраняемого межсессионного кеша. Распознавание циклов, вычисление closure и вывод use должны иметь отдельные состояния обхода: ранний выход из одного этапа не должен скрыть зависимости другого.

## 5. Точное транзитивное происхождение

Каждый статический lookup образует запись:

| Состояние | Что закрепляется | Последствие для полноты |
| --- | --- | --- |
| PRESENT | Target ID, signature revision, definition revision | Тело анализируется |
| EXTERNAL | Target ID и revisions объявления | Incomplete: поведения нет в профиле |
| MISSING | Target ID и явное отсутствие revisions | Incomplete: определение не найдено |

Closure содержит такие записи для entry, всех его аргументов, обеих ветвей и всех транзитивно вызываемых тел. Представление канонично: стабильная сортировка, отсутствие дубликатов, точная сериализация. Для одного target в одном immutable registry не могут одновременно действовать разные найденные определения.

Алгоритм closure — конечный обход с visited set:

1. Собрать статические targets в entry, обходя все дочерние выражения.
2. Для очередного target зафиксировать результат lookup, включая отсутствие.
3. Если тело присутствует и ещё не было пройдено, собрать все его targets.
4. Продолжить до пустой очереди, канонизировать bindings и вычислить stamp.

Это не active stack интерпретатора. Даже обнаруженный цикл `f → g → f` не разрешает пропустить другую ветку `g → h`. Изменение `h` должно менять closure независимо от того, где встретился цикл.

`registry_stamp` закрепляет весь переданный registry для provenance. `semantic_stamp` entry включает точный input consumer, его достижимый closure, config, provider, requirements и версии профиля/проверяющих исходников. Поэтому:

- изменение leaf callee при неизменном тексте entry меняет семантические предпосылки;
- добавление определения на месте прежнего MISSING меняет предпосылки;
- удаление вызываемого определения сохраняет вызывающего в графе как неполный;
- добавление корректной unrelated функции может менять registry stamp без изменения semantic stamp entry.

Полный registry всё равно проверяется как вход. Разделение stamps не разрешает скрывать некорректные unrelated определения. Оно отделяет происхождение полного snapshot от предпосылок конкретного потребителя.

## 6. Проверяемое понижение в закрытый OBS

### 6.1. Зачем нужен второй путь

Модульный анализ даёт переиспользуемое описание тела, но для применения уже проверяемых правил R03 нужен закрытый OBS AST. Поэтому CALL предоставляет отдельное детерминированное expansion. Это аналитическое представление; исходный CALL AST остаётся входом прямого исполнения.

Expansion разрешено только для полного resolved acyclic анализа. Missing, external, cycle, opaque/unknown и unsupported provider дают `BRIDGE_UNSUPPORTED`. Ошибки лимитов и проверки сертификата также не преобразуются в complete summary.

### 6.2. Hygiene и strict lets

Для вызова с параметрами `p1…pn` создаются свежие временные имена `t1…tn`. Каждый аргумент сначала преобразуется в **caller scope**. Затем формируется цепочка строгих lets:

```text
let t1 = lower(a1, caller_scope) in
let t2 = lower(a2, caller_scope) in
...
lower(body, scope containing only p1↦t1, p2↦t2, ...)
```

Все локальные binders тела тоже переименовываются в свежие имена. Temp не должен перехватывать свободное чтение в последующем аргументе. Callee не получает другие bindings caller. Тело и каждый аргумент появляются в lowering с предусмотренной кратностью вычисления; текстовая подстановка выражения вместо параметра недопустима.

Active stack расширяется только при преобразовании тела, а не аргументов. Уникальные имена выбираются детерминированно относительно полного множества исходных имён; повторная проверка того же входа должна получить то же дерево.

### 6.3. Ограничение размера

Даже ациклический граф функций может дать экспоненциально большое развёрнутое дерево. До построения expansion проводится preflight подсчёта AST-размера и JSON-глубины с ранней проверкой верхней границы. Превышение лимита обнаруживается до выделения полного дерева. Лимиты CALL-0.1 и диагностические коды перечислены в API; они являются частью принимаемой области входов, а не доказательством производительности реализации V1. Анализ и прямое исполнение дополнительно ограничены 65 536 внутренними шагами и общей глубиной обхода AST/тел функций 128. Превышение даёт диагностический CallError инструмента, без частичного complete Execution. Это не моделируемая ошибка приложения и не подтверждение эквивалентности по времени или затратам ресурсов. Глубина цепочки вызовов проверяется отдельно от memoization summaries.

### 6.4. Сертификат и checker

`Expansion` содержит точный context, полное expanded AST и bindings мест вызова к определениям/temps. Context включает entry, registry и closure stamps, profile revision и SHA-256 закреплённых OBS, R03 laws и CALL engine.

`verify_expansion` заново валидирует исходную программу, воспроизводит заданный lowering, сравнивает context, всё дерево и bindings, затем независимо от присланных summary получает `obs.infer_use`. Подмена одного узла, определения, revision или имени temp должна быть отказом проверки.

Повторное воспроизведение lowering защищает от поддельного сертификата, но **не является независимым доказательством семантической правильности самого lowering**. Lowering остаётся частью доверенной реализации исследовательского профиля. Его ошибки ищутся отдельным прямым CALL oracle, вручную заданными ожидаемыми результатами и сравнением с OBS-исполнением expansion.

На поддержанном DAG проверяется дополнительное согласование: модульный use исходной программы равен `obs.infer_use` проверенного expansion. Это условие относится к обычному use до уточнения законами.

### 6.5. Подключение R03

`refined_bridge_use` принимает только проверенное expansion. Далее R03 проверяет derivation для точного закрытого OBS Consumer и самостоятельно выводит уточнённый use. Сохраняются прежний фиксированный каталог законов, контекст и replay каждого шага. Законы не проталкиваются через параметры и не превращаются в правила произвольной подстановки.

Изменение исходной функции остаётся изменением семантических предпосылок CALL, даже если две expanded формы можно привести к общему выражению. R04 не расширяет отдельный R03 API эквивалентности правки на изменённый registry.

## 7. Решение о влиянии изменения

Для старого и нового Program сначала заново выводятся summaries и точные предпосылки. При добавлении или удалении consumer используется соответствующий случай OBS assessment. Для обеих существующих сторон действует порядок:

1. Неполнота анализа сохраняется как UNKNOWN.
2. Изменение entry, значимой definition/signature/closure, config, provider или requirements требует RECHECK при полном анализе.
3. Только при одинаковом semantic stamp допустимо сравнивать требуемые наблюдения конкретных старого и нового ресурсов.
4. EXCLUDED требует равенства всех необходимых наблюдений и отсутствия неизвестности. В refined-пути use предварительно получен через проверенный bridge и replay.

Таким образом, точность на уровне ресурса не отменяет проверку исходных предпосылок. Нельзя сравнить только `size` нового ресурса и забыть, что функция теперь возвращает другую величину.

Статусы требования `OPEN`, `REMOVAL_OPEN`, `UNCHANGED_UNASSESSED` сохраняются независимо. Ни EXCLUDED, ни равенство наблюдаемого поведения не являются satisfaction, полномочием выполнить изменение или нормативной приёмкой.

## 8. Несколько потребителей и обратный запрос

`extract_project` строит полный frozen snapshot из registry и конечного набора consumers. Каждый consumer анализируется автоматически. Дубликаты stable ID и несовпадение ключа mapping с ID записи запрещены. Порядок перечисления consumers не меняет manifest. Полная проверка тел registry выполняется для каждого Program под compile-config его Consumer. При пустом наборе consumers нет Program и его config, поэтому пустой project-query не является сертификатом типовой корректности всех объявленных тел registry. Его complete относится к поиску потребителей.

Обратный function-query возвращает consumers, в транзитивном closure которых есть target. Сюда входят MISSING bindings: появление отсутствующей функции должно обнаружить прежних вызывающих. Resource-query CALL-0.1 поддерживает Authorship и возвращает известных явных потребителей ресурса.

Если неизвестность не позволяет доказать полноту поиска, `complete=false` сохраняется рядом с найденными элементами. Пустой список без полноты не означает отсутствие потребителей.

Premise stamp любого запроса, включая пустой ответ, зависит от полного project manifest, в том числе набора consumers. Добавление нового consumer должно изменять основание старого пустого ответа. Перед использованием сохранённого ProjectGraph он сверяется с полным rebuild из собственных frozen исходников. Подмена analyses или manifest отвергается.

`assess_project` рассматривает объединение старых и новых consumer IDs. Удалённый consumer и удалённое ребро остаются частью перехода. Проверка только нового графа запрещена: она теряет ровно те связи, исчезновение которых может требовать пересмотра.

В этой реализации queries и assessments делают полную проверку snapshot. Persistent incremental index, транзакционная публикация поколений и восстановление из предыдущих глав остаются отдельными работами. Совпадение результата с полным rebuild — будущий oracle для такого индекса, а не заявление, что он уже реализован.

## 9. Свидетельства и незакрытые обязательства

Сохранённый отчёт (`r07:results/call-profile/report.json`) отделяет вручную заданные случаи, прямое исполнение, проверку lowering, конечные пары ресурсов, проверки revisions/project и обнаружение намеренно неверных вариантов. Воспроизведение описано в [README профиля](../../models/r07-core/experiments/call-profile/README.md). Числа из конкретного прогона не являются новыми критериями прогресса.

Минимальные отрицательные сценарии: unused аргумент с ошибкой/эффектом; повторное чтение параметра; захват caller-имени; nested `f(f(x))`; missing→present; изменение leaf callee; цикл с дополнительной зависимостью; stale пустой query; удалённый consumer; поддельное expansion; переполнение размера expansion. Тестовый oracle должен исполнять исходные вызовы напрямую, а не повторно использовать проверяемый lowering.

Остаются открытыми общий IR и семантические контракты V1, нормативное извлечение связей для всех конструкций, рекурсивные summaries, persistent incremental maintenance, интеграция с capability/acceptance, conformance и реальный A/B/C опыт авторства. T00 остаётся воротами совместимости с исходным репозиторием.

Следующая R05 должна собрать полный feature ledger V1 и единый семантический контракт: форма → IR → типы/порядок вычисления → ошибки/эффекты → oracle → владелец. Непокрытые persistence, события, миграции и другие обязательные возможности помечаются unresolved. OBS+CALL дают проверенные входы для этой работы, но не заменяют её область.
